# 下拉刷新：桌面鼠标输入的可达性与触摸门控（本机取证）

## 取证元信息与重跑

- 取证日：2026-09-29
- 环境：macOS（Apple Silicon）/ Compose Multiplatform 1.12.0 /
  `org.jetbrains.compose.material3:material3-desktop:1.12.0-alpha03` /
  `org.jetbrains.compose.foundation:foundation-desktop:1.12.0`
- 重跑：库层判定见第一节的 javap 命令；端到端门控见第三节的用例
  `:shared:desktopTest --tests "lovehan1me.ui.component.HanimePullRefreshInputTest"`
  （其 `滚轮在列表滚到顶部后继续上推不会拉出下拉指示器` 即第三节对照表第一行的固化）。
- 失效条件：Compose 改变滚轮/拖动的嵌套滚动派发方式时，第一、二节要重测；各节另记更细的触发条件。
- 起因：桌面端没有"下拉"手势，需要判断鼠标输入**会不会**触发下拉刷新、
  以及只认触摸的门控是不是在防一条真实路径。

### 一、库层：M3 的下拉刷新只看滚动来源，不看指针类型

- 结论：`PullToRefreshModifierNode.onPostScroll` 的判定只有
  `NestedScrollSource == UserInput` 这一条，**没有任何指针类型检查**。
  同时桌面滚轮的唯一路径 `MouseWheelScrollingLogic` 派发嵌套滚动时用的正是
  `NestedScrollSource.UserInput`。两条合起来说明"库层不拦鼠标"。
- 重跑：

  ```bash
  JAR=$(ls ~/.gradle/caches/modules-2/files-2.1/org.jetbrains.compose.material3/material3-desktop/1.12.0-alpha03/*/material3-desktop-1.12.0-alpha03.jar | head -1)
  rm -rf /tmp/m3probe && mkdir /tmp/m3probe
  unzip -o -q "$JAR" "androidx/compose/material3/pulltorefresh/*" -d /tmp/m3probe
  javap -p -c /tmp/m3probe/androidx/compose/material3/pulltorefresh/PullToRefreshModifierNode.class \
    | sed -n '/onPostScroll/,/^$/p' | grep -n "getUserInput\|isAnimating\|enabled"

  FJAR=$(find ~/.gradle/caches/modules-2/files-2.1/org.jetbrains.compose.foundation -name "foundation-desktop-*.jar" | head -1)
  rm -rf /tmp/fprobe && mkdir /tmp/fprobe && unzip -o -q "$FJAR" -d /tmp/fprobe
  javap -p -c /tmp/fprobe/androidx/compose/foundation/gestures/MouseWheelScrollingLogic.class | grep -c getUserInput
  ```

  实测输出：前者在 `onPostScroll` 里命中
  `NestedScrollSource$Companion."getUserInput-WNlRxjI"` 与 `equals-impl0`；
  后者计数 `1`（滚轮路径确实以 `UserInput` 派发）。
- 失效条件：material3 / foundation 版本变更（现钉在 `gradle/libs.versions.toml:50`、
  `:52`）。届时重跑本节两条命令复核。

### 二、输入可达性：哪种桌面输入才能把过卷位移交到父级连接

- 方法：在一个 `verticalScroll` 外层挂一个只记录不消费的 `NestedScrollConnection`，
  打印每次回调的 `source` / `consumed` / `available`，逐个输入试。
- 结论（实测，非推断）：

  | 输入 | 父级连接看到的东西 |
  |---|---|
  | 滚轮下推（内容可滚） | `post UserInput consumed=(0,-156) available=(0,-3)` —— 负方向 |
  | **滚轮上推、把剩余滚动余量用光后继续** | `pre UserInput available=(0,7999)` / `post consumed=(0,674) available=(0,7325)` —— **正方向，正是下拉消费的信号** |
  | 滚轮上推、内容本来就在顶部且不可滚 | **完全没有回调**（父级收不到任何位移） |
  | 鼠标按住拖动 | **完全没有回调** |
  | 触摸下拉 | 每个移动事件 `post consumed=(0,0) available=(0,4.x)` —— 正方向 |

  ⇒ 桌面滚轮能触发下拉的**唯一**形态是「列表先有滚动余量、同一次滚动把它用光后继续上推」。
  内容不可滚时直接上推、以及鼠标拖动，都到不了下拉刷新。
- 失效条件：Compose 改变滚轮/拖动的嵌套滚动派发方式（例如让鼠标拖动也走 UserInput）。
  届时本表要重测；重测方法见第三节的探针写法（已随本节结论一并删除，可按上表输入重构）。

### 三、端到端：门控开 / 关两轮对照

- 方法：`HanimePullRefreshBox` + `rememberPullToRefreshState()`，读 `distanceFraction`
  与 `onRefresh` 触发次数。门控的开关靠临时把 `TouchOnlyConnection.onPostScroll`
  首行改成 `if (true) return Offset.Zero`。
- 结论（实测）：

  | 输入形态 | 门控**关闭** | 门控**开启** |
  |---|---|---|
  | 1000dp 内容 / 初始位置 300 / 滚轮 -5000 | `distanceFraction = 2.0` | `distanceFraction = 0.0` |
  | 1dp 内容 / 位置 0 / 滚轮 -5000 | `0.0` | `0.0` |
  | 1dp 内容 / 位置 0 / 滚轮 -100 | `0.0` | `0.0` |
  | 触摸下拉 | `onRefresh` 触发 1 次 | `onRefresh` 触发 1 次 |

  ⇒ 桌面缺陷**成立**：门控缺失时，滚轮过卷会把下拉指示器整块拉出来（`distanceFraction` 达 2.0，
  远超阈值 1.0），且因为滚轮不产生抬手/fling，指示器会**挂在屏幕上不回弹**。
  注意 `onRefresh` 在两轮里都是 0 次 —— 该缺陷是视觉层面的，不是"多发了一次请求"。
  ⇒ 门控**有效且无副作用**：过卷被挡住，触摸照旧。
- 重跑：`:shared:desktopTest --tests "lovehan1me.ui.component.HanimePullRefreshInputTest"`
  其中 `滚轮在列表滚到顶部后继续上推不会拉出下拉指示器` 就是上表第一行的固化；
  反向验证 = 临时改 `TouchOnlyConnection` 首行后重跑该用例，实测
  `HanimePullRefreshInputTest > 滚轮… FAILED`。
- 失效条件：`HanimePullRefreshBox` 的嵌套滚动挂载顺序（`HanimePullRefreshBox.kt:93`）
  或 `TouchOnlyConnection` 的消费条件（同文件 `:130`）被改动。

### 四、一条被证伪的初判（留作教训）

初版回归用例用的是「1dp 内容 + 滚轮上下推」，它在门控开关两种状态下**都**通过 ——
即门控被摘掉之后用例仍然全绿，是**空用例**。原因是那种输入根本不产生父级可见的过卷位移
（见第二节表格第 3 行）。教训：只验"期望值没出现"的用例，必须先确认"不设防时期望值会出现"，
否则它验的是测试环境，不是被测代码。
