## 出口能力矩阵（自有源码 7 个客户端构造点）

**结论**：出口三件套（DNS 覆盖 / 显式代理 / 网关改写）在需要的地方是齐的；两处"裸"点是
刻意的（有理由），不是漏接。判据只有一处（`EgressPlanner.plan()`）——jvm 的 OkHttp 拦截器
与 iOS 的 Ktor 插件消费同一份计划、同一个熔断器，插件里没有第二份回退逻辑。

- 取证日：2026-10-02

- 重跑：

  grep -rn "platformOnNetworkChanged\|evictConnectionPools\|evictAll" --include="*.kt" shared/src video/
  grep -rn "platformSystemProxyUsable\|proxyUrlFor\|isBypassHost" --include="*.kt" shared/src video/

- 观测（矩阵）：

  | 构造点 | DNS 覆盖 | 显式代理 | 网关改写 | Cookie | 磁盘缓存 | 重试 |
  |---|---|---|---|---|---|---|
  | `ServiceCreator.hClient`（浏览 / API） | ✓ | ✓ | ✓ | HCookieJar | ✓ 10MB | ✓ 最外层 |
  | `ServiceCreator.getchuClient` | ✓ | ✓ | ✓ | NO_COOKIES | ✗ | ✓ |
  | `ServiceCreator.downloadClient` | ✓ | ✓ | ✓ | — | ✗ | ✓ |
  | `CdnFetchClient` 基础（封面 / 图片 / 保存 / 桌面下载） | ✓ | ✓ | ✓（不注 cookie） | — | ✗ | ✓ |
  | `createThirdPartyClient`（更新检查等第三方） | ✓ | ✓ | ✗ | — | ✗ | ✓ |
  | `DesktopDownloadWorkController.httpClient`（桌面下载） | ✓ | ✓ | ✓ | — | ✗ | ✓ |
  | `HanimeDns` 内部 DoH client | ✗ | ✗ | ✗ | — | ✗ | ✗ |

### 判为"刻意保留"的三处（不是缺陷）

1. **DoH client 裸**：它**就是**解析器 —— 接 DNS 覆盖会递归，接网关会绕回自己。
2. **第三方 client 不进网关**：网关只对 `--cf-hosts` 点名的域名走 CF IP + ECH；
   第三方域名进去只是普通转发，多一跳无收益（这些站点也不在阻断名单上）。
3. **`HCookieJar` 每个客户端各 new 一个**：类内是 companion 全局表（issue-71 的修法），
   实例只是入口，不产生分叉。

### 判为"人肉维护"的形状（本轮收口）

`ServiceCreator.evictConnectionPools()` 的清单原样写死了 4 组（hClient / getchuClient /
downloadClient / CDN 链），第 6 个客户端（桌面下载控制器，独立一组池）不在其中 —— 差集。

- 失效条件：矩阵随客户端增减失效；新增任何 `OkHttpClient.Builder()` 都要重跑本节重跑命令
  并把新点补进矩阵（工厂内部的分支也要一并看，如 `createCdnFetchClient` /
  `createThirdPartyClient` 这类同文件多入口）。

## C5 收口：网关种子表提升到 commonMain，iOS 不再传空

- 取证日：2026-10-02
- 环境：`:shared` commonMain / jvmMain / iosMain；iOS 壳（Xcode 26.6，Apple Silicon 模拟器目标）
- 重跑：
  1. `./gradlew :shared:compileKotlinIosArm64 :shared:compileKotlinIosSimulatorArm64 --console=plain`
  2. iOS 壳：`cd iosApp && xcodebuild -project iosApp.xcodeproj -scheme iosApp -configuration Debug -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO build`
- 观测：
  - 静态兜底 IP 表（原 `HanimeDns` 私有的 `cloudFlareIps`）上移为
    `HanimeConstants.CF_FALLBACK_IPS`
    （`shared/src/commonMain/kotlin/lovehan1me/core/constant/NetworkConstants.kt`），
    `HanimeDns` 改为读它 —— 一份表两个消费方（DNS 兜底链 / 三端起服器的 `ip-list`）。
  - iOS 侧新增 `EchGatePortReporter.fallbackSeedCsv()`；Swift 起服时传它
    （`iosApp/iosApp/EchGateBootstrap.swift` 的 `GateStartFlat` 第二个参数）。
  - Android / 桌面**行为不变**：它们本来就传"探测过能建连的种子"（`echGateSeedIps()`），
    而后者的兜底分支正是这张表。
  - iOS 为什么可以直接给全表：网关侧对种子**逐 IP 拨号挑能连的**（`gate.probeCandidates`），
    不可达项只会被跳过；而留空会被污染的 DoH 带偏（Android 实测 hanime1.me → Facebook 段、
    拨号 15s 超时）。
  - iOS 壳构建结果：`xcodebuild … BUILD SUCCEEDED`（本轮实跑，见"全量验证"一节同批记录）。
- 失效条件：`CF_FALLBACK_IPS` 变更后 iOS 侧自动跟随（同一份常量），但**报文里的 ip-list
  内容**会变 —— 若网关对 IPv6 项的处理有改动需复验；iOS 若将来引入自己的解析链，
  本节的"静态表即种子"结论需重新评估。

## 换网复位清单改登记制（并顺带为桌面备好回路）

- 取证日：2026-10-02
- 环境：`:shared` jvmMain / desktopMain；`:shared:desktopTest`（JVM）
- 重跑：
  1. `./gradlew :shared:desktopTest --tests "lovehan1me.data.network.NetworkChangeReactionsTest" --console=plain`
  2. 反向验证：`python3 /tmp/rv_network.py`（临时脚本，未入库；每轮先删该类的 XML 报告、finally 还原源码）
- 观测：
  - `ServiceCreator` 新增 `registerConnectionPoolEvictor`；`evictConnectionPools()` 改为
    "三条主链 + 遍历登记项 + CDN 链"。登记项抛异常只记自身，不连累其余复位
    （这里是"尽力清干净"，不是事务）。
  - 桌面下载控制器在 `init` 里登记自己的池，并用 `lazy.isInitialized()` 保证
    **没建过就不为复位把它建出来**（复位不该产生副作用）。
  - 新增用例 `登记过的额外连接池也会被摘`；反向验证 **PASS=1 FAIL=0 SKIP=0**
    （关掉遍历 → 该用例转红）。
  - 桌面**仍没有**网络变化事件（已知限制不变）：本项只把清单从"人肉维护"改成
    "谁建池谁登记"，桌面一旦接上检测即自动纳入。
  - **刻意未登记的一处**：`HanimeDns` 的 DoH client。它的池在换网后失配的代价是
    "DoH 多失败一次 → 连续 3 次后整档摘 30s → 系统解析与内置 IP 兜底"，自愈且代价小；
    而登记它需要在 DoH client 重建时替换登记项（否则登记表会随配置变更累积），
    复杂度与收益不成比例。
- 失效条件：若复位入口改为按类型/注解自动发现，登记表可删；**新增自建 OkHttp 客户端
  而没登记时，本项就退回人肉维护** —— 守卫测试只能证"遍历生效"，证不了"每个客户端都登记了"，
  后者靠代码评审。这条纪律与矩阵一节的重跑命令要一起看。
