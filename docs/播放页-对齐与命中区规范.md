## 二、目标规范

### 2.1 三条硬规则

1. **R1 间距只能来自 `Spacing` 阶梯**，且播放器 chrome 内**只允许两档**：
   - **8dp（`Spacing.medium`）**：同组控件之间（如「倍速 ↔ 清晰度」）。
   - **12dp（`Spacing.large`）**：跨组之间（如「chip 组 ↔ 图标按钮」）。
   - 0 只允许出现在「同一 `Row` 内的无缝图标对」，且必须是刻意的（见 2.3）。
2. **R2 间距表达只允许两种形态**：容器 `padding`，或 `Row(horizontalArrangement = spacedBy(x))`。
   **禁止手写 `Spacer(Modifier.width(…))`** —— 这是现状里 6/10/18 三个魔数的唯一来源。
3. **R3 图标尺寸只用 4 的倍数阶梯**，播放器内固定三档：
   - **32dp** 主操作（播放 / 下一集 / 全屏 / 返回 / 主页）
   - **24dp** 常规图标（`iconLarge`，顶栏辅助位）
   - chip 由文字决定高度，不参与图标阶梯。

### 2.2 唯一参考线：**16dp**

选 16dp 不是拍脑袋 —— 我们的图标是 **32dp 视觉装在 48dp 命中盒**里，单侧内缩
`(48−32)/2 = 8dp`。所以：

```
容器水平 padding 8dp  +  图标单侧内缩 8dp  =  图标视觉左缘 16dp
容器水平 padding 8dp  +  时间行 start 8dp  =  时间文字左缘 16dp
```

**两条线天然重合。** 这是一个免费的收敛点，只要把容器 padding 定为 **8dp**、
时间行额外缩进定为 **8dp** 即可，不需要任何补偿。

| 元素 | 目标左缘 | 推导 |
|---|---|---|
| 顶栏 返回图标 | 16dp | 容器 8 + 内缩 8 |
| 底栏 时间文字 | 16dp | 容器 8 + 额外 8 |
| 底栏 播放/下一集图标 | 16dp | 容器 8 + 内缩 8 |
| 底栏 末位全屏图标**右**缘 | 16dp | 容器 8 + 内缩 8（**要求图标 32dp，见 2.4**） |
| 底栏 进度条轨道 | **8dp** | 容器 8（**刻意例外**：轨道要贴容器满宽） |

进度条轨道是**唯一**的例外，且这个例外与 animeko 一致：它 expanded 态的 slider row 也是
`fillMaxWidth()` 落在容器 padding 内，时间文字靠额外 start 缩进对齐到图标线，而轨道贴边。

### 2.3 目标间距表（现状 → 目标）

| 位置 | 现状 | 目标 | 依据 |
|---|---|---|---|
| 顶栏 返回 ↔ 主页 | 2 | **0** | 同一组无缝图标对 |
| 顶栏 主页 ↔ 标题 | 10 | **8** | 跨组 |
| 顶栏 标题 ↔ 超分 | 10 | **8** | 跨组 |
| 顶栏 三个 chip 之间 | 6 | **8** | 同组（R1） |
| 顶栏 chip 组 ↔ 时间电池 | 6 | **8** | 跨组 |
| 底栏 播放 ↔ 下一集 | 0 | **0（保留）** | 无缝图标对，视觉间隙 = 8+8 = 16dp，已足够 |
| 底栏 chip 之间 | 6 | **8** | 同组 |
| 底栏 chip 组 ↔ 左/中/右相邻元素 | 4 / 8 | **12** | 跨组（消除命中盒重叠，见 §四-2） |
| 底栏 容器水平 padding | 12 | **8** | 参考线 16dp |
| 底栏 外层 Box 水平 padding | 18（仅 Glass） | **0（删掉）** | 两皮肤内缩必须一致 |
| 底栏 时间行 start | 4 | **8** | 参考线 16dp |

### 2.4 「26dp」必须改成 32dp —— 它数学上就产生不了 16dp 线

`PlayerSizes.bottomSecondaryIcon = 26.dp`（`Defaults.kt:201`）。

- 26dp 图标装在 48dp 命中盒 → 单侧内缩 `(48−26)/2 = 11dp`
- 容器 8 + 内缩 11 = **19dp** ≠ 16dp

**差 3dp。** 单看是「好像有点歪」，跟顶栏 16dp 并排就是明确的错位。
改成 32dp → 内缩 8 → 19 变 16，自动归线。**这是 26 这个数值的唯一问题，改掉它不需要别的补偿。**

> 顺带：26 也不是任何阶梯上的数（`Sizes` 是 32/40/56，`PlayerSizes` 其他是 24/32）。
> 它是个纯粹的遗留魔数。

## 三、`playerHitTarget` 的一个陈旧结论要更正

`VideoPlayerControls.kt:191-193` 的注释写着：

> 已知取舍：底栏是 6+12(进度条)+30(按钮行)+6 = 54dp，装不下两个 48dp，所以底栏按钮的命中盒
> 会向上压进进度条下沿 9dp

**这个前提已经不存在了。** 底栏操作行现在走 `PlayerSizes.bottomControlRow = minTouchTarget = 48dp`
（`VideoPlayerBottomBar.kt:468 / :501`），行高本身就 ≥ 48dp。命中盒 48dp 居中压在 32dp 视觉上，
上下各外扩 8dp，**完全落在 48dp 行内，不会溢出**。

→ 注释与「54dp / 9dp」的推算已经过期，应删除或改写，否则后人会按错误前提做设计。

## 四、命中区与触发的 4 个实证问题

### 4.1 点底栏空白 = 把控件关掉（最影响手感）

播放器根 `Box` 挂着全局单击手势：

```kotlin
// VideoPlayerUi.kt:414-457
Box(modifier = modifier.background(...).pointerInput(isLocked) {
    detectTapGestures(onTap = { showControlsState = !showControlsState }, …)
})
```

`PlayerBottomBar` 是这个 `Box` 的子节点（`BoxScope` 扩展 + `align(BottomCenter)`）。
Compose 的事件顺序是**子节点先于父节点**消费 Main pass，而 `detectTapGestures` 用
`awaitFirstDown(requireUnconsumed = true)`。于是：

- 点**按钮** → 按钮的 clickable 消费掉 → 父级不触发 → ✅ 正常
- 点**底栏的空白处**（chip 之间的间隙、expanded 态的中间占位、time 行右侧）→
  **没有任何子节点消费** → 父级手势触发 → ❌ **整条控制栏消失**

animeko 对此有专门一行防御（`PlayerControllerBar` 第 820 行）：

```kotlin
.clickable(remember { MutableInteractionSource() }, null, onClick = {}) // Consume touch event
```

**我们缺这一行。** 补上即可 —— 这是最低成本、收益最直接的一处。

### 4.2 「清晰度」右侧约 9dp 实际点不到，点下去会进全屏

`PlayerBarEndActions` 的顺序是：

```
[清晰度 chip] —2dp— [全屏图标]
```

- 清晰度 chip 视觉宽 ≈ 44dp，`playerHitTarget()` 以 `visual = null` 上报
  **内容固有宽度**（约 44dp），命中盒 48dp → 单侧外扩 **2dp**
- 全屏图标视觉 **26dp**，命中盒 48dp → 单侧外扩 **11dp**
- 两者**上报宽度**之间只隔 2dp

→ 全屏命中盒向左伸出 `11 − 2 = 9dp`，**覆盖在清晰度 chip 的有效区域上**。
Compose 命中测试对后置的兄弟节点优先 → **清晰度 chip 最右 9dp 改判给全屏**。

用中心距可以算清安全阈值：`chip宽/2 + gap + 全屏视觉宽/2 ≥ 48`
→ `22 + gap + 13 ≥ 48` → **`gap ≥ 13dp`**（按现状 26dp 全屏图标）。

按 §二 把全屏图标改成 32dp：`22 + gap + 16 ≥ 48` → **`gap ≥ 10dp`** → 取阶梯上的 **12dp** ✅

> 这也解释了为什么 §2.3 里「chip 组 ↔ 图标按钮」定为 12dp 而不是 8dp —— 8dp 仍会重叠 2dp。
> **间距值在这里有硬下限，不是审美问题。**

### 4.3 chip 没有按压反馈

`PlayerMenuChip`（`VideoPlayerControls.kt:240-245`）：

```kotlin
.combinedClickable(interactionSource = null, indication = null, …)
```

`indication = null` = 点了没有任何视觉变化。animeko 的入口是 M3 `TextButton`
（自带 ripple）。用户反馈的「响应触发问题」里，有一类就是「点了感觉没反应」。

→ 至少补一个 `indication`（或用 `interactionSource` 驱动一层背景 alpha 变化）。
注意 chip 是玻璃底，直接套 M3 默认 ripple 会盖住玻璃质感，建议走 alpha 反馈。

### 4.4 底栏两皮肤内缩差 18dp（重复强调，因为它既是「歪」也是「跳」）

见 §1 表格：Glass 的 `18dp` 外层 padding 是**独立于内容 Column 之外**多出来的一层，
而 Bilibili 分支没有这层。同一个 `PlayerBottomBarContent` 骨架被塞进两个不同的容器内缩里。

→ 删掉 Glass 的 `18dp`（改 0），让两个皮肤共用容器内缩。**这是「皮肤只改颜色不改几何」原则
的回归** —— 骨架已共用，容器却还在分叉。

## 五、关于「干脆照抄 animeko」—— 我的判断

**方向我同意，做法要改。** 三条具体理由。

### 5.1 许可证：不是死路，但要动文件

| | 本项目 | animeko |
|---|---|---|
| 许可证 | **GPLv3**（`README.md:4`、`LICENSE`） | **AGPLv3**（每个源文件头都带着） |

**GPLv3 §13 明确允许**「link or combine any covered work with a work licensed under
version 3 of the GNU Affero General Public License into a single combined work, and to
convey the resulting work」，结果按 GPLv3 传播。所以把我们 GPLv3 的项目并入 animeko 的
AGPLv3 代码**是允许的**，两个许可证在同一许可家族内是兼容的。

代价是三条，都必须做：

1. **保留原文件头**：animeko 每个文件头都写着
   `Copyright (C) 2024-2026 OpenAni and contributors` + AGPLv3 声明，照抄的代码必须原样带上；
2. **`NOTICE` 增记**：本项目 `NOTICE` 已有「为遵守上游许可证保留署明」的先例
   （Han1meViewer / GPLv3），照抄的模块同样是上游，同样要记；
3. **接受 AGPL §13 网络条款**：整个组合作品要满足「通过网络交互的用户须能获取源码」。
   对一个本地播放器来说这条基本是惰性的，但它会**跟着整个项目走**，不再只是被抄的那个模块。

> 结论：**法律上可行**，比一般人以为的宽松。所以这不该是拒绝照抄的理由 —— 但它是「抄了就要
> 认账」的理由，需要在动手前把 NOTICE 一起改掉，而不是事后补。

### 5.2 技术上「整段复制源文件」不成立

`PlayerControllerBar.kt` 的 import 区里，来自 `me.him188.ani.*` 的符号约 30 个：
`AniTheme`、`Lang`（20 个字符串资源）、`PlayerControllerState`、`PlaybackSpeedControllerState`、
`PlayerProgressSliderState`、`MediaCacheProgressInfo`、`MediaProgressFramePreviewState`、
`TouchSeekState`、`PlayerFullscreenState`、`VideoAspectRatioControllerState`、`SteppedSlider`、
`PlatformPopupProperties`、`slightlyWeaken` / `stronglyWeaken` …

这不是一个能贴进来的文件，而是**一个要移植的功能单元**。而且最核心的那几个是
**状态对象**（`PlayerControllerState` 带 `setRequestAlwaysOn`、`PlaybackSpeedControllerState`
带 `previewSpeed/commitSpeed`）—— 我们没有任何对应物，抄过来等于要连它的 state 层一起搬。

**「照抄」的移植成本比想象中高得多，而且抄进来的多数是我们要自己重写的东西。**

### 5.3 而且会抄错重点

animeko 真正值得抄的**不是控件长相**（我们的图标、token、玻璃底都是自研的，长相本来就不同），
而是它的**对齐纪律**。逐条列出，全部可在源码核对：

| animeko 的做法 | 位置 | 我们的现状 |
|---|---|---|
| **顶栏直接用 stock M3 `TopAppBar`**，自己一行 padding 都不写 | `PlayerTopBar.kt` 全文 92 行 | 手写 `Row(padding(horizontal = 10.dp))` |
| **只有一个间距表达式** `if (expanded) 8.dp else 4.dp`，在容器 padding / 时间行 start / 行内 spacedBy **三处复用同一表达式** | `PlayerControllerBar.kt:822 / 831 / 849` | 七种散落魔数 |
| **全文件零个手写 `Spacer(width(…))`** | 同上 | 顶栏 6 处 + 底栏 2 处 |
| 图标尺寸是**4 的倍数阶梯** 36 / 32 / 24 | `PlaybackIcon` / `FullscreenIcon` | 32 / **26** / 24 |
| 底栏根节点 **consume touch** | `:820` | 缺 |

**这五条才是「为什么 animeko 不歪」的全部答案。** 它们不涉及任何 AGPL 代码，是我们完全
可以独立实现的 —— 而且实现方式就是把 §二 的规范落进 token，比移植 800 行代码快得多。

### 5.4 我的建议

> **抄纪律，不抄代码。** 具体化为：把 §二 的规范落成一份单点常量表（直接进
> `HanimeDefaults.PlayerSizes` / `Spacing`），然后按 animeko 的**表达式结构**重写底栏与顶栏的
> 排布。预计改动 4 个文件、新增 0 个文件、无需接触许可证。
>
> 如果你之后确实想直接搬 animeko 的某个**具体控件实现**（例如 `SteppedSlider`、
> `VerticalSlider`、`OptionsSwitcher` 这类自包含的），那是可以的 —— 那时再单独走
> 「保留文件头 + NOTICE 增记」的流程。**但那应该是个案决策，不是整体策略。**
