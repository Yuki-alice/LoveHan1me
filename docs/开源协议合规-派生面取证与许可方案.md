## 0. 结论先行

**当前项目在法律上无法改为 MIT / Apache-2.0。**
"尽量宽松"的合法上限就是 **GPLv3——也就是现状**。

这不是保守建议，是有硬证据的三条锁定（见 §1）。要换协议，前置条件是**真的重写 183 个文件**，并且**换掉 mpv 播放引擎**，二者缺一不可。

## 2. 为什么不能"改一下 LICENSE 文件"就完事

1. **改 LICENSE 不构成重新授权**。逐字复制的那 9 个文件，版权人是上游作者，你无权替他们改许可。
2. **反向风险更大**：一旦以 MIT 发布，等于对外宣称"这些代码我有权宽松授权"。上游任何时候都可以要求下架、发 DMCA，而你的用户已经基于错误授权做了二次分发。
3. **自我承认的证据已在仓库里**：`@author Yenaly Liew` × 50 + NOTICE 的 "derive from" 声明。这些如果被删掉而代码没重写，性质从"合规署名"变成"隐瞒来源"，比现在严重得多。

## 3. 可执行路径

### 阶段 0 · 清理（零风险，建议立刻做）

| 动作 | 理由 |
|---|---|
| 删 `NOTICE` 的 **MomoQR** 段 | 全仓已无 MomoQR 代码（`app` 与 `shared` 均无匹配），只剩 `OpenSourceLicensesScreen.kt` 里的一条许可页条目。这是**过期声明** |
| 删 `LICENSE-APACHE` | 与 `LICENSE`(GPLv3) 并存是混乱源。Apache-2.0 部分单向兼容 GPLv3，已被吸收，无需单独全文 |
| **保留** `NOTICE` 的 animeko 段 | 那句 "No source code from animeko is included" 是**护身符**，别删 |
| `OpenSourceLicensesScreen` 的手工条目改为 aboutlibraries 自动生成 | 手工维护容易漏报依赖 |

### 阶段 1 · 重写强派生文件（按 ROI 排序）

1. **先啃 9 个 100% 逐字文件** —— 都是 15~173 行的小文件，成本极低，收益（消除"逐字复制"这个最刺眼的定性）最大。
2. **`Parser.kt`（1019 行，96.3%）** —— 最核心、最能代表原创性的文件。这也是路线图 M6 就规划过的事。
3. 其余 174 个 ≥0.75 的文件 —— 按业务价值排序，不必一次做完。

**重写纪律（决定成败）**：
- **clean-room**：看着需求/接口从零写，不要"打开上游边看边改"。
- **改包名 / 改变量名 / 重排函数不算重写**。行级相似度检测照样会判高。
- 重写后**立刻重跑扫描脚本**验证，别靠感觉。

**达标线建议**：`≥0.75 文件数 = 0`，且 `≥0.5 文件数 < 5%`。达标后才谈换协议。

### 阶段 2 · 隔离 GPL 引擎依赖

把 mpv / mediamp 的 import 收敛到 `feature/player/mpv/*` 单一包，其余业务代码对 mpv **零 import**。

目的不是现在换引擎，而是**保留未来重新授权的可能**：等哪天真换掉了 mpv，主体才有资格脱离 GPL。

### 阶段 3 · ⚠️ 必须叫停的一件事

上一轮规划的 **「P8 转 AGPLv3 + 直接借鉴 animeko 源码」** 与本目标**正面冲突**：

- animeko 的 `LICENSE.txt` 是 **AGPLv3**，比 GPLv3 **更严格**（多出网络交互条款）。
- 引入它的源码会把项目从 GPLv3 锁进 AGPLv3，方向完全相反。

**正确做法**：保持现状——只借鉴架构思想，不抄代码。目前仓库确实没抄（仅 `import org.openani.mediamp.*` 这种依赖库调用），`NOTICE` 的声明是准确的，**维持住**。

## 4. 如果仍希望有"宽松"的部分

可行的合法做法：**主体 GPLv3 不变 + 原创子模块单独宽松授权**。

把真正原创、零 GPL 依赖的模块（如 GIF 编码器、主题板生成器、搜索筛选快照）以 MIT / Apache-2.0 单独发布到独立仓库。

⚠️ 但要清楚边界：这些模块一旦被主 App **链接进同一个可执行文件**，整体仍是 GPLv3。MIT 授权只对"第三方单独取用该模块"有意义。

## 5. 顺带：内容侧免责

开源协议只管代码，不管你抓来的内容。建议在 README / 应用内补一句免责：本应用不托管任何媒体内容，所有数据来自用户主动访问的第三方站点，版权归原权利人所有。这与换协议无关，但能显著降低运营风险。

## 6. 责任边界

以上结论基于源码扫描与许可证文本的通读，**不是法律意见**。
若你仍打算以非 GPLv3 协议公开发布，建议二选一：

1. 咨询熟悉开源许可的律师；
2. 直接联系上游作者（`daisukiKaffuChino` / `Yenaly`）取得**书面**重新授权（dual-license 或例外条款）——这是唯一能在保留代码的前提下合法宽松化的路径。
