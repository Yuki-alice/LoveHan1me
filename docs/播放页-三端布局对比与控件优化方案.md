# 播放页三端布局对比与控件优化方案

> 对照对象：**animeko**（`open-ani/animeko` 桌面窗口模式）、**Kazumi**（B 站风）、
> **本项目 LoveHan1me**（宽屏双栏 / B 站风皮肤，浅色主题）。
> 三张截图均为实机截图，本文所有数字都是**从截图像素实测**得来，不是估计值。
> 方法见附录 A（含可复现脚本），源码位置逐条给出以便开刀。

## 0. 一句话结论

**骨架已经对了**：三行底栏、详情｜评论右栏、B 站风皮肤、时间行独占一行——
这些都和 animeko 同构，不需要重做布局。

**剩下的差距集中在四件事**：
① 内缩尺度（进度条比画面窄了 42dp）② 分组栅格（右侧按钮间距 27/16 不成节奏）
③ 层级颜色（进度条在恒黑画面上只有 2.44:1 对比度，不达标）
④ 列表留白（右栏 Tab 徽标压字、FAB 压内容）

其中 ①②③ 各有一个**结构性根因**（不是调数值能解决的），④ 是纯粹的实现疏漏。

## 2. 逐区对比

### 2.1 顶栏

| | animeko | Kazumi | 我们 |
|---|---|---|---|
| 左侧 | `← 01 集数+标题` | `← 标题`（常规字重） | `‹ 标题`（粗体，ink 高 19dp） |

| | animeko | Kazumi | 我们 |
|---|---|---|---|

## 3. 问题清单（按优先级）

### P0 —— 明显缺陷 / 无障碍不达标 / 越界

**P0-1 进度条对比度 2.44:1，低于非文本图形 3:1 门槛**
- 实测：播放进度 `137,78,90`（= 浅色主题的主色）压在未播放轨 `36,36,36` 上 → **2.44:1**
- 对照：animeko 淡紫 `198,177,252`/轨 `20,18,23` → **9.8:1**；Kazumi 亮绿 `161,211,148`/轨 `37,49,35` → **8.0:1**
- 根因：**播放器画面是恒定深色（黑），却直接吃了主题 primary**。浅色主题的 primary 本来就是给浅底准备的深玫瑰，放到黑画面里必然塌。这与上次「右栏强制深色」是同一条教训的镜像：**主题色不能无脑跨到恒定深色表面上**。
- 修法：新增 `HanimeDefaults.PlayerAccent`（播放器专用强调色，浅/深主题下都算过对比度），播放进度、缓冲、thumb 光晕一律走它；主题 primary 只用于"跟随主题"的界面（右栏、设置页）。**验收：进度色 vs 未播放轨 ≥ 4.5:1（文字级），至少 3:1。**

**P0-2 进度条比画面窄 42dp（左右各 21dp），两个参照都满宽**
- 实测：轨道 21dp..898dp；视频列 0..920dp
- 根因（两段叠加）：`PlayerBottomBarContent` 的 `Column(padding horizontal = Spacing.large /*12dp*/)` **＋ M3 `Slider` 载体自带的 thumb 半径内缩（≈9dp）**——后者是关键：`PlayerSlider` 用 M3 `Slider` 当触摸/无障碍载体，M3 会把 track 按 thumb 半径左右内缩，**这个内缩没有公开参数可关**。
- 修法（顺带解决 P0-1 的绘制自由度）：把三条色块从 `Slider` 的 `track` 槽**移出来**，改为进度条自己的 `Box(Modifier.fillMaxWidth())` 里自绘 4 层（底轨/缓冲/播放/thumb），M3 `Slider` 退回"全透明 + 只做触摸与无障碍"——animeko `MediaProgressSlider` 正是这个做法（951 行自绘 + M3 只当载体）。同时**进度条行不再吃容器水平 padding**（满宽），时间行与操作行保留内缩。

**P0-3 顶栏右侧文字组贴住右栏边界**
- 实测：右组 ink x768..914dp，视频列右缘 920dp → **净距 6dp**；左侧返回键视觉内缩 22dp → 左右不对称 16dp
- 代码：`BilibiliTopBar` 的 `Row(padding(horizontal = 10.dp))`，右组是三枚 `BiliTextButton` 紧排
- 修法：内容基线统一为 `barContentInset = 20.dp`（左侧图标视觉居中后即 22dp，取 20dp 对齐），右组额外补 `Spacer(16.dp)`；并把三枚纯文字按钮换成**图标 + 文字**或 icon-only（kazumi 的顶栏就是 4 枚图标）。

**P0-4 Tab 徽标与「评论」文字重叠**
- 实测：badge `x1192..1216, y40..56`；“评论”文字 `x1175..1204, y42..57` → **交叠 12dp**
- 原因：M3 `BadgedBox` 把 badge 放在锚点内容的 top-end 且**默认允许与内容重叠**
- 修法：badge 加 `Modifier.offset(x = 4.dp, y = (-4).dp)`，或把 tab 内容改成 `Row { Text; Badge }` 手动留 6dp 间距。**验收：徽标左边缘 ≥ 文字右边缘 + 4dp。**

**P0-5 评论 FAB 遮挡列表**
- 代码：`CommentScreen` 的 `listContentPadding` 默认 `PaddingValues(horizontal = 8.dp, vertical = 8.dp)` —— **没为 56dp 的 ExtendedFAB 预留底部空间**；FAB 宽 ~170dp（占右栏 47%）
- 修法（二选一）：
  - 保守：`PaddingValues(bottom = 56.dp + 16.dp)`，并给 FAB 的 `Modifier.padding(8.dp)` 保留；
  - 更贴 B 站风：**把 ExtendedFAB 降级为 56dp 圆形按钮**（icon-only，`ic_reply`），宽 170→56dp，右栏不再被切掉一半。
  另：它与上方 Tab「评论」是**重复入口**，若 Tab 已在当前页，可只在滚动超过阈值时才出现（现在 `showCommentFab` 已有类似逻辑，确认阈值）。

### P1 —— 一致性与分组

**P1-1 底栏右侧三元素间距不成栅格**：实测 ink 间距 `1.0x→480P = 27dp`、`480P→全屏 = 16dp`；左组图标间距 16dp。代码是三处不同的 `Spacer`（6dp / 6dp / extraSmall 2dp）叠加各自命中盒的结果。
→ 统一为 `Arrangement.spacedBy(12.dp)` + 等宽命中盒；文字按钮引入统一 token `barTextButton`（14sp、水平内边距 10dp、最小高 48dp），animeko 的「选集/适应/倍速」就是这种等距文字钮。

**P1-2 顶栏把产品名当功能名**：「Anime4K」用户不可解读（kazumi 叫「超分辨率」）。
→ 文案改「超分」/「超分辨率」，或中文 + 图标；三枚按钮的视觉权重拉开一档（截图/录制是次要动作）。

**P1-3 投票行三个 M3 `TextButton` 不成组**：`Row(Arrangement.spacedBy(4.dp))` 里放三个 `TextButton`——**M3 TextButton 最小宽 58dp + 内容内边距 12dp**，于是 4dp 的名义间距被撑成 ~28dp 的视觉间距；且「踩」无计数却与「顶」同宽 → 视觉不等重。
→ 换成自绘行内操作（`Icon` 16dp + 可选计数 + `spacedBy(16.dp)`，命中区 40dp），或统一 `contentPadding(horizontal = 8.dp)` + `minWidth = 0`。

**P1-4 弹幕输入框缺状态语义**：我们的 placeholder 是**宣传语**（"发个友善的弹幕，见证当下"）；kazumi 显示**状态**（"已关闭弹幕"），且框左侧有「弹幕开关」「弹幕设置」两枚图标。
→ placeholder 拆成「状态 + 引导」两态；若弹幕开关能力尚未接入，输入框应先呈现禁用态（现在能打字但发不出去，是"假入口"）。

**P1-5 三行左基线不一致**：时间行在代码里多一个 `padding(start = Spacing.small)`（4dp），实测 ink 起点 时间 19dp / 轨道 20dp / 操作行 22dp。
→ 引入 `barContentInset = 20.dp` 常量，三行共用；**进度条改为满宽（P0-2）后这一项必须同批做**，否则"贴边轨道 + 内缩时间"会更明显。

### P2 —— 打磨

- **P2-1 右栏评论卡密度**：卡内 12dp / 头像 40dp / 卡距 8dp → 一屏 4 张（animeko 无卡片、一屏 7+）。若不改卡片形制，可把头像降到 36dp、卡内边距 12→10dp。
- **P2-2 矮窗口缺 compact 行高**：行高恒 48dp（进度条行 + 操作行 = 96dp）。**`playerHitTarget(visual = …)` 工具已经有了**，正是为"视觉小、命中区 48dp"设计的 → 可在窗口高 < 860dp 时把两行视觉行高压到 36/40dp，省 ~20dp（画面多出 2.6% 高度）。手机横屏（360dp 高）收益更大。
- **P2-3 输入框高 40dp vs 行高 48dp**：让它与行高一致（44–48dp），命中区更舒服，也不会比左右图标"矮一截"。

## 5. 实施顺序与验收口径

**批次 1（P0，单文件为主，1 次编译可验）**
1. `PlayerSlider`：轨道自绘 + 满宽（P0-2）+ 进度色走 `PlayerAccent`（P0-1）
2. `BilibiliTopBar`：右组内缩 20dp + 图标化（P0-3）
3. `HostVideoTabs`：徽标偏移（P0-4）
4. `CommentScreen`：底部留白 / FAB 降级（P0-5）

**批次 2（P1，一致性）**：间距栅格 + `barTextButton` token + 内容基线统一 + 投票行 + 弹幕框状态。

**批次 3（P2，打磨）**：compact 行高、卡片密度、输入框高度。

**红线（三批共同）**
- **窄屏（内容宽 < 840dp）逐像素不变** —— 新增能力一律走"默认关的开关/默认值等于现状的参数"，`bilibiliStyle` 已经是这个模式。
- `:shared:compileKotlinDesktop` + `:shared:compileAndroidMain` + `:app:compileDebugKotlin` 三端全绿（iOS 目标另有既有欠账，不在本轮范围）。
- **改后必须回测**目标值表（附录 A 脚本原样重跑）：
  进度条 x = 0..920；播放进度对比度 ≥ 4.5:1；顶栏右组右缘 ≈ 900dp；
  徽标左缘 ≥ 评论文字右缘 + 4dp；FAB 与最后一张卡片不重叠。

## 附录 A：测量与复现

三张截图存于 `~/.workbuddy/clipboard-images/`。量纲先定，再量本体：

```python
from PIL import Image
import numpy as np
a = np.asarray(Image.open(shot).convert("RGB")).astype(int)

# 1) 定缩放：macOS 红绿灯红点直径（系统 12pt → 12px@1x / 24px@2x）
sub = a[0:80, 0:200]; R, G, B = sub[:,:,0], sub[:,:,1], sub[:,:,2]
red = (R>180)&(G<110)&(B<110)
ys, xs = np.where(red); print("红点直径", max(xs.ptp()+1, ys.ptp()+1))

# 2) 找轨道行：某行「非黑且非亮」的长行程
lum = a.mean(axis=2)
for y in range(y0, y1):
    row = lum[y, x0:x1]
    m = (row > 12)                     # 底轨很暗（≈14% 白 = 36/255）
    if m.sum() > 800: print(y, np.where(m)[0].min(), np.where(m)[0].max())

# 3) 进度色对比度（WCAG 相对亮度）
def L(rgb):
    c = [v/255 for v in rgb]
    c = [x/12.92 if x <= 0.03928 else ((x+0.055)/1.055)**2.4 for x in c]
    return 0.2126*c[0] + 0.7152*c[1] + 0.0722*c[2]
def ratio(a_, b_):
    la, lb = L(a_), L(b_); hi, lo = max(la,lb), min(la,lb)
    return (hi+0.05)/(lo+0.05)
print(ratio((137,78,90), (36,36,36)))    # 我们   → 2.44
print(ratio((198,177,252), (20,18,23)))  # animeko → 9.83
print(ratio((161,211,148), (37,49,35)))  # Kazumi  → 7.95
```

> 关键提醒：**我们那张截图是 2×**，所有像素值除以 2 才是 dp。直接拿像素当 dp 比会整体偏大 2 倍。
