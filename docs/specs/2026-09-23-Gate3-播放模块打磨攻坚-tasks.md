## 0. 前提

### 0.1 为什么单列

Gate 2 的验收只管"功能有没有"，播放模块剩下的全是**引擎抽象缝**带来的质量债：

## 2. G3-0 换底裁定

### 2.1 第一步是取证，不是决策

裁定把"Android mpv 内核 mediamp 不提供"写成了既定代价，这是**未验证的推断**。
开工前必须拿到三个答案：

1. **mediamp 是否有 Android mpv 后端？** 查 `org.openani.mediamp` 的 artifact 清单
   （我们桌面用的是 `mediamp-mpv-desktop` 0.3.2，`gradle/libs.versions.toml:66`）。
   animeko 桌面用 mpv、安卓用 exoplayer 是**它的选择**，不等于 mediamp 的能力边界。
2. **mediamp 的 `FramePreview` 在四端是否都是非破坏性的？** 桌面确认是
   （`SD/…/DesktopMpvPlaybackEngine.kt:377-378`，不 pause 不 seek）。这一条直接决定 G3-4b 的做法。
3. **`EchGateDataSource` 管道能否重接？** 旁证：animeko 用 `mediaSourceInterceptor = pipeline::intercept` 挂进去。

### 2.2 决策矩阵

| 条件 | 结论 |
|---|---|
| mediamp 有 Android mpv 后端 **且** FramePreview 四端非破坏 | **换**。删 Exo/System/mpv-android/iOS 四引擎，G3-5/G3-6 规模降到 S/M |
| 有 Android mpv 后端，但 FramePreview 仅桌面可用 | 换，G3-6 仍可做 |
| **无** Android mpv 后端 | 若"Android mpv 内核"是产品刚需 → **不换**，G3-5 按三端各写一遍计价 |

**2026-09-23 补充取证（更新了上面这张表的输入）：**

1. **mediamp 的 mpv 后端有 `androidMain` 源集**（`MpvMediampPlayer.android.kt`、
   `MpvFramePreview.android.kt` 等，main 分支）。所以"Android mpv 后端"**可能确实存在**，
   只是 README 的支持矩阵把 Android 标为 ExoPlayer（推荐后端 ≠ 唯一后端）。
   ⚠️ 需确认我们依赖的 **0.3.2** 是否也带 Android 产物 —— 这直接决定换底能否保住 Android mpv 内核。
2. **换底会让 Android 失去画面比例。** mediamp 的 exoplayer 后端**未实现** `VideoAspectRatio`
   （其 `androidMain` 下 14 个 kt 文件里没有 aspect 相关文件，对比 mpv 后端有
   `MpvVideoAspectRatio`）。而 animeko 的 Android 端因此**根本没有这个入口**。
   → 若 Android 走 exoplayer 后端：画面比例从"Fit/Crop 两档"退化为"没有"，
   这是 G3-9 刚要补的能力反过来被换底吃掉。若 Android 走 mpv 后端则不受影响。
3. **换底对 iOS 无 FramePreview 增益**：mediamp 的 avkit 后端未实现该 feature。

⚠️ 换底的代价要重估，别用裁定里那句 LOC 对比——审阅实测我方 16,934 行、animeko 16,316 行（差 4%），
且 animeko 的后端 mediamp **不在本仓**（`find reference -iname "*mediamp*"` 为空），口径不对等。

## 3. G3-7 播放器稳定性回归（最先做）

## 4. ~~G3-4 预览帧管线~~ —— 不做（2026-09-23 产品取舍）

保留诊断，因为**将来若要捡起来，坑不在 UI 而在语义**。

### 4.1 现状：能力在，语义不对

`grabFrameArgb` 四端全实现、`supportsFrameCapture()` 四端 true，但**语义是"抓一张确定的帧"**：

| 端 | 实现 | 是否破坏性 |
|---|---|---|
| 桌面 mpv | `SD/…/DesktopMpvPlaybackEngine.kt:369-381`，mediamp `features[FramePreview.Key].getPreviewFrame(pos,w,h)` | ✅ **非破坏性** |
| Exo | `SA/…/ExoPlaybackEngine.kt:233-236`：`player.pause()` + `seekTo` + `FrameReadyWaiter` 等帧 | ❌ 会暂停并跳走 |
| mpv-android | `SA/…/MpvPlaybackEngine.kt:323-324`：`pause=true` + `seekTo` | ❌ 同上 |
| iOS | `SI/…/IosFrameCapture.kt`：`player.pause()` + `seekToTime` | ❌ 同上 |

对 GIF 录制 / 截图（暂停着抓）这个语义是对的；**对拖动预览是错的** —— 拖进度条时不能把播放暂停。

### 4.2 若将来要做（记录坑位，不要现在开工）

- **桌面**：引擎侧 mediamp `FramePreview` 非破坏性，可直接做，只缺滑条 UI
  （LruCache(8) + 2s 栅格键去重 + 50ms 去抖 + 切集预热；拖动期间只写 `previewPositionRatio`，
  引擎只在 `onPreviewFinished` 被 seek 一次；BT/未下载区域不请求以免抢播放带宽）。
- **Android**：~~基本不可做~~ —— **2026-09-23 更正：可做，我之前的判断是错的。**
  依据是本仓 `SA/…/ExoPlaybackEngine.kt:204-207` 的注释"MMR 拿不到自定义 header"，
  但**这条注释不准确**：`MediaMetadataRetriever` 有 `setDataSource(uri, headers)` 重载。
  mediamp 的 `ExoFramePreview.kt` 正是这么做的：

  ```kotlin
  is UriMediaData -> {
      if (uri.startsWith("http://") || uri.startsWith("https://")) {
          retriever.setDataSource(uri, data.headers)      // ← 带 header
      }
  }
  ```
  其注释明写："The retriever decodes independently from ExoPlayer, so **extracting a frame
  never disturbs playback**." —— 即非破坏性，正是拖动预览需要的语义。
  代价是**重新打开媒体源消耗带宽**（其注释也提醒"未下载区域会阻塞，优先请求已下载位置"），
  不是播放中断；可用缓存/去抖/限流化解。
  ⚠️ 那条过期注释建议顺手改掉，它会持续误导后来人。
- **iOS**：可行解是 `AVAssetImageGenerator`（从 asset 取帧，不动 player），但现有实现没走这条。
  注：mediamp 的 avkit 后端**未实现** `FramePreview`，所以换底对 iOS 预览帧无帮助。

### 4.3 遗留的过期注释

`S/feature/video/VideoPlayerControls.kt:284-285` 那句"有帧预览需要引擎提供抓帧…等接上再做"
是**过期注释**（能力早已接上，缺的是非破坏性语义）。建议改为"能力已具备但语义为破坏性，
拖动预览未启用"，否则下一个人会再得出一次"引擎没有能力"的错误结论。这个改动极小，
可在 G3-3 顺手做掉。

## 5. G3-9 画面比例三端拉齐（真实现）

### 5.1 先澄清：不是"没接"，是"三端不齐"

链路是通的（别去找断线）：`VideoRouteHostScreen.kt:918-923` → `VideoShellContent.kt:220-222`
→ `VideoPlayerUi.kt:910-912` → `VideoPlayerBottomBar.kt:255-264 / 369-378`（expanded 与
collapsed 两套菜单），持久化在 `SettingsRepository.kt:176` + `DataStoreManager.kt:160`。

**真问题在能力表**：

| 引擎 | `supportedAspectModes()` | 实情 |
|---|---|---|
| 桌面 mpv | Fit / Stretch / Crop（`:267-268`） | ✅ 三档 |
| mpv-android | Fit / Stretch / Crop（`:225-226`） | ✅ 三档 |
| iOS AVPlayer | Fit / Stretch / Crop（`:155-156`） | ✅ 三档（走 `videoGravity`） |
| **Exo（Android 默认内核）** | **只有 Fit / Crop**（`ExoPlaybackEngine.kt:120-121`） | ❌ **没有 Stretch** |
| **System MediaPlayer** | **完全没 override** → 基类 `emptyList()` | ❌ **菜单直接不出现** |

所以用户实际碰到的是：**Android 默认内核上没有"拉伸"档，切到 System 内核连菜单都没了。**

### 5.2 为什么 Android 缺 Stretch

Media3 的 `setVideoScalingMode` 只有 `SCALE_TO_FIT` 与 `SCALE_TO_FIT_WITH_CROPPING`
两档 relevant 值，**没有拉伸**。代码注释（`ExoPlaybackEngine.kt:112-119`）明写：

> 不要为了凑三档去接 media3-effect 的 `ScaleAndRotateTransformation`：
> 那条路要重走 prepare（与超分切档同款重建续播），为了一个"把人拉扁"的非推荐档位付这个代价不值当。

这个取舍本身合理，但**结果是三端能力不齐**，而"补齐能力"正是 Gate 3 的职责。

### 5.3 animeko 怎么做：自己一行都不实现，全委托 mediamp

对照结论先说清楚：**这一项不要向 animeko 对齐，我们比它强。**

animeko 的实现（`reference/animeko/.../ui/VideoAspectControllerState.kt`，**全文件 68 行**）：

```kotlin
class VideoAspectRatioControllerState(
    private val videoAspectRatio: VideoAspectRatio,   // ← mediamp 的 feature
    scope: CoroutineScope,
) {
    var currentMode by mutableStateOf(videoAspectRatio.mode.value)
    fun setMode(mode: AspectRatioMode) = videoAspectRatio.setMode(mode)   // 直接转发
    companion object { val Entries = AspectRatioMode.entries }            // 固定三档
}
```

三条设计点：

1. **能力判定 = feature 查找**（`EpisodePage.kt:1109`）：
   `vm.player.features[VideoAspectRatio]?.let { ... }` —— 返回 null 就不建 state，
   UI 侧 `videoAspectRatioControllerState?.also { ... }` 就不显示入口。**全有或全无**。
2. **档位固定三档，不做细粒度过滤**：`VideoAspectRatioSelector` 用
   `optionsProvider = { Entries }`（`PlayerControllerBar.kt:664`）。因为 mediamp 的契约是
   `setMode(mode: AspectRatioMode)` 吃掉三档枚举，后端要么全支持要么不注册。
3. **无平台分支**：`AspectRatioMode` 在 animeko 全仓只出现在 3 个文件，全是 commonMain。
   另有 `NoOpVideoAspectRatio`（空实现）供预览/测试兜底，以及
   `VideoAspectRatioControllerStateTest` 纯状态单测。

**但后端能力其实不齐**（查 mediamp main 分支源码）：

| mediamp 后端 | `VideoAspectRatio` | `FramePreview` |
|---|---|---|
| mpv（android / desktop / ios） | ✅ `MpvVideoAspectRatio`（`keepaspect` + `panscan`） | ✅ |
| **exoplayer（Android）** | ❌ **未实现** | ✅ `ExoFramePreview` |
| avkit（iOS） | ❌ **未实现** | ❌ 未实现 |

→ **animeko 在 Android 上根本没有画面比例入口**（Android 只能用 exoplayer）。
它的 mpv 实现是 `FIT: keepaspect=true/panscan=0`、`CROP: keepaspect=true/panscan=1`、
`STRETCH: keepaspect=false`，**和我们 `MpvPlaybackEngine.kt:261-275` 的做法一样**。

对我们的三点结论：
- **我们的 `supportedAspectModes()` 逐档声明比 animeko 的"全有或全无"更严谨**，不要退化。
- G3-9 的目标是**我们自己的三端一致**，不是对齐 animeko（它更弱）。
- ⚠️ **换底 mediamp 会让 Android 失去画面比例**（exoplayer 后端未实现）。这是换底的
  **新增代价**，之前没识别出来，见 §2.2。

### 5.4 做法（按性价比排序）

1. **先确认 Crop 在 Android 上到底生不生效。** `SCALE_TO_FIT_WITH_CROPPING` 配合
   全屏 `SurfaceView` 在部分设备/Media3 版本上行为不一致。**真机验证优先于写代码**——
   如果 Crop 也没生效，那 Android 上等于"两档里只有一档是真的"，问题比现在判断的更严重。
2. **给 System 引擎补 `supportedAspectModes`**（至少 Fit/Crop 两档，或明确返回空并在
   UI 上说明"该内核不支持"）。当前返回 `emptyList()` 导致菜单静默消失，属于"假占位"。
3. **Stretch 的取舍要重新拍一次。** 两个选项：
   - (a) 接受三端不齐，在 UI 上如实标注"当前内核不支持拉伸"——零成本，诚实；
   - (b) 接 `ScaleAndRotateTransformation` 补齐——代价是切档重走 prepare（闪一下）。
     注意超分切档**已经接受**了同样的代价，所以"重走 prepare"不再是绝对的否决理由，
     值得为一致性重新评估。

### 5.5 验收

三端 × 三内核 的能力矩阵写清（哪档真生效、哪档降级、哪档不支持），
`supportedAspectModes()` 的返回值与**真机实测**一致；UI 对不支持的档有说明而不是静默消失。

## 6. G3-1 超分诚实化

### 现状

### 要点

- 素材已在仓：`shared/src/commonMain/composeResources/files/shaders/` 9 个 Anime4K `.glsl`，
  MIT bloc97 上游。mpv 路径在用（`S/core/util/MpvShaders.kt:22-34`：PERFORMANCE 3 个 / QUALITY 5 个）。
- 与 animeko 逐字比对的结果（审阅实测，别照抄裁定那句"9 个逐字相同"）：
  **7 个 md5 完全相同**；`Anime4K_Clamp_Highlights.glsl` 仅尾随空白差异（语义相同）；
  **`Anime4K_Upscale_CNN_x2_S.glsl` animeko 根本没有**（它只有 8 个）。
  → PERFORMANCE 链依赖的正是 animeko 没有的那个，所以档位配置本来就不是抄的。
- 工作量在"按 `//!DESC` 切分 `.glsl` → 注入模板 `.frag` → 多 pass FP16 ping-pong"，
  不是找素材。animeko 的 `Anime4kQualityEffects.kt:106` 可作形态参考：
  `if (upscale) Size(inputWidth*2, inputHeight*2) else Size(inputWidth, inputHeight)`。
- **二选一**：接真 CNN 链，或把菜单文案改成"锐化"。不要维持现状。

### 附带

- 等级目前是 `var superResolutionIndex by remember { mutableStateOf(0) }`
  （`S/feature/video/VideoRouteHostScreen.kt:227`），**无设置键**；而 Exo 引擎的 level
  跨 re-prepare 存活（`SA/…/ExoPlaybackEngine.kt:53`）→ 菜单可能显示"关闭"而特效仍挂着。
  加键时**注意本仓首启即全量落盘，改默认值对老存档无效，需读侧回落**。
- Android mpv 侧同源问题：`MpvPlaybackEngine.kt:351` 的 `setSuperResolution` 不记住等级、
  `load()` 后不重挂。
- **两侧都没有任何 FPS / GPU 时间 / 输出像素的实测**。做完请补一次性能实测，"超分"的代价目前无人知道。

## 7. G3-10 超分性能与掉帧治理（实测痛点，次优先）

> 用户实测反馈：**开超分后画面卡顿 + 弹幕抖动**。
> 关键判断：这**是一个问题的两种表现**——超分把渲染帧率打下去，`withFrameNanos` 的
> delta 从 16.7ms 变成 33~66ms，弹幕按 `nowMs` 闭式解算，一帧就跳很远，于是"抖"。
> 所以 G3-2 的 PLL 只能摊平相位抖动，**救不了掉帧**；根因在超分开销。

### 7.1 现状：三重叠加，且无门控

打开超分（桌面路径）时同时吃到三份开销：

1. **Anime4K CNN shader 链**（`S/core/util/MpvShaders.kt:22-34`）
   - PERFORMANCE 3 个：`Clamp_Highlights` + `Restore_CNN_S` + `Upscale_CNN_x2_S`
   - QUALITY 5 个：`Clamp_Highlights` + **`Restore_CNN_VL`(144KB)** + **`Upscale_CNN_x2_VL`(146KB)**
     + `AutoDownscalePre_x2` + `Upscale_CNN_x2_M`
   - 注意 QUALITY 链里含 **x2 放大 → x2 降 → x2 再升**，等于跑了**两轮放大**。
2. **mpv 缩放算法被全局换成最贵的一档**
   `SD/…/DesktopMpvPlaybackEngine.kt:400-403` 把 `SCALING_KEYS`（`:560`
   = `scale` / `cscale` / `dscale` / `sigmoid-upscaling`）**全部**设成 `ewa_lanczossharp`
   + `sigmoid-upscaling=yes`。`ewa_lanczossharp` 是 mpv 里最贵的缩放之一。
   ⚠️ 这不只是 shader 链的开销，是**全局叠加**。
3. **没有分辨率门控**：1080p 片源开 QUALITY 会被 x2 放大到 2160p 跑 VL 级 CNN，
   再用 lanczos 缩回窗口尺寸 —— 算力全花在"放大再缩回"上。

另外 `dscale`（缩小）也用 `ewa_lanczossharp` 属于**方向错配**：缩小用 lanczos 既贵又容易振铃，
通常 bilinear / spline 就够。

### 7.2 第一步必须是量化

代码注释自陈"**两侧都没有任何 FPS / GPU 时间 / 输出像素的实测**"——现在所有优化判断都是猜。
先加实测（帧时间分布 + 输出分辨率 + 各档位的相对开销），再谈优化。没有这一步，
后面每一项都是在黑暗里调参。

### 7.3 优化项（按性价比排序）

1. **分辨率门控**：源 ≥1080p 时只跑 Restore、跳过 Upscale（放大无意义且最贵）。
   这一条预计收益最大。
2. **`dscale` 换便宜算法**（`scale`/`cscale` 保留 lanczos）。改动一行。
3. **QUALITY 链裁剪**：去掉 `AutoDownscalePre_x2` + `Upscale_CNN_x2_M` 这第二轮升降，
   或把它降级为独立开关。
4. **默认档位下调**：默认 OFF 或 PERFORMANCE，别让用户一上来就掉进 QUALITY。
   注意本仓**首启即全量落盘**，改默认值对老存档无效，**读侧要回落**。
5. **弹幕侧自适应**：检测到帧时间持续超阈值时，降低同屏弹幕上限。
   这是兜底，不是药——根因仍是 1~4。

### 7.4 验收

- 有实测数据：各档位 × 各分辨率的帧时间分布（不是"感觉快了"）
- 开 PERFORMANCE 时中低端设备不掉帧；QUALITY 只在高端设备/低分辨率源上可用
- 开超分时弹幕不抖（先靠 1~4 把帧率救回来，再靠 G3-2 的 PLL 摊平残余抖动）

### 7.5 与 G3-1 的关系

G3-1 解决"Exo 路径是不是真的超分"（诚实性），G3-10 解决"开超分还跑得动吗"（性能）。
两者都落在超分上，**建议合并推进**：先把开销测清楚，再决定 Exo 那条 CNN 链要不要接
（如果连 mpv 的原生链都跑不动，Exo 上接真 CNN 只会更糟）。

## 8. G3-2 弹幕：两处外科手术，几何不动

闭式解算是资产（`S/feature/danmaku/DanmakuEngine.kt:187-188`，每帧位置由 `nowMs` 直接算出，
不存在累积漂移），比 animeko 的增量二分 + 防超车更干净。**不重写**。

### (a) 帧时间 PLL 平滑

现状：`S/feature/danmaku/DanmakuLayer.kt:75` 直接吃 `withFrameNanos` 原始值。
Skiko 上它给的是 EDT 回调开始时刻而非 vsync，原始 delta 会在 12/21/14ms 之间抖 → 弹幕左右抽动。

取 animeko `FrameTimeSmoother.kt:66-91` 的算法（简化 PLL）：EMA 估计周期（钳制 20~500Hz）、
相位误差以 0.1 增益回灌、校正量上限 0.2×周期、≥250ms 空档直接透传。
掉帧被摊平而非一次跳完，长期漂移有界。

注意别动空闲降频：`DanmakuLayer.kt:76` 的 `delay(IDLE_POLL_MILLIS)`（`:182` 定义 50L）。

### (b) 文本一次栅格化

现状：`DanmakuLayer.kt:133-157` 每条弹幕两次 `drawText`（描边 1.5dp + 填充），
每帧还走 `textMeasurer.measure`（`:164` 缓存 512 条）。

取 animeko `StyledDanmaku.kt:77-82`：首次绘制栅格化成 `ImageBitmap`，之后每帧只 `drawImage`。

### 验收

两项合计 <200 行，且都能套 animeko 那套**纯状态测试**范式（有 `FrameTimeSmootherTest` 可参考）。
渲染侧用 `DanmakuLayerRenderTest` 的落墨断言兜底。

## 10. G3-8 引擎测试补位

### 现状（审阅修正后）

### 根因：`shared` 根本没有 Android 测试源集
