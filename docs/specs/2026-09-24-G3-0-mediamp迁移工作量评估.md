# G3-0 换底 mediamp —— 工作量评估

> 取证日期 2026-09-24。所有数字来自本仓代码实测 + mediamp 上游产物核验（版本 0.3.2）。
> 本文只回答"多大"，不回答"该不该换"；决策矩阵见
> `docs/specs/2026-09-23-Gate3-播放模块打磨攻坚-tasks.md` §2.2。

## 0. 许可分层：这一步把决策难度降了一个数量级

> **2026-09-24 关键取证**：animeko 的播放器能力不在 animeko 里，在 **mediamp** 里。
> 而 mediamp 是 **Apache-2.0**，不是 AGPLv3。这条改变了整个"能不能抄"的计算。

| 层 | 许可证 | 能怎么用 | 备注 |
|---|---|---|---|
| **mediamp**（播放后端） | **Apache-2.0** | ✅ **可直接依赖，也可参考其源码实现** | 与 GPLv3 兼容；Apache-2.0 要求保留声明 → 增记 `NOTICE` |
| `mediamp-mpv` Android AAR 内 libmpv `.so` | Apache-2.0 + LGPL-2.1-or-later | ✅ 兼容（LGPL-2.1 可升至 GPLv3） | 用 `-Dgpl=false` 构建 |
| `mediamp-mpv-runtime-linux-x64` | **GPL-3.0** | ✅ 兼容（我们就是 GPLv3） | 该包 libmpv 带 GPL-only X11 代码 |
| animeko `app/` 与 `video-player/` | **AGPLv3** | ❌ 只能用其**设计**，不可用其代码 | 除非把本仓 LICENSE 升到 AGPLv3 |

**所以"模仿 animeko"的正确姿势是：用 animeko 用的那个库，而不是抄 animeko 的代码。**

三处证据：
- mediamp `LICENSE` 全文是 Apache License 2.0；README 明确
  "All MediaMP source code is licensed under the Apache License version 2"
- animeko 的 `VideoAspectRatioControllerState` 只有 **68 行**，能力全在
  `player.features[VideoAspectRatio]`（mediamp）
- 我们桌面**已经在用 mediamp**，这条路已被证明走得通

→ G3-0 的性质因此变了：不是"要不要抄 AGPLv3 代码（需升 LICENSE）"，
而是"**要不要接一个 Apache-2.0 的库（只需 NOTICE 增记）**"。

## 0.1 结论速览

| 场景 | 范围 | 净改动量 | 规模 | 代价 |

## 3. 四个会让工作量翻倍的风险

### 3.0 "摸着石头过河"的边界：河里哪些地方没有石头

采纳"跟随 animeko 设计"是合理的，但要清楚三块：

**(a) animeko 自己也没解决、抄不来的：**
- **Android 画面比例** —— exoplayer 后端未实现 `VideoAspectRatio`，animeko 的 Android 端
  **根本没有这个入口**。我们反而比它多（Exo 有 Fit/Crop）
- **画面调节 UI** —— `G2-播放器对照表` 已确认 animeko 也没有，这是本仓自有需求
- **iOS 预览帧** —— avkit 后端未实现 `FramePreview`
- **超分性能** —— animeko 也挂 Anime4K，同样没有性能实测数据

**(b) 我们特有、animeko 完全没有的（必须自己趟）：**
- ECH 免梯网关（Hanime1 站点特性）
- 双源弹幕（评论投影 + 弹弹）
- javchu 双站点热切换
- CF 过盾

**(c) animeko 解决但我们不能直接搬的：** 其 AGPLv3 的 UI 代码
（`PlayerControllerBar.kt` 1000+ 行等）——除非升 LICENSE。

→ **结论：mediamp 能替我们解决"播放后端能力"，解决不了"Hanime 特有的网络与站点纵深"，
也解决不了"我们比 animeko 多出来的那部分需求"。**

### 3.1 Android mpv 的 native 库没人分发（最大未知数）

核验结果：

- `org.openani.mediamp:mediamp-mpv-android:0.3.2` **存在** ✅（AAR 已发布）
- 但该 AAR **只有 73 KB**：内部仅 `classes.jar` + `AndroidManifest.xml` + `R.txt`，**零个 .so**
- **0.5.0 的 AAR 同样只有 79 KB、零个 .so** —— 所以不是版本问题
- `mediamp-mpv-runtime-*` 只发了 **linux-x64 / macos-arm64 / macos-x64 / windows-arm64 / windows-x64**
  —— **没有 Android**
- ⚠️ mediamp README 写"Android AAR bundles libmpv `.so`"，**与上面实测不符**。
  要么 README 过时，要么 .so 走 `mediamp-native-loader-android` 从别处加载 —— 需要向
  上游确认加载约定（AAR 的 `classes.jar` 里有 `LibraryLoader.android`，可反查期望路径）

→ Android 的 `libmpv.so` **必须自己打包**，且要匹配 `mediamp-native-loader-android` 的加载约定。
我们现在用的是 `com.github.abdallahmehiz:mpv-android:v0.1.7`（`libs.versions.toml:131`），
它的 .so 能否被 mediamp 的 loader 直接吃，**没有先例，需要 spike**。

**这条是场景 C 的成败手**。评估时不要把它当成"接个依赖"，它可能是几天到几周，
也可能结论是"接不上"。

### 3.2 ECH 网关要走两条完全不同的路

`EchGateDataSource.kt`(76 行) 现在是 **Exo 专属**的 `DataSource.Factory` 包装，
在 `open()` 层按"每个请求的实际 URL"改写（HLS 分片域名与顶层不同，工厂级加头会错贴）。

换底后：

- **Exo 后端**：要改接 mediamp 的 `MediaData` / 数据源注入点
- **mpv 后端**：mpv 是**独立原生网络栈，不走 OkHttp**。我们桌面侧的对策是
  `applyNetworkOptions()` 透传 `http-proxy`（`DesktopMpvPlaybackEngine.kt:407-418`）——
  但那是**代理**，不是 **ECH 逐请求改写**。ECH 怎么对 mpv 生效，**无先例**

### 3.3 超分不在 mediamp 的 feature 体系里

查 mediamp-mpv 的 `MpvPlayerFeatures.kt`，注册的 feature 只有：
`AudioLevelController` / `Buffering` / `NetworkStats` / `Screenshots` /
`VideoAspectRatio` / `TrackGroup` / `MediaMetadata`。

**没有"视频增强/超分"**。所以：

- mpv 侧：仍要走 handle 反射挂 `glsl-shaders`（本仓桌面已在这么做，可保留）
- Exo 侧：要走 media3-effect 那套（即 animeko `Anime4kQualityEffects.kt` 的形态），
  **等于换底后要重写一遍超分**

→ G3-1「超分诚实化」**不会因换底变简单**，这是之前没算进去的。

### 3.4 版本节奏

0.3.2 已经落后：maven central 上 `mediamp-*` 已发布到 **0.4.0 / 0.5.0**。
换底即意味着开始跟上游节奏；`settings.gradle.kts` 里那批 `exclusiveContent`
说明依赖面在国内镜像下本就脆弱，多 3 个 artifact = 多 3 个坑位。

## 4. 收益侧也要重新算

裁定原本给换底列的收益，现在少了两项（预览帧、字幕音轨已决策不做）：

| 收益项 | 状态 |
|---|---|
| 预览帧 | ❌ 不做（且 Android 侧现在已知可用 MMR+headers 自己做，不依赖换底） |
| 字幕/音轨 | ❌ 不做 |
| 缓冲进度真实 | ✅ 仍成立（mpv 后端有 `Buffering`） |
| 画面比例三端统一 | ⚠️ **反向**：exoplayer 后端**未实现** `VideoAspectRatio`，Android 会失去 |
| 抓帧 | ⚠️ mpv/exoplayer 有 `FramePreview`，**avkit 没有** |
| 少写几遍能力 | ✅ 成立 |

**净收益现在只剩"缓冲真实 + 少写几遍"**，而代价多了"Android 失去画面比例"。

## 5. 建议

0. **先采纳"跟随 mediamp"这个方向本身**（§0）。它是 Apache-2.0，许可上零障碍，
   且桌面已验证可行。这一步与下面所有取舍独立，可以现在就定。
1. **再做 §3.1 的 spike**（半天~一天）：确认 `mpv-android` 的 .so 能否被 mediamp native-loader 加载，
   或向 mediamp 上游问清 Android libmpv 的加载约定。这条不通，场景 C 直接出局。
2. **若 Android mpv 内核是刚需且 spike 失败 → 直接裁定不换**，把资源转投 G3-9 / G3-10。
   理由：预览帧与字幕音轨已砍，换底的收益/代价比已经不支持 L~XL 的投入。
3. **若仍要换，优先场景 B**（Android exoplayer + iOS avkit），并接受两件事：
   Android mpv 内核退役、Android 画面比例暂时没有（或只对 mpv 后端保留）。
4. **无论换不换，G3-1（超分）和 G3-10（性能）都要照做** —— 换底不解决这两个。
