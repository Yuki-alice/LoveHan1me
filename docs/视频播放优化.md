## A. 首视频加载 3–4 分钟：链路与嫌疑排名

点击 → 首帧的真实链路（shared，Android/Desktop 同构，引擎不同）：

```
点击 → VideoRouteHostScreen (导航传参)
  → 同步构造播放器引擎（组合线程）
  → VideoViewModel.getHanimeVideo() 取 watch 页（单请求串行，无预热）
  → Ksoup 全页解析出直链
  → controller.load() → 引擎 load → 首帧
```

| # | 嫌疑 | 位置 | 理由 |
|---|---|---|---|
| 1 | **无 read/call 超时** | `jvmMain/.../data/network/ServiceCreator.kt:83-91`（只有 connectTimeout=15s） | 弱网/CF 复位时靠 TCP 栈硬拖到分钟级；且"第二次秒开"正好符合"无超时+10MB 缓存"（`ServiceCreator.kt:28-31`） |
| 2 | **链路串行、无预取** | `VideoRouteHostScreen.kt:465-469` → `VideoViewModel.kt:264-317` | 首播必须等 watch 页回来才有直链；列表页本可预取 |
| 3 | **首次 DoH/代理/CF 握手** | `jvmMain/.../HanimeDns.kt:92-121`、DoH 10s+回落、`HanimeProxySelector.kt:77-94` | 首请求替全应用交学费；且桌面 SOCKS 被引擎侧弃用（`DesktopMpvPlaybackEngine.kt:374-377`），代理用户更慢 |
| 4 | **引擎同步构造 + mpv 原生初始化** | Android `ExoPlaybackEngine.kt:41-43`（组合线程直接 build）、`MpvPlaybackEngine.kt:290-309`（15 个 setOptionString + 原生库加载）；桌面 `DesktopMpvPlaybackEngine.kt:55-59,132-144`（mediamp 预热与 load 抢跑） | 新包/冷启动必走 |
| 5 | **看不见** | `PlayerTrace.kt:46-105` 起点是视频数据到货后 | **3–4 分钟花在哪一段，目前没有任何数据**，全是推测 |

### 优化方案（按顺序，先度量再动刀）

1. **补埋点（P0，先做）**：watch 请求起止、解析耗时、引擎构造耗时、load→Ready 间隔、DoH/代理/CF 分支标记。没有这一步，后面全是盲调。
2. **加超时 + 失败 fast-fail（P0）**：read/call 超时 + 重试上限。分钟级转圈变秒级报错，体验先赢一半。
3. **预取 + 并行（P1）**：列表页预取 watch 页 / 预热引擎；引擎构造挪出组合线程。
4. **首请求加速（P1）**：DoH 结果缓存、代理预检、CF clearance 复用（登录修过的那套）。
5. **验收**：埋点立基线 → 定目标（参考：二次打开秒开已成立，首次目标等基线出来再定，不拍脑袋）。

## B. 详情页布局：播放器高度与下半信息区

### 先纠偏：高度不是固定 dp，是公式

`VideoRouteHostScreen.kt:616-622`：

```
resolved = maxOf(240.dp, minOf(mainPaneWidth * 9/16, windowHeight * 0.55))
```

16:9 优先，封顶窗高 55%，保底 240dp。应用点 `VideoShellContent.kt:263-268`。
你感受到的"固定、压着下面"，实际是：**单栏下播放器置顶吸顶 + 信息区只分剩余高度**
（`VideoShellContent.kt:254`），窗矮一点下面就只剩一条缝——机制没错，体感差。

### 信息区现状

- Tab 只有简介/评论（`VideoRouteContent.kt:52-59`），`PrimaryTabRow` 固定 + `HorizontalPager` 各页独立滚动（`VideoTabsContent.kt:59-94`），页间不联动。
- 简介页 `VideoIntroductionScreen.kt:395-508`：LazyColumn 里依次 artist/标题/meta/可展开简介/actions/tags/横向选集/手工网格相关推荐；滚动位置有记忆（`VideoTabScreens.kt:67,126`）。
- 宽屏（≥840dp）双栏：播放器左、信息右（`VideoShellContent.kt:335-398`），简介内相关推荐会被隐藏转右栏。
- 细节债：简介 LazyColumn 用裸 `6/12/16/24dp`；简介/评论无宽屏限宽（`readingMax/formMax` 现成没用）。

### 优化方向

1. **播放器高度自适应**：窄屏改"吸顶→随滚折叠"（滚一下简介，播放器缩成迷你条，而不是永远占 55%）；或高度档位可切（用户手势/按钮在 16:9 与迷你间切）。
2. **信息区联动滚动**：TabRow 吸顶、简介+评论同一滚动容器（动 HorizontalPager 结构，中等改动，需保住滚动记忆）。
3. **宽屏收敛**：简介/评论套 `readingMax` 限宽 + token 替换裸 dp（小改动，先做）。
4. 影响面：`VideoRouteHostScreen.kt:616-622` 公式 + `VideoShellContent.kt:263` 应用点必改；
   `VideoViewModel.kt:72,208` 遗留高度字段顺手清；不动断点阈值与评论/选集内部。

## C. 子评论样式重设计

### 现状

- 主楼子楼**共用同一张卡**（`ui/component/VideoCommentCard.kt:67`），无独立子评论样式，
  无缩进、无嵌套、无引用块——两屏都是平铺。
- 模型是扁平的（`core/domain/model/VideoComments.kt`）：`VideoComment` 有
  `isChildComment/hasMoreReplies/replyCount`，无内嵌子列表、无分页。
- "展开更多回复"已有：卡片内按钮 → `CommentScreen.kt:360` → `VideoTabScreens.kt:304`
  取 `replyTargetIdOrNull` → 底部弹窗开 `ChildCommentScreen`（二级不再展开）。
- 网络够用：`getComments/getCommentReply/postComment/postReply/like` 全齐
  （`HanimeCommentService.kt` + `NetworkRepo.kt:394-467`），无分页参数但现状够画。
- 样式一半 token（字/色/形）一半裸值（间距全裸、头像 40dp 裸）。

### 重设计方向（配合"情感化文案与图标资产齐了再系统性设计"）

1. **层级视觉**：子评论缩进 + 左侧引用线 + "回复 @xxx" 引用头；主楼保持卡片，子楼去卡片化（列表行），一眼分出层级。
2. **收敛 token**：间距/头像尺寸进 `HanimeDefaults`（与 B-3 同一批活）。
3. **交互不动**：底部弹窗看二级回复的链路保留，只换皮——数据层零改动。
4. 影响面：`VideoCommentCard.kt` 拆分子样式 + `ChildCommentScreen.kt:238` 列表；
   不碰模型、网络、ViewModel。
