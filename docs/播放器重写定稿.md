## 一、为什么必须重写（三条根因，均有代码证据）

现状：**编译绿、单测绿、运行崩**（桌面端起播后很快闪退，详情页出现过白屏）。
所以不是"改坏了"，是**组合层的所有权设计错了**。三条互相叠加的根因：

### 根因 1：播放器实例由 Composable 拥有，却被跨分支"搬运"

`VideoRouteHostScreen.kt:148`：

```kotlin
val playbackEngine: PlaybackEngine = remember(route.videoCode, route.localUri, kernel) {
    createPlaybackEngine(kernel = kernel)...
}
```

实例挂在组合上。而 `VideoShellContent.kt:173` 又用 `movableContentOf` 把这棵子树在三个**互斥布局分支**
（`:301` 经典双栏 / `:343` 右栏 Tab / `:368` 单栏）之间搬来搬去，且每个分支传**不同的 modifier**
（`weight(1f).fillMaxHeight()` vs `fillMaxSize()`）。

→ 搬运 = 渲染面 detach / re-attach，同时尺寸变化。mpv 的原生渲染线程仍在向旧 Skia layer 输出
→ **崩溃**。这正是 `播放器重构方案.md` 记下的 animeko 纪律「**播放器不动**」
（`reference/animeko/.../AdaptivePlayerScreenLayout.kt:146` 用 movable 的前提是
**player 实例在 ViewModel 里**，`EpisodeViewModel.kt:296-302`，与组合解耦）。

### 根因 2：桌面渲染面自己就是个结构性地雷

`PlatformVideoSurface.desktop.kt:39-57`：

```kotlin
var readyPlayer by remember(mpvEngine) { mutableStateOf<MpvMediampPlayer?>(null) }
LaunchedEffect(mpvEngine) { readyPlayer = mpvEngine?.awaitPlayer() }
val player = readyPlayer
if (window != null && mpvEngine != null && player != null) {
    MpvMediampPlayerSurfaceProvider().Surface(player, modifier)   // ← 每帧 new 一个 provider
} else {
    Box(modifier.background(Color.Black))                          // ← 分支切换
}
```

两个问题：
- **异步就绪导致结构性分支切换**（黑盒 ↔ Skia 面）。`player` 从 null 变非空时整个子树被销毁重建，
  而 mpv 可能**已经在渲染**。叠加根因 1 的搬运，就是崩溃的完美配方。
- `MpvMediampPlayerSurfaceProvider()` 在组合体里**每次重组都新建**。核过 jar（mediamp 0.3.2）：
  该类只持一个 `forClass` 字段、未覆写 `equals`，`Surface` 是它的 `@Composable` 成员函数 →
  接收者每帧都"变了"，`Surface` body 反复重跑。

### 根因 3：非法起播 gate —— 本地片整条链路被掐断（当前 stash 里那层引入的回归）

```kotlin
// VideoPlaybackCoordinator.resolveStart()
if (!isCurrent(generation, videoCode) || videoCode == LOCAL_VIDEO_CODE) return null
// VideoRouteHostScreen.kt:526 调用方
val decision = coordinator.resolveStart(gen, route.videoCode, policy)
if (decision == null) return@collect        // ← 本地片在这里被丢弃
```

这块 `else` 分支是**唯一**构造 `PendingPlayback` 并调 `load` 的地方，`LOCAL_VIDEO_CODE = "-1"`
正是本地/下载片的码（`VideoViewModel.kt:265,316-317`）。旧实现里 `"-1"` 只在 `persistPlaybackProgress`
早退，**不影响起播**。→ 本地片永远走不到 `load`。

> 注：这条是 `git stash@{0}` 那层未提交重构引入的，重写时天然消失；记录下来是为了
> **不要再犯同一类错**：把"该不该写历史"的判据误用成"该不该起播"的闸门。

## 一·五、决定性事实：与 animeko 是**同库同版本**

这条改变了整个方案的可行性评估 —— 不是"技术栈相近可以借鉴"，而是**可以直接照抄用法**：

| | animeko | 本项目 |
|---|---|---|
| 播放抽象层 | `org.openani.mediamp:*` | 同 |
| 版本 | `0.3.2`（`gradle/libs.versions.toml:93`） | `0.3.2`（`gradle/libs.versions.toml:62`） |
| 桌面内核 | `mediamp-mpv` → `MpvMediampPlayerSurface` | 同库，但用成了 `MpvMediampPlayerSurfaceProvider().Surface(...)` |
| Android 内核 | `mediamp-exoplayer` | `mediamp` 走 Exo 内核 |
| iOS 内核 | `mediamp-avkit` | 自研 `IosAVPlaybackEngine`（AVPlayer/AVPlayerLayer，同构） |

`org.openani.mediamp` 即 animeko 官方出品。所以 **animeko 的 `video-player` 模块就是 mediamp 的正统用法示范** ——
照抄它的结构 = 照抄这个库「被设计成该怎么用」。

### ⚠️ 但必须「抄纪律，不只抄形状」

animeko **确实用了 `movableContentOf`**（`ui-episode/.../AdaptivePlayerScreenLayout.kt:146`）。
它能这么用，是因为**播放器实例在 ViewModel 里**（`ui-subject/.../EpisodeViewModel.kt:296-302`），组合层只是投影。

它的写法是"一份内容 + 多个**互斥**分支，每分支调用一次"：

```kotlin
val movablePlayer = movableContentOf { ... player(...) ... }   // :146 只创建一次
when (layoutParamsState.value.mode) {
    Mode.COMPACT -> movablePlayer()                    // :178  ├─ 互斥
    Mode.HORIZONTAL, Mode.THEATER -> movablePlayer()   //       ┘─ 同一时刻只有一个活跃
}
```

我们若只抄「movable 这个形状」而不搬「实例所有权」，会**再崩一次**。
→ 顺序被锁死：**先上提实例（S4），才有资格讨论 movable**。

## 二、参考项目分工（谁管什么，不许越界）

| 层 | 权威来源 | 理由 |
|---|---|---|
| **渲染面接口形态** | **animeko** | 同库同版本，`VideoPlayer` 是 `expect fun(player: MediampPlayer, modifier: Modifier)` |
| **播放器脚手架分层** | **animeko** | `VideoScaffold` 的 video 单一调用点 + 覆盖层全 `matchParentSize` + 全屏只改约束 |
| **控制器/手势状态所有权** | **animeko** | `PlayerControllerState` 等均为 commonMain `@Stable class` + `rememberXxxState()` |
| **全屏语义** | **animeko** | `maintainAspectRatio = !expanded`：只改尺寸，不改结构 |
| **数据源解析** | **Han1meViewer** | animeko 是 BT 磁力聚合，我们是「在线直链解析 + 本地文件 + 下载」，形态完全不同 |
| **起播链路 / 续播决议 / 自动播放闸门** | **Han1meViewer** | 直系来源，业务语义权威 |
| **三内核选择策略** | **Han1meViewer** | 本地文件 vs 在线直链走哪个内核，它有现成判据 |
| **失败与重试语义** | **Han1meViewer** | 「失败即停」，无同 URL 静默重试 |
| **本地/下载片播放** | **自己写** | 两边都无对应形态（`LOCAL_VIDEO_CODE`） |
| **`PlaybackEngine` 接口** | **自己写（资产）** | 已对齐 Han1meViewer，全程只读 |

## 二·五、目标架构

原则一句话：**引擎与渲染面由长生命周期对象拥有并固定挂载；组合层只做投影，不拥有、不搬运播放资源。**

| 关注点 | 现在（错） | 重写后（对齐 animeko） |
|---|---|---|
| 引擎实例所有权 | Composable `remember(videoCode…)` | **画面级 Controller（`remember` 一次、key 只含 videoCode）**，且**不参与任何布局分支** |
| 渲染面挂载点 | 在 `movableContentOf` 里被搬运 | **固定挂载在稳定的单一点**，尺寸变化只改 modifier，**绝不换分支、绝不搬运** |
| 分支切换 | 黑盒 ↔ Skia 面（异步就绪触发） | **永远只走一条路径**：面常驻，未就绪时面内画 poster（不换分支） |
| 布局自适应 | 播放器子树被搬到不同分支 | **播放器子树在布局树里位置固定**；自适应只影响播放器**外部**的兄弟节点 |
| 失败语义 | 失败即停（已对） | 保留；重试保留位置 |
| 进度落盘 | 15s 心跳（已对） | 保留（animeko 为 1 分钟心跳 + 事件驱动，语义一致） |

### 三条硬纪律（违反任一条即为回归）

1. **播放器不动**：不 `movableContentOf`，不用共享元素过渡，全屏只改 modifier，
   绝不因布局分支/异步就绪改变播放器所在的组合结构。
2. **失败即停**：异常 → `Error` 态 + `stopPlayback`，无"同 URL 静默自动重试"（手动重试保留）。
3. **一个闸门只判一件事**：起播闸门只判"能不能播"（网络/引擎/源可用），
   绝不掺"要不要记历史""是不是本地片"这类旁支判据。

## 五、红线

- **不许再动引擎层接口**：`PlaybackEngine` / `ComposePlaybackController` 是资产，S1–S5 全程只读。
- **每一步都必须能单独回退**：按步提交，提交信息写清做了什么。
- **不许把 `movableContentOf` 用于播放器**：animeko 能用是因为实例在 VM；我们实例在组合层，
  要用就得先把实例上提（S4 之后才有资格讨论）。
- **三端编译口径**：`./gradlew :shared:compileKotlinDesktop :shared:compileAndroidMain :shared:compileKotlinIosSimulatorArm64`；
  改了 `:app` 或平台壳槽位必须加跑 `:app:compileDebugKotlin`（`:shared:compileAndroidMain` **不包含** `:app`）。
