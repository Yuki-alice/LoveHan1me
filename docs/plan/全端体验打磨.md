## C1b｜iOS 全屏（已落地，待真机）

> 对标结论（2026-10-04 研读 `reference/animeko`）：animeko 用**手动全屏**，
> 不是 `AVPlayerViewController`——`isUndecoratedFullscreen` 布局态（见
> `reference/animeko/app/shared/ui-foundation/src/commonMain/kotlin/ui/foundation/layout/Fullscreen.kt:31`），
> iOS 落点是自有 hosting VC 的 `statusBarHidden` 开关 + Swift 方向桥 + 转屏触发
> （见 `reference/animeko/app/shared/ui-foundation/src/iosMain/kotlin/ui/foundation/layout/Fullscreen.ios.kt:22`，
> 其中 `attemptRotationToDeviceOrientation` 已 deprecated，有 TODO 待换新 API；
> 方向桥 Swift 实现见 `reference/animeko/app/ios/Animeko/ContentView.swift:80`：
> iOS 16+ 走 `requestGeometryUpdate`，失败/低版本回退 UIDevice KVC hack。
> 但我们**不用照抄它的 VC 子类**：本仓 iOS 壳是 SwiftUI（`ContentView`
> 已 `ignoresSafeArea(.all)`），有 SwiftUI 原生三件套——`.statusBarHidden()`
> 修饰符 + `.persistentSystemOverlays(.hidden)`（iOS 16+ 管 Home 指示条）+
> 同一个 Swift 方向桥。Kotlin→Swift 用既有桥模式（`EchGatePortReporter` /
> `NetworkChangeBridge` 同款：Kotlin reporter 对象 + Swift 侧订阅）。
> 另附赠：`UIDeviceOrientation` 在 KN 里要类名限定
> （见 `reference/animeko/app/shared/ui-foundation/src/iosMain/kotlin/platform/PlatformWindow.ios.kt:59`，
> 直接 import 条目解析不到——我们 C4 踩的正是这个坑，现已绕开）。
> animeko AGPLv3，与本仓同许可族；照搬代码段按 `NOTICE` 既有 animeko 条目合规即可。

- 现状：`supportsFullscreen()` 显式 false（见
  `shared/src/iosMain/kotlin/lovehan1me/feature/player/IosVideoPageHost.kt:98`），
  UI 已隐藏入口，不撒谎。
- 方案 B1（推荐，animeko 手动路线 + SwiftUI 化）：Kotlin 侧 `applyFullscreen` 真实现 →
  reporter 桥 → Swift 侧改状态栏/指示条/方向（requestGeometryUpdate 为主，
  KVC hack 为兜底）；布局复用现有 `isFullscreen` 态 + PiP 层不动。中改，设计不断。
- 落地记录：`IosFullscreenBridge`（通知桥）+ `applyFullscreen` 真实现 +
  `supportsFullscreen` 翻 true（C4 门控同步激活）；Swift 侧状态栏/指示条
  （iOS 16+ 分支）/方向三件套；Kotlin 与 Swift 双编译通过。
  待真机：刘海/手势/指示条体感 + 横竖切换 UX（模拟器只能验编译与旋转布局）。
- 方案 B2（轻量，折价）：不 subclass、不转设备方向，只做横屏铺满布局。
  状态栏留着，算"伪全屏"——诚实度打折，除非你接受。
- 方案 A（原生控制器）：`AVPlayerViewController` 全套原生体验；代价是播放归属
  搬家（`IosPipPlayerHolder` 的 AVPlayer 可用）+ dismiss/转屏/现有 PiP 层重理 +
  控制条风格脱离自家设计。改动最大。
- 待决策：UX 取向（原生手感 vs 自家设计）、Swift 侧工作量接受度、真机排期。
  定了才动工；模拟器只能验编译与旋转布局，真机确认刘海/手势。

## C2｜后台下载

- 落地 C2a（2026-10-04 审计 + 一处 parity 修复）：三端续传语义逐行比对——
  Range 续传 + 取消进 Paused + 进度落库 + 失败带字节一致；挖出唯一分叉并修掉：
  服务器无视 Range 回 200 全量时桌面/iOS 截断重写自愈，Android 直接判失败
  （且重试撞同一面墙，永久失败），现与前两者同语义（清响应后 continue，
  下一轮走全量分支）。Android 侧只走编译门，真机下载回归待补。
- 唯一保留分叉是**重试自动化**，定为刻意行为差异，不予对齐：
  Android 流内 ×3 + Work ×3 自动重试（移动网络常断 + WorkManager 约束廉价）；
  桌面/iOS 中途失败即 Failed、手动一点即从断点续传（进度与字节都在库里，
  无丢失无损坏）。给桌面/iOS 加自动重试是新功能不是修复，不在本期。
- C2b **冻结**（2026-10-04 决策）：核查发现"桌面重启恢复"已存在
  （`initialize()` 重拉未完成任务续跑），C2b 实为"iOS 后台下载"单项——
  Background session 重写传输栈 + 生命周期钩子，2–4 天量级，且挂起后网关同死、
  后台只能直连/代理，受限网下收益打折。当前前台下载 + 断点续传已覆盖 95% 场景，
  待 iOS 用户明确要"锁屏下完"再立项；立项前先跑完 R 项受限网验收
  （后台在两种网络下是两种行为，矩阵翻倍）。

## Phase 1 收口（2026-10-06，R0 真机周之外并行）

决策（用户已拍板）：三条红线维持（崩溃只做本地诊断增强）、账号同步后议、

- **F12 正名（零行为变更）**：回到调用图核对，原判"iOS PiP 控制条假动作"
  不成立 —— `togglePlayPause` / `onPipModeChanged` 在三端宿主上都是**零调用方**
  的死方法（Android 走 MainActivity→共享包装器，iOS 走 delegate→PipModeReporter

  Android 补同款注释，桌面早已有。真机仍需验"PiP 键按了走不走、状态同不同步"
  （引擎外部 rate 观察），列入 R0。
- **P1-2 下载限速移除（用户决策，替代原"接通"方案）**：经讨论限速只对
  移动数据后台下载有窄场景价值，投入产出比不如下载调度本身 —— 整体移除：
  删除 `SpeedLimitInterceptor` / `SpeedLimitResponseBody`（含 Android

  文案（`:app` 三处历史残留一并清）、`toDownloadSpeedPrettyString`。
  存量迁移：老设备 DataStore 里残留的键不再读取、无害忽略；旧备份同理。
  决策登记见 `docs/decisions.md`（下载限速移除一节）。
- **下载调度优化（与移除同批）**：三端对齐就剩一处 —— 桌面下载自建链用
  `EchGateInterceptor()` 默认 Api 档（预算/熔断错档），Android（`downloadClient`）

  `defaultPurpose = Download`。分段并行下载另议（需逐 CDN 验 Range，大改动）。

  `Semaphore` 无法扩容且 `release` 禁止凭空放行（凭空放行抛
  `IllegalStateException`，测试实锤）—— 改通道许可池（扩容塞、缩容后台取，
  在飞任务收发配对，稳态 `空闲+在飞==上限`）。守卫 `DesktopDownloadLimitTest`

  选择器，选完即满足导入前置。复用既有文案，未新增字符串。
