## B2-D｜发现页（已落地 2026-10-05，与 B2 同批）

- D1 默认浏览 stale 缓存（E2 同款机制，`discover_` 前缀隔离）：
  每次进 tab 不再白等整轮网络，先展上次第一页再后台刷新。
  - 只缓存"无条件浏览"（page=1 + 无词无筛选无 broad）：key 本来就不含筛选参数，
    有条件的请求天然 miss，不会串结果；
  - 写路径：`pageIOFlow` 加可选 `onBody`（E2 同款，默认 null，其余调用点零影响），
    `getHanimeSearchResult(writeCache)` 透传；
  - 读路径：`SearchViewModel` 先读缓存 `Parser::hanimeSearch` 首展，
    新鲜第一页到达时**替换**（不是追加，去重保首项，追加会把旧快照顶前面）；
  - 已看标记内联逻辑抽 `withWatched()`，缓存首展与网络刷新共用；
  - 下拉刷新同样受益（先展旧页再覆盖）。
- D2 网格 `contentType = { it.itemType }`（normal/simplified 双构型混排不断言）。
- D3 新页预热：`takeLast(12)` 只热新到页（已热过的不重做，无 churn），磁盘-only。
- 刻意不做：列表截断（B3 独立项，语义变更另议）；筛选面板/历史建议（DB 防抖已有，无实测热点不动）。
- 验证：三端编译过；一次性 live 测试实证全链路（真页抓取→写透→读回→重解析，
  videoCode 序列完全一致，通过后已删）；全量 496 中唯一失败是 `EchGateLiveTest.javchu`
  —— 干净树同失败（预存环境问题，调度器/网关，非本次回归）。
  ViewModel 替换语义为 review 验证（headless 无网关 sidecar，走 appraisal；
  hook 形状与已上线的 E2 完全同构）。

## B5｜播放页高频重组隔离（已落地 2026-10-05）

- **先纠一处计划误判（回到代码核对的结果）**：原文说 `DanmakuLayer.kt:76` 的
  `frameNanos` 每 vsync 写 state "等于每帧重组" —— 实测不成立。它只在 `Canvas`
  的绘制 lambda 里被读，属绘制期读，写它只失效绘制、不进组合；同目录
  `DanmakuLayerSteadyTest` 两条用例（空屏 / 有弹幕各连渲 30 帧、父树组合恰好 1 次）
  钉的正是这条，本期实跑 **2/2 绿**。故本期**未动**弹幕层，去追真正在重组的那个源。
- **真源**：`MediampPlaybackEngineBase.kt:99` 把 `currentPositionMillis` 也合进状态流，
  于是每个推送周期都 `publish()` 一份新的 `PlaybackEngineState`（位置+缓冲在内）
  → `PlaybackController` 随之写出新的 `PlaybackSessionState`
  → 而播放页是"整页读一个状态对象、逐层往下传"（`VideoRouteHostScreen` 起，经
  `VideoShellContent` 到 `VideoPlayerShell`）：**一次位置推进 = 整棵播放页组合树重算**，
  频率即推送频率（代码自记：Android 250ms / iOS 500ms / 桌面事件驱动）。
  另一处同源浪费：`rememberDanmakuSession` 的 `LaunchedEffect(playbackState)` 以同一个
  每 tick 都换体的对象为 key，等于每 tick 取消重建一次协程。
- 改动（只动组合期读取路径，行为零变更）：
  1. 新增 **`PlaybackUiState` 投影**（`PlaybackController.kt`）：剔除每 tick 变的
     `positionMs` / `bufferedPositionMs`；字段只收组合期真有消费点的那批
     （`title`/`artworkUri` 是开流参数、组合期无读者，未收）。照 B4 既有
     `themeConfigFlow` 模式：`state.map{ toUiState() }.distinctUntilChanged().stateIn(Eagerly)`。
  2. `VideoRouteHostScreen` 改订 `uiState`；`VideoShellContent` / `VideoPlayerShell`
     参数类型改 `PlaybackUiState`（读点仍是那几个相位/布尔/画质）。
  3. 位置退到命令式读：录 GIF 的起点改
     `playbackController.state.value.engine.positionMs`（点开对话框那一刻取，不该驱动组合）。
  4. `rememberDanmakuSession` 改收 `StateFlow`，在 `LaunchedEffect(session, flow)` 里
     `collect` —— key 稳态，位置快照照送（弹幕时钟依赖它）。
- 刻意不做（附理由）：`MediaProgressSlider` 的 `Slider(value = state.displayPositionRatio)`
  是 Material3 要求组合期取值的读法，属"该在组合期读"那一类，按 skill 明令不动；
  播放页内层不再拆更细的投影（进度条另有 mediamp 直读通道，没有第二个消费者）。
- 验收（计数器为准，两条腿各管一半）：
  - 新增 `PlaybackUiStateTest`（3 例，`shared/src/desktopTest`）：①流级——5 次位置/缓冲
    推进，`uiState` 发射 **0** 次；②正向对照——相位变化必须发射；③组合级——
    `ImageComposeScene` 里 5 次位置推进后，读 `uiState` 的那一层重组 **0** 次
    （用例内自带正向对照，防"零重组"其实是"用例自己没跑起来"）。
  - **反向验证**：把 `positionMs` 加回投影 → ②仍绿、①③转红
    （①报"发射 5 次"、③报"重组 1 次，headless 下 StateFlow 会合并同帧内的多次发射"）；
    撤掉改动后 3/3 复绿。
  - 全量：`:shared:desktopTest` **503 用例 / 0 失败 / 0 skip**（B4 时 500，+3 即本用例；
    取数那次是 `cleanDesktopTest + --no-build-cache` 的强制实跑，不是缓存回放）；
    desktop / androidMain / iosSimulatorArm64 三端编译 + `:app:compileDebugKotlin`
    + `:desktopApp:compileKotlin` 全绿。
  - 用例自身的抖动与修法：③ 起初把"状态投递落到哪一帧"写成固定 3 帧预算，全量并行跑时
    正向对照假红过一次。改成"静置到连续三帧计数不变 + 观测给足 30 帧窗口"后连跑 3 次全绿。
    **headless 组合计数用例不写死帧数**（同 `DanmakuFrameBaselineTest` 不断言时间的道理）。
  - 期间另见一次 `EchGateLiveTest.不经网关直连站点必然失败`（`NoRouteException`）在
    `--rerun-tasks` 的全量并行跑里翻红；单跑该文件 **4/4 绿**、随后全量亦绿 ——
    记为既存环境抖动，与本改动无关（本改动不触网络路径）。
- 未做/待验：真机（Android）Layout Inspector 的重组计数与帧时间 —— headless 计数器只证
  "组合次数"，不证"帧时间"；本期也没跑 `:desktopApp:run` 目视（改动不涉布局与绘制路径）。

## B7｜备份流式化

- 现状：`BackupManager.kt:32` 的 `prettyPrint = true` + 先全拉 List
  再 `encodeToString` 一个大 String（见 `:75`），导入 `readUtf8` 全读
  再 decode（见 `:84`）。万级记录即数十 MB 峰值抖动。
- 改动：`prettyPrint = false`，`encodeToSink/decodeFromSource`
  或分表流写，`getAll()` 改分块 `LIMIT/OFFSET`。
- 验收：10MB 备份导出峰值内存降至 O(chunk)（profiler 为准）。
