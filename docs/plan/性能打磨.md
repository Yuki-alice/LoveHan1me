## B6｜图片定尺寸与稳定缓存键

- **先纠原稿前提（回到代码核对的结果）**：原稿说"`ImageRequest` 无 `size()`，
  解码按原图尺寸" —— **对 coil3 不成立**。AsyncImage 走 `ConstraintsSizeResolver`
  从布局约束解析解码尺寸；项目自己的预热路径也写着"解码尺寸由展示侧定，预热定死
  尺寸反而污染内存缓存"。在这里写死 `size()` 只会把不同宽度的卡片塞进同一个缓存键。
  **故未加 `size()`**。
- **原稿另一半已失效**："`RetryableImage` 重试拼 `?retry=` 换 URL" 已随 **B2-3** 先一步
  落地（同 URL 重发 + `networkCachePolicy(DISABLED)` 显式 bypass 磁盘），本项不再包含。
- **真正的病根（原稿没写，本期找到）**：`ImageRequest` 原先直接 new 在组合体里，
  于是**每次重组都是一个新实例**。AsyncImage 以 model 作为"要不要重启这次加载"的
  依据，实例一换就把加载从头再来 —— 表现就是卡片一重组就闪回占位图。快滑时一屏
  几十张卡在反复重组，图闪正是这么来的（而 B6 的验收口径恰恰就是"快滑图闪"）。
- 改动：`RetryableImage` 里改 `remember(context, model, retryCount) { ...build() }`。
  只有 URL 真变或重试推进才重建请求。记忆住的请求本身就是稳定缓存键的来源
  （data + 解析出的尺寸 + 变换），不必再手工指定 `memoryCacheKey`。
- 刻意不做：写死 `size()`（理由见上）；网格可见区预取 —— **B2 / B2-D 已落地**
  （首页 `HomePageContent`、搜索 `SearchResultsGrid`、预览 `PreviewScreen` 都有
  `ImageLoader.enqueue` 预热），不重复做。
- 未测：图闪"减半"是主观口径，需要真机录像前后比对，headless 断言不了，
  **如实记为未测**。

## B7｜备份流式化（已落地 2026-10-06）

- 原状：三处 `Json { prettyPrint = true }` + 先全拉 List 再 `encodeToString` 攒出
  整份 JSON 字符串，导入 `readUtf8()` 全读再 decode。万级记录即数十 MB 峰值抖动。
  （`LocalListRepository` / `OnlineListsBackup` 两处是 2026-10-06 复核时补的，
  原稿只列了 `BackupManager`。）
- 落地：
  1. 新增依赖 `kotlinx-serialization-json-okio`（与 `serialization = 1.11.0` 同源）。
     ⚠️ **1.11.0 的函数名是 `encodeToBufferedSink` / `decodeFromBufferedSource`**
     （收 `BufferedSink` / `BufferedSource`），不是 `encodeToSink` / `decodeFromSource`。
     写错名字的表现是"依赖解析成功、但符号找不到"，排查时别被"依赖下下来了"骗过去。
  2. `BackupManager.exportTo` / `importFrom` 改流式：不再 `encodeToString` 攒整份
     字符串再 `writeUtf8`，也不再 `readUtf8()` 全读再解析。万级记录下那个字符串是
     峰值内存的大头（UTF-16 驻留，约为落盘字节的两倍，且与实体列表同时在堆上）。
  3. 三处 `prettyPrint` 全改 `false`。
- 刻意不做：DB 侧分块 `LIMIT/OFFSET`。实体列表仍会在内存里常驻一次，
  峰值从 **O(整份 JSON 字符串)** 降到 **O(实体列表)**，**并非 O(chunk)**。
  分块要动 DAO，且导入侧拿到的就是整份 `BackupData` 对象，分块读也省不掉 ——
  收益与改动量不匹配，另立小项。
  另：`LocalListRepository.exportLocalLists()` 在播放列表循环里逐表 `dao.getItems()`
  是 N+1 查询，与本题相邻但不相同，一并记录待议。
- 验收：`BackupStreamTest` **3 例** —— ①流式往返等价（换通道最怕换出个坏通道）
  ②`prettyPrint` 真的关了 ③**旧版缩进过的备份仍能读进来**（存量用户红线，
  不是性能项）。全量 `:shared:desktopTest` **510 / 0**（+3 即本用例）。
  峰值内存本身要 profiler 量，headless 断言不了，**如实记为未测**。
- 跟进 B7-N1（2026-10-06）：`exportLocalLists()` 的 N+1 收口 —— 原先
  `getPlaylistsOnce` 1 次 + 逐表 `getItems`（P 个播放列表共 P+3 次查询）。
  新增 `LocalListDao.getAllItems()`（全表 `ORDER BY addedAt DESC` 一次拿全），
  组装抽纯函数 `assembleListsExport`（`groupBy` 保遭遇顺序，每组仍 DESC，
  与逐表查序列一致；未知桶丢弃，旧实现根本不会去查它们）。
  查询数 P+3 → 2。守卫 `LocalListsExportAssemblyTest` **4 例**：
  交错分组保序 / 空表+未知桶 / 与逐表拼装逐字段等价（200 条正向对照，
  改排序即红）/ 空输入。`:shared:desktopTest` **514 / 0**（+4 即本用例）；
  desktop / iosSimulatorArm64 / androidMain 全绿（DAO 改动走 Room KSP，
  三端注解处理均过）。DB 分块 `LIMIT/OFFSET` 仍另立小项（理由同上）。
