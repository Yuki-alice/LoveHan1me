## 1. 阻断级（P0）：三处挡在"三端都能用"前面

### F1｜iOS 播放链路完全不过网关，也不给代理，UA 是空串

`shared/src/iosMain/kotlin/lovehan1me/data/network/PlayerWiring.ios.kt:9-13`：


> 注：`EchGateBootstrap.swift` 确实在 iOS 起了网关，Ktor 浏览链路也确实走了

## 2. 严重（P1）：调度器的"路由"在执行层是空转

### F4｜UserProxy / SystemProxy / Direct 三者在执行器里物理等价

JVM 侧 `EchGateInterceptor.kt:114-144`：三个 RouteId 共用同一个分支，
都只是 `chain.proceed(request)`。真实出口由 **client 级** `HanimeProxySelector`
（`ServiceCreator.kt:158/134/116`）在连接时按设置决定，与调度快照无关。

Darwin 侧 `EchGatePlugin.kt:131-158` 同理：都是 `restoreOriginal` 后 `proceed(request)`，
出口由 NSURLSession 决定；**手填代理根本不会生效**（`ProxyCapability.ios` 已知缺口）。

于是：

- 设置是 HTTP 代理时，计划里的 `Direct` 步实际走的是代理 → **成功记到 Direct 头上**；
- 设置是直连时，计划里的 `UserProxy` 步实际是直连 → 成功记到 UserProxy 头上；
- iOS 上手填代理的用户：`UserProxy` 连续 3 次"成功"（其实是直连）→
  `RouteHealth.LOCK_SUCCESS_THRESHOLD` 锁定 → **网关被挤出首位**。

这正踩 `POSITIONING.md` 的红线："UI 上显示的每个字段，都得能回答'这是引擎的真值，
还是我们替它编的'"。现在的路由字段是编的。

### F5｜非网关步失败直接抛，计划里后续步是死步

`EchGateInterceptor.kt:116-131`：

```kotlin
val via = try { chain.proceed(request) }
          catch (e: IOException) { ...; throw e }   // ← 不让位，直接抛
...
return finishGateResponse(via, ...)                  // ← 成功就返回
```

非网关步要么 return、要么 throw，**永远不会走到 `plan.attempts` 的下一步**。
同理 `EchGatePlugin.kt:134-157`。

后果："多步让位 / attempts 全部耗尽才 NoRoute"这个语义**只在网关步之间成立**
（网关 502 重试一次 + 让位一次）。任何排在非网关步之后的路由都是死代码。
`EgressScheduler.kt:58` 那行 `if (!domain.isRestricted || !state.gate.enabled) add(RouteId.Direct)`
在有代理时排在 `UserProxy` 之后 —— 那个 Direct 永远不会被尝试。

### F6｜"purpose × route 预算表"其实只有 purpose 一维

`SchedulerModels.kt:83-92`：

```kotlin
fun budgetFor(purpose: EgressPurpose, route: RouteId): Long = when (purpose) { ... }
```

`route` 参数**从未被使用**。计划里画的二维预算表（Api 60s / Image 30s / Video·Download
UNLIMITED / Probe 10s）实际只有一维。这不是 bug，是"文档描述了一个不存在的维度"。

而且预算只在 502 重试门控处真正执行（`EchGateInterceptor.kt:222-227`、
`EchGatePlugin.kt:226-231`），其余场景"socket 级硬上限仍是各 client 超时"。
KDoc 承认了，但对 Api 档来说，所谓"单步预算 60s"和 client 的 callTimeout 60s 完全重合——
**预算机制目前唯一的实际作用是防止第二次网关重试**。

### F7｜`RouteRegistry.update` 是 volatile map 的读-改-写，无 CAS

`RouteRegistry.kt:21-23`：

```kotlin
fun update(domain: DomainClass, transform: (RouteHealth) -> RouteHealth) {
    snapshot = snapshot + (domain to transform(healthOf(domain)))
}
```

并发上报（图片链几十个请求同时到达）会丢更新。作者的注释说"丢一次上报不影响结论"——
对"成功率排序"成立，对**熔断计数**不成立：少算一次就可能让本该在第 3 次熔断的路由
拖到第 4 次，而冷却是 5 分钟（`RouteHealth.kt:107`），代价不是"少一次上报"而是"多 5 分钟坏路由"。

## 3. 中等（P2）：播放链路三端三种行为，且都没有出口健康数据

### F8｜Android 播放没有回退，桌面有一次，iOS 没有网关

| 端 | 网关改写 | 网关失败后 | 显式代理 |
|---|---|---|---|
| Android | `EchGateDataSource.kt:32` 有 | **无回退**，直接失败 | 靠 JVM 系统属性，代码自己写"是否被 Exo 尊重**未实测**"（`PlayerWiring.android.kt:30`） |
| 桌面 | 有 | `DesktopMpvPlaybackEngine.kt:136-145` 回退直连一次 | `proxyUrlFor` 真分派（SOCKS→null→隧道） |
| iOS | **无**（F1） | 无 | 无 |

同一份 `ScheduledPlan`，三端执行出来是三种行为。这正是调度器计划想消灭的东西，
它在 HTTP 层消灭了，在播放层没有。

### F9｜播放 outcomes 不上报，视频域健康是"推断"出来的

`docs/plan/网络连接调度器.md:257-258` 承认"播放器 outcomes 不上报（引擎无钩子）"，
补救是"图床流量已喂 CdnMedia 域健康……视频 outcomes 缺席不影响熔断（同域图片先熔）"。

这个补救有个漏洞：**视频 CDN 和图床往往不是同一个域**。计划书里自己写过
`vdownload.hembed.com → *.rsc.cdn77.org`（`PlayerWiring.desktop.kt:31-33`），
而封面图床是另一个 host。当视频 CDN 单独被封时，没有任何数据会流进它的 RouteHealth，
它**永远不会熔断**。这就是 `POSITIONING.md` 说的"编的"。

### F10｜桌面无换网监听 × 5 分钟冷却 = 换到好网还要等 5 分钟

`NetworkSettingsRoute.kt:425` 只有在用户手动拨网关开关时才 `RouteRegistry.reset()`。
桌面没有换网监听（计划 7.6 已列为已知缺口）。配合 `COOLDOWN_MS = 5 分钟`，
用户换到一个好网络后要干等 5 分钟，或者手动开关一次——而"手动开关复位"这件事
只有读过源码的人知道。

## 6. 改进意见（按性价比排序）

### A. 【最高性价比】把"计划里的路由"收敛成"执行器真能执行的路由"

调度器的 4 个 RouteId 里，只有 `Gate` 是真能执行的。与其维持一个执行不了的抽象，
不如**折叠**：

- 新增 `RouteId.Default`，含义是"客户端当前出口（代理/直连由设置决定，本层不区分）"；
- `UserProxy` / `SystemProxy` / `Direct` 三者在 JVM 与 Darwin 上全部折叠为 `Default`；
- 计划变成最多两步：`[Gate, Default]`；
- 诊断事件里 `Default` 显示成"当前网络出口"，不再谎称"直连"。

代价：择优维度从 4 降到 2，EWMA/成功率排序几乎失去意义（只剩 Gate vs Default）。
**这是应该接受的代价**——两个真维度好过四个假维度。
`RouteHealth` 的排序代码可以留着（将来有真执行器时直接启用），但不再参与当前排表。

这一步同时修掉 F4（记账失真）、F5（死步，因为只剩一步非网关步）、
D4（iOS 不再排执行不了的 UserProxy）。

### B. 【必须】让多步让位真的跑起来

折叠之后仍然要修 `EchGateInterceptor.kt:116-131` / `EchGatePlugin.kt:134-157` 的
"非网关步失败直接抛"：改成 `continue` 到下一步，非幂等方法禁止让位（现已有
`isIdempotent` 判定，沿用）。并补一条 e2e：

```
Gate 抛 IOException + Default 成功 → 期望 chain.seen.size == 2，返回 200
Gate 成功                          → 期望 chain.seen.size == 1
Gate 失败 + Default 失败           → 期望 NoRouteException
```

现有 `EchGateInterceptorTest` 13 条用例**没有一条**覆盖"非网关步失败后的行为"，
只有 `网关异常且无代理时诚实失败`（:315）这类"表空"场景。这是覆盖缺口，不是口味问题。

### C. 【P0，排期】iOS 播放分两步走，先止血

第一步（1 天，立刻可做）：
1. `PlayerWiring.ios.kt:10` 的 `userAgent` 从 `""` 改成与 Android 一致的 `USER_AGENT`；
2. `proxyUrlFor` 至少返回一个可用的系统代理出口（或明确返回 null 并在 UI 上标注）；
3. **给一次失败重排**：AVPlayer 加载失败时用 `EgressScheduler.plan` 重排一次出口再试。

第二步（3–5 天，评估后立项）：`AVAssetResourceLoaderDelegate` 原生改写，让 iOS 播放真正进网关。
在这之前，UI 上必须**明说**"iOS 播放暂不经网关"，不能让用户自己撞。

### D. 【P0，半天】iOS 网络设置页去占位化

把 `NetworkSettingsRoute.kt` 里与平台无关的骨架（三态计算、事件列表、导出、强制选路对话框）
提到 commonMain，iOS 只实现"网关开关 + 状态行 + 三态 + 诊断 + 强制"这五项的 actual。
顺带删掉 `PlatformSettingsRoutes.ios.kt:23-30` 两行硬编码英文，改走 `strings.xml`。

最低限度：如果"iOS 没有自定义 DNS/代理"确实是真的，就**只暴露网关与诊断**，
不要写"not available on iOS"这种整体否定的假话。

### E. 【关键】不要等换网，本机造受限形态

受限形态的三件事里，至少两件本机可造：

| 形态 | 本机造法 | 覆盖 |
|---|---|---|
| 网关出口被封 | 给 `echgate --ip-list` 喂一个黑洞 IP，让网关必失败 | R2（自动回退 + 三态贴熔断条）、R4（降级矩阵） |
| 直连必撞 RST | hosts 把站点域名指到 `127.0.0.1:1` | R1 的"关开关后回落"、验证"受限域不排 Direct" |
| 代理可用 | 本地 15 行 Go/mitmproxy 起一个 HTTP 代理 | yield 定责（`gateBlameAfterYield`）、R5 切站/切网/强制 |

做成 `tools/phase5/restrict_sim.sh`（起/停/断言三段），R2/R4/R5 就能在本机跑完，
只剩 R1（真 SNI 阻断）、R3（真 CF 挑战）、R6（三端冒烟）需要真受限网。
**把"等换网"变成"等 3 项"，是这个阶段最大的杠杆。**

### F. 播放链路补回退与上报

1. Android：给 `EchGateDataSource` 加一次 `allowGate = false` 兜底（与
   `DesktopMpvPlaybackEngine.kt:136-145` 同语义），别让三端在这里分叉。
2. 三端：给 `PlayerNetworkConfig` 加 `onLoadOutcome(uri, ok, reason)` 钩子，
   回调 `EgressReporter.report(domain, Gate, ...)`，让视频域有自己的健康数据（修 F9）。
3. 顺手把 `PlayerWiring.android.kt:30` 那条"是否被 Exo 尊重**未实测**"实测掉——
   一句话的事，别留着。

### G. 加一条"能力矩阵"守卫测试

把三端的 `supportsFullscreen` / `supportsBrightness` / `shouldEnterPip` /
`rewriteForGate != null` / `proxyUrlFor != null` / `userAgent.isNotBlank()`
钉成一张期望表，任何一端偷偷翻 true 而实际没实现，测试就红。

这是防"假动作"回归**最便宜**的手段——F12、F13、D5 这三类问题都能被它提前抓住。

### H. 顺手清理

- `RouteRegistry.update` 改 CAS 循环（`snapshot` 用 `AtomicReference` + `getAndUpdate`），
  或者把熔断计数单独用 `AtomicInteger` 存（修 F7）。
- 删掉三处过期注释：`EchGate.ios.kt:46`、`EchGate.kt:122`、
  `SchedulerModels.kt` 的 `route` 参数（或真的用起来）（修 D1–D3）。
