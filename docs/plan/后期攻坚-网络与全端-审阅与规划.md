## 一、定位 → 可验收目标

### 1.1 四条定位（原文转述）

| #  | 定位        | 关键词                             |
| -- | --------- | ------------------------------- |
| P1 | **免梯直连**  | 面向全端用户提供极致网络体验，用户可以**不用代理直接访问** |
| P2 | **代理开规则** | 使用代理时，**简单开规则**即可访问             |
| P3 | **镜像无缝**  | **域名镜像无缝切换**                    |
| P4 | **极客可控**  | 满足极客用户的**配置直连**                 |

### 1.2 定位 → 可验收目标

定位是方向，必须转成能验收的句子，否则"极致体验"无法判断做没做到。

| 定位 | 可验收表述                                              | 主指标                         | 现状                                                            |
| -- | -------------------------------------------------- | --------------------------- | ------------------------------------------------------------- |
| P1 | 全新安装、无任何配置、**不挂代理**，首屏 5s 内可交互；站点不可达时不出现"转圈到超时"    | `T1` 首屏可交互 / `R_fail` 会话失败率 | **部分达成** —— 网关 + 自动档默认开，但只有 ECH 与 CNAME 真名两条路（F2）             |
| P2 | 用户填一次代理地址，**不需要额外配规则**，站点链路自动走代理、其余自动直连            | 手动配置项数 = 1                  | **未达成** —— 当前只有"全局代理 / 全局直连"两态（F5）                            |
| P3 | 切换镜像**不掉登录态、不弹验证窗、不需要用户感知**；主镜像不可用时能自动换一个          | 切换成功所需用户动作数 = 0             | **部分达成** —— clearance 已按 zone 存档，但仍需 `killProcess` 重启（F8）     |
| P4 | 极客可逐项控制：域名 → IP 映射、每域出口、网关参数、DoH 端点，且**可导出可复现的配置** | 可配置维度数                      | **部分达成** —— routes/ForceMode/DoH/hosts 已有，缺导入导出与每域粒度（F11–F13） |

> **注意 P1 与 P2 的语义边界**：P1 是"不配代理也能用"，P2 是"配了代理更简单"。二者不能互相顶替——P2 的实现**不得**削弱 P1 的零配置默认体验（默认路径不能变复杂）。

### 1.3 负向定位（明确不做）

| 不做                       | 理由                                        |
| ------------------------ | ----------------------------------------- |
| 不做"必须挂代理才能用"的默认路径        | 与 P1 直接冲突                                 |
| 不做 PAC 脚本下发 / 规则订阅       | 引入远端依赖，违反"零配置可用"；规则以**本地内置 + 本地可编辑**为界    |
| 不引入需要用户理解的技术概念作为**必经**步骤 | 极客能力一律是**可选增强**，不是前置条件                    |
| 不为 iOS 单独维护一套判定逻辑        | 判定必须在 `commonMain`，平台只提供原语（现有架构已保证，需继续守住） |

### 2.2 已有的可复用基建（做新功能时**不要**另起炉灶）

| 基建                                  | 可以拿来做什么                             |
| ----------------------------------- | ----------------------------------- |
| `DomainClass` + `isRestricted`      | **代理规则分流的现成判据**（F5 落地成本因此很低）        |
| `EgressScheduler.plan()`            | 镜像选优可直接复用同一套健康/熔断/择优模型              |
| `RouteHealth` / `RouteRegistry`     | 新增"镜像"维度 = 新增一个健康域，模型无需改            |

| `PlayerTrace` / `StartupTrace`      | 指标埋点已在，缺的是**汇总口径**（F4）              |
| `EgressEvents` + 导出                 | 诊断报告的现成数据源（F14 只需加排版与结论层）           |
| `Buffer 已有的 settings 热读模式`          | 新配置项应沿用"存储 + 每请求读"，**不要**引入 rebuild |

### 2.3 指标埋点现状（决定"极致体验"能不能被证明）

| 追踪器            | 覆盖                                        | 缺口                                   |
| -------------- | ----------------------------------------- | ------------------------------------ |
| `StartupTrace` | 冷启动各阶段                                    | 无首屏**网络**耗时拆分                        |
| `PlayerTrace`  | `video-request-start` → `first-frame` 全链路 | 有标记但无出口归因（不知道这一跳走的是 Gate 还是 Default） |
| `EgressEvents` | 每次出口尝试（域 / 路由 / 结局 / rtt / budget）        | 只到"尝试"粒度，不与用户可感知指标（首屏 / 起播）关联        |

> **这是 P1 的第一优先项**：没有 `T1`/`T2` 与出口归因的关联，任何"优化"都无法判定是改善还是运气。

> **编号说明**：以下编号为本文件自有体系。代码注释中历史引用的 `F*`（那份审阅稿不在仓库内）请以本条为准：**原 F6（`EgressBudgets.budgetFor` 的多余 `route` 参数）已随该参数删除而关闭**，详见 `egress/SchedulerModels.kt` 的 KDoc。

### 3.1 P1 免梯直连

| #      | 差距                                                                | 影响                                     | 参考项目做法                                                                                                    | 采纳建议                                                                                                                  |
| ------ | ----------------------------------------------------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| **F1** | **ECHConfigList 来源偏窄**：网关只有「DoH JSON 正则抓 `ech=`」+「内置 base64 兜底」两级 | CF 轮换密钥或 DoH 端点不可达时，只剩会过期失效的内置兜底       | `EchDoh` 手写 DNS wire 查询 + 手解 **SVCB/HTTPS 记录 key 5** + 三级来源（`cloudflare-ech.com` 实时记录 ⇄ 目标域自有记录 ⇄ 配置 DoH） | **采纳**。Go 侧 `lookupHTTPS` 已能拿记录文本，缺的是：① 目标域自有 HTTPS 记录作为第二源；② A/AAAA 之外**独立**取 HTTPS 记录（现在只在 `resolveECHConfig` 里取一次） |
| **F2** | **无 QUIC / HTTP-3**                                               | 静态资源（封面、站点图）走 TCP；慢启动与队头阻塞全吃           | Rust quiche 0.22 静态链入 `libchino.so`，`H3Interceptor` 对静态扩展名改走 UDP QUIC                                     | **待决策 D1**。本项目网关是 Go 进程，用 `quic-go` 无需 Rust/NDK，成本远低于参考项目                                                             |

| **F4** | **直连质量不可见 / 无归因**                                                 | 用户不知道"这次走的是网关还是直连"；开发者不知道优化有没有效        | `EchDiagnostics` 四步报告（解析 → ECH 配置 → 请求 → H3）                                                              | **采纳（优先）**。先做「指标 ↔ 出口」关联，再做报告 UI                                                                                      |

## 五、参考项目能力采纳清单（学什么 / 不学什么）

> 定位要求的"学习 han1meviewer 的优秀之处"在此收敛为一张决策台账。  
> 判据：**能不能帮忙达成 §1.2 的可验收目标**，而不是"对方做了我们也要做"。

### 5.1 采纳

| 参考项目能力                                             | 采纳形式                                                     | 落点            | 为什么值得学                                            |
| -------------------------------------------------- | -------------------------------------------------------- | ------------- | ------------------------------------------------- |
| `EchDoh` 的 **SVCB/HTTPS 记录解析**                     | 网关侧扩展 ECHConfigList 来源（不做手写 DNS wire，用 Go 的 DoH JSON 即可） | **B1-2**（F1）  | 我们只有"DoH 正则抓 `ech=`"一级来源，对方有三级；CF 轮换密钥时差距直接体现为连不上 |
| `EchDoh` 的 **IPv6 候选**                             | DoH 加 AAAA 查询                                            | **B1-3**（F3）  | 低成本，v6 边缘往往更快                                     |
| `EchDiagnostics` 的**四步报告**                         | 在现有 `EgressEvents` 上加"结论层"                               | **B4-4**（F16） | 我们有数据没结论，用户看不出问题在哪                                |
| `SpeedLimitInterceptor` 的**下载限速**                  | 直接对齐                                                     | **B5-2**      | 独立小项，移动端刚需                                        |
| `EchTransportPolicy` 的**域分级思路**                    | 升维为"规则分流"（对方只有 core / 非 core 两档）                         | **B2-1**（F5）  | 思路可用，粒度我们要更细                                      |
| `AutoBuiltInHosts` 式"**探测 + 回退**"（对方用无探测的硬编码 IP 池） | 我们已是更优解，反向确认                                             | 已有            | 证明"可探测的默认开"比"强制档"更安全                              |

### 5.2 明确不采纳

| 参考项目做法                                                                                             | 不采纳理由                                                                                                                                                                        |
| -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **WebView 三层接管**（`shouldInterceptRequest` + JS hook `fetch`/`XHR`/form + `@JavascriptInterface` 桥） | 本项目用 `GateWebViewProxy` 把 WebView **整体**对齐到 App 出口，语义上更强：对方 JS 桥只覆盖 `hanime1.me` 系域名且要手动序列化 body，我们是出站级对齐，天然覆盖所有子资源。代价是 WebView 内请求用不了 ECH（走 CONNECT 隧道），但 CF 验证页本来就只需要"同出口" |
| **进程内 Conscrypt ECH**                                                                              | 需要 R8 keep 反射契约（改一个字节即静默失效，且**失败是静默的**）+ 只支持 TLS 1.3 + Android 专属。本项目进程外网关反而**三端统一**且失败隔离                                                                                    |
| **body 层替换备用 CDN**（`replaceBackupMediaCdnHost` 字符串替换）                                              | 本项目用网关 `alias` 策略在 **SNI + Host 层**解决，比响应体字符串替换更根本——对方只能覆盖已出现在 HTML 里的 URL，且换不掉 SNI                                                                                          |
| **Rust quiche + NDK 工具链**                                                                          | 若做 QUIC，Go 侧 `quic-go` 同语义且不引入第二条原生工具链（对方为此写了 223 行 `EchH3.kt` + `prepare_quiche.py` + `verify_ech.py`，且只覆盖 Android）                                                         |
| **切域名/改 hosts 就 `killProcess` 重启**                                                                 | 对方同样这么做，但这正是 P3 要消灭的行为——**不学**                                                                                                                                               |

### 5.3 反向借鉴（对方踩过的坑，我们不重犯）


| 对方的问题                                        | 我们的现状                                     | 后续注意                                        |
| -------------------------------------------- | ----------------------------------------- | ------------------------------------------- |
| `rebuildNetwork()` 漏重建 `subscriptionService` | 我们是稳定单例，不存在此问题                            | 新增 client 时沿用"稳定单例 + 拦截器每请求读设置"             |
| `HCookieJar.cookieMap` 无界累积导致全站 400          | 已按名对账 + 有界去重（`HCookieJarBoundsTest`）      | 新增 cookie 路径必须过同一有界化                        |
| `HDns.getCDNList()` 与实际解析路径不一致（延迟测试显示假数据）    | 已改为走 `preferredIps()`                     | 任何"测试/诊断"功能必须复用**真实**判定路径，不得另写一份            |
| 三个 client 均未配 `readTimeout`                  | 已按用途补齐（Api 30s / Image 15s / Download 不限） | 新增 client 必须显式声明三档超时                        |
| `EchDoh.invalidateEch()` 的副作用对所有 host 生效     | 我们的失效粒度按域（`RouteRegistry.reset(domain)`）  | 新增缓存注意失效范围                                  |
| 并发上报未加锁致熔断计数少算                               | 已用 `PlatformLock` 包住读-算-写                 | 任何"读快照 → 算 → 写回"都必须加锁（`EgressReporter` 是样板） |

## 六、待决策点（讨论用）

> 以下六项**未收敛前不应动代码**。每项给出选项与我的建议，请逐项确认或否决。

### D1 · QUIC / HTTP-3 做不做？走哪条技术路线？

| 选项                          | 成本 | 收益                                       | 风险                                                                            |
| --------------------------- | -- | ---------------------------------------- | ----------------------------------------------------------------------------- |
| **D1-a 不做**                 | 0  | 0                                        | `T1` 上限被 TCP 慢启动锁死；参考项目有而我们没有                                                 |
| **D1-b 网关侧 `quic-go`**      | 中  | 静态资源走 UDP + 0-RTT；**不引入第二条原生工具链**（Go 已在） | `quic-go` 的 ECH 支持需实测验证；UDP 在部分网络被 QoS 降级                                     |
| **D1-c 照搬参考项目 Rust quiche** | 高  | 与参考项目同款已验证路径                             | 引入 Rust + NDK + 版本脚本 + Gradle 任务链（参考项目为此写了 223 行 `EchH3.kt`）；**且只覆盖 Android** |

**我的建议：D1-b，但排在 B5**（即"先做 B1–B4，QUIC 最后"）。理由：QUIC 优化的是静态资源与 ECH 复用，而当前最大收益点在**路径正确性**（F1/F5/F9）而非传输效率；且 D1-b 需要实测 `quic-go` 的 ECH 支持度后才能给出确定成本。

**需要你确认**：① 是否接受"QUIC 排在最后"；② 是否接受走 Go 而非 Rust。

### D2 · 镜像无缝切换做到哪一档？

| 档                   | 内容                       | 用户体验           |
| ------------------- | ------------------------ | -------------- |
| **D2-a 免重启**        | 只做 B3-1                  | 切换不再重启，但仍需用户手选 |
| **D2-b 免重启 + 手动探测** | B3-1 + 设置页一次"测速并推荐"      | 用户点一下，看到哪个最快   |
| **D2-c 全自动**        | B3-1..B3-4：自动选优 + 失效自动切换 | 用户完全无感         |

**我的建议：D2-c**，但**分两步交付**（先 B3-1，验证无副作用后再 B3-2..4）。理由：P3 的字面要求是"无缝"，D2-a/b 只是"少一次重启"，不算无缝。

**需要你确认**：自动切换是否可接受"用户正在浏览时后台悄悄换域名"（会带来 clearance/登录态的一次校验开销）。若不可接受，退化到 D2-b。

### D3 · 代理规则的粒度？

| 选项                 | 规则形态                  | 极客可编辑   |
| ------------------ | --------------------- | ------- |
| **D3-a 内置单档**      | 只有「只代理受限域」一个开关        | 否       |
| **D3-b 内置 + 用户追加** | 内置规则 + 用户加域名/后缀       | 是（文本列表） |
| **D3-c 规则文件导入**    | 支持导入规则文本 / 从 hosts 样式 | 是（文件）   |

**我的建议：D3-b**。理由：P2 说"**简单**开规则"，D3-a 已经满足字面要求；但 P4 说"极客可配置"，D3-b 用一个文本列表同时满足两者，成本可控。**D3-c 不做**（与 §1.3 负向定位冲突）。

### D4 · iOS 代理缺口怎么补？

| 选项                | 做法                                                                | 成本            | 副作用                                    |
| ----------------- | ----------------------------------------------------------------- | ------------- | -------------------------------------- |
| **D4-a 不管**       | iOS 只支持系统代理                                                       | 0             | iOS 手填代理永久失效，P2 在 iOS 上不成立             |
| **D4-b 网关代转**     | 网关新增"上游代理"能力：Kotlin 侧把用户代理**配给网关**，网关出站时先连代理                      | 中             | 网关多一跳；但**三端语义统一**，且顺带解决 F7（SOCKS）      |
| **D4-c 换引擎**      | iOS 不用 Ktor Darwin，改用 NSURLSession 手动 `connectionProxyDictionary` | 高             | 要重做 iOS 传输层；Darwin 引擎的 cookie/超时语义全部重来 |
| **D4-d iOS 也走网关** | iOS 进程内起服网关（已具备），把用户代理交给它                                         | 低（= D4-b 的特例） | 依赖 iOS 网关可用；但 iOS 网关本就无条件起服            |

**我的建议：D4-b（= iOS 走 D4-d）**。理由：选项 d 复用已有架构（iOS 网关本就无条件起服、端口经 `EchGatePortReporter` 回填），网关出站加一个 `--upstream-proxy` 就能同时解决 F6 与 F7，且**判定逻辑不进平台分叉**（符合 §1.3）。

**需要你确认**：是否接受"iOS 的用户代理经由本地网关中转"（表现为 `T2` 可能多几毫秒，但换来三端一致）。

### D5 · 优先端顺序？

| 选项                  | 顺序                      | 影响                                                |
| ------------------- | ----------------------- | ------------------------------------------------- |
| **D5-a Android 优先** | Android → Desktop → iOS | 与现有测试覆盖一致（desktopTest 3,003 行 > commonTest 1,216） |
| **D5-b Desktop 优先** | Desktop → Android → iOS | 桌面是当前唯一验证过 ECH 全链路的端（`EchGateLiveTest`）           |
| **D5-c 三端同步**       | 每批次都三端验收                | 最慢，但不会出现端间行为漂移                                    |

**我的建议：D5-c（但按 D5-a 的验收顺序）**。理由：本项目最大的架构资产是"判定在 commonMain、三端共用"，端间漂移是这套设计唯一的结构性风险（`MediaProxyResolver` 的历史 bug 就是 android 侧另写了一份判据不同的实现）。每批次三端都过一遍验收，代价换的是不返工。

### D6 · 极客能力的边界？

| 选项                     | 范围              |
| ---------------------- | --------------- |
| **D6-a 现有 + 导入导出**     | 只做 B4-1（F13）    |
| **D6-b a + 每域出口**      | 加 B4-2（F14）     |
| **D6-c b + 网关参数 + 报告** | 加 B4-3、B4-4（全量） |

**我的建议：D6-c**。理由：这四项之间共享基础设施（`EchGateContract` / `BackupManager` / `EgressEvents`），全做只比部分做多约 30% 成本，但能把"极客可控"这条定位做实。

**需要你确认**：F14（每域出口）会不会让设置页过于复杂？若是，可放"高级"折叠区。
