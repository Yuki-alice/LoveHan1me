## 一、U1 · 跨镜像的登录态是否可复用

**结论：可复用，且已实站验证过。B3 不需要处理登录态迁移。**

### 证据（代码内记录的实站验证）

`shared/src/commonMain/.../site/SiteSwitcher.kt:125-138`：

```kotlin
// 3) 清进程级站点凭据，但**保留登录态**。
//
//    javchu 与 hanime 后端共用同一套账号（订阅 / 历史 / 收藏互通，实站验证），
//    同一个会话 ID 两边都认；`loginCookie` 又是按 host 重写的全局值，
//    DataStore 里的 `isAlreadyLogin / loginCookie / savedUserId` 必须原样保留。
//    之前这里调 `logout()` 是登录丢失的根因 —— 它还跟"等价于重启"矛盾：
//    上游杀进程根本不清 DataStore，登录本来就该留下来。
```

### 机制（为什么能复用）

| 环节 | 实现 | 效果 |
|---|---|---|
| 存储 | `AppSettings.loginCookie: String`（**单一全局值**） | 不区分域名 |
| 注入 | `HCookieJar.loadForRequest(url)` 对**任意 host** 都注入 `CookieString(loginCookie).toLoginCookieList(host)` | 请求哪个域，就用哪个域重新构造 cookie |
| 服务端 | 四个域共用同一套账号，同一会话 ID 互认（实站验证） | 会话在目标域有效 |

即：**"单一全局 loginCookie + 按当前 host 重写" 恰好就是跨域复用所需的形态**——不需要按域存档。

### 对规划的影响

| 原判断 | 修正 |
|---|---|
| U1 是 B3-1 的最大不确定性 | **不确定性消除**。B3 无需登录态迁移 |
| — | `cfCookies` 为**按域存档**（`Map<host,String>`），与 `loginCookie` 的全局形态不同——这是**正确的**，因为 clearance 按 CF zone 签发（见 U4） |

**剩余无需处理**：会话若恰在新域过期，走既有登录过期路径重新登录，与正常过期一致。

### 2.2 缺口（本次新增发现）

#### F22 · iOS 切站不复位熔断健康度（平台不对称，**P1**）

```kotlin
// iosMain/.../core/platform/ProxyPlatform.ios.kt —— 全部内容
actual fun rebuildSystemProxy() {
}
```

`SiteSwitcher.switchTo()` 只调 `rebuildSystemProxy()`，**没有**直接调 `RouteRegistry.reset()`。
于是：

| 平台 | 切站时 `RouteRegistry.reset()` | 后果 |
|---|---|---|
| Android / Desktop | ✅ 经 `ProxyPlatform.jvm.kt:16` 执行 | 熔断结论清空，新站重新评估 |
| **iOS** | ❌ **不执行** | **旧站的熔断结论带到新站** |

而 `ProxyPlatform.jvm.kt` 自己对这条复位给了明确的理由：

> *同一个理由作用在各域健康上：出口换了，"这个网关还能不能用"的旧结论也失效。不给它归零的话，用户换到一条能用的代理后，网关照旧被冷却期挡着 —— 那是误判。*

**iOS 无 `CdnIpProbe` 与系统代理，空实现本身合理；但 `RouteRegistry` 是 commonMain 的，iOS 同样适用。**
**修法**：把 `RouteRegistry.reset()` 从平台 actual 上移到 common 的调用点（`SiteSwitcher` / `BackupManager`），平台 actual 只保留平台专有项。这正是 §1.3「不为 iOS 单独维护一套判定逻辑」要守的线。

> 注：iOS 设置页在 DoH / 代理改动处**有**直接调 `RouteRegistry.reset()`（`PlatformSettingsRoutes.ios.kt:187,231`），说明作者知道要复位——只是**漏了切站这一条路径**。

#### F23 · 切站不复位 DoH 负缓存冷却（**P2**）

`HanimeDns` 的 DoH 负缓存（`dohFailures` / `dohCoolingUrl` / `dohCooldownUntilMs`）只在**换网**时清理：

```kotlin
// NetworkChangeReactions.jvm.kt
actual fun platformOnNetworkChanged() {
    rebuildSystemProxy()
    ServiceCreator.evictConnectionPools()
    HanimeDns.clearDohCooldown()   // ← 只有换网走这里
}
```

切站走 `rebuildSystemProxy()`，**不含** `clearDohCooldown()`。
**后果**：若切站前 DoH 刚连续失败 3 次进入 30s 冷却，切站后新站首屏仍走系统 DNS（可能被污染），表现为"切了站还是打不开"。
**修法**：`rebuildSystemProxy()`（jvm）内补一行 `HanimeDns.clearDohCooldown()`——语义与它已有的"出口现实变了"完全一致。

### 2.3 未清理但确认无害（不建议动）

| 对象 | 为何无害 |
|---|---|
| `ServiceCreator` 三个 client + CDN 链的连接池 | 按 host 分键；旧 host 的空闲连接在 5min / 网关 90s 后自行回收。**不调 `evictConnectionPools()` 是对的**——那是"换网"语义，切站时旧连接可能还在用（例如下载中） |
| `EchGate` 网关进程 | host 无关；Go 侧 `plans` 按 host 分键，旧 host 条目留着无副作用 |
| Coil 图片缓存 | 按 URL 分键 |
| `EgressEvents` ring buffer | **建议保留**——切站后翻诊断，正好能看到"切之前发生了什么" |
| Room 四个库 / DataStore / OkHttp 磁盘缓存 / 下载文件 | 按上游语义保留（"等价于重启"不清持久层） |

## 四、U4 · 自动切镜像对 CF 的副作用

> ⚠️ **本项结论与已确认的 D2-c 冲突，需要重新拍板。**

### 4.1 硬事实：clearance 必然跨域失效

| 事实 | 依据 |
|---|---|
| `cf_clearance` 按 **CF zone** 签发 | CF 机制 |
| 四个域名（`hanime1.me` / `hanime1.com` / `hanimeone.me` / `javchu.com`）分属**不同 registrable domain** ⇒ **必然不同 zone** | 域名注册规则（一个 zone 只服务一个 registrable domain） |
| `cfCookieFor(host)` **不跨 zone 匹配** | `CloudflareClearanceTest.兄弟zone拿不到主站的凭据` 固化了这条规则 |
| `cfCookies` 按 host 存档，是**正确**的设计 | `AppSettings.cfCookies` KDoc：单行存储会让"在 B 域验证成功"顶掉 A 域凭据 |

### 4.2 直接推论

**自动切换到另一个镜像后，目标域的首次请求必然撞 CF 挑战**（除非该域**已有存档 clearance**）。

这与 P3「域名镜像**无缝**切换」直接冲突，且**不是能靠代码消除的**——zone 由域名决定，不由我们决定。

### 4.3 对 D2 的影响（需重新决策）

| 档 | 是否仍可行 | 需要的补充条件 |
|---|---|---|
| D2-a（免重启） | ✅ 已实现（见 F9 修正） | — |
| D2-b（免重启 + 手动探测推荐） | ✅ 可行 | 提示"目标域可能需要验证一次" |
| **D2-c（全自动）** | ⚠️ **需补前置条件** | **只在目标域已有有效 clearance 时自动切**；否则不切、或降级为提示 |

**我原先给 D2-c 建议时没有发现这一条，这是我的疏漏。** 建议改为：

> **D2-c'**：全自动切换，但**以"目标域已有 clearance"为前置**。
> 用户首次访达各域的 cost 只付一次（手动切过去验证一次，clearance 就按域存下来了），
> 之后自动切换才是真无缝。对**从未访问过**的域，不自动切——因为切过去也是弹窗，不如不切。

### 4.4 仍需实测（本机无凭据，做不到）

1. 四个域是否真的各需一次验证（而非某两域共用 zone）——需在 4 个域上各走一次验证
2. 频繁切换域名/IP 是否触发 CF 风控（含 clearance 提前作废）
3. `javchu.com` 的 clearance 是否与 `hanime1.me` 互认（若后端共用账号，理论上仍各签各的）

## 五、U5 · 网关做上游代理转发后的 ECH 行为

**结论：不需要 PoC——现有语义已经给出答案：配了代理就不走 ECH。**

### 5.1 既有设计已经这么编码了

```kotlin
// EchTransportPolicy.kt
fun shouldFailClosed(host: String, proxyType: Int): Boolean =
    EchHosts.isCoreDomain(host) && !isProxyRoute(proxyType)   // 代理路由时不再 fail-closed
fun shouldUseH3(proxyType: Int): Boolean = !isProxyRoute(proxyType)   // 代理路由时禁用 H3
```

**"代理优先于 ECH"是本项目从一开始就有的策略**（源码注释：*"When the user selects a proxy route, the proxy must win over direct-only ECH behavior so proxy-only networks remain usable."*）。

### 5.2 为什么在代理隧道里做 ECH 是零收益

ECH 的目的是**对本地网络**隐藏 SNI。一旦使用代理：

- 本地网络看到的只是"到代理服务器的一条连接"，**真 SNI 本来就不在暴露面上**
- 在代理隧道内再做一次 ECH（HPKE 加解密 + 一次额外往返）**不增加任何隐私**，只增加 CPU 与延迟

### 5.3 对 D4-b 的实现要求

| 项 | 要求 |
|---|---|
| 新增 flag | `--upstream-proxy http://host:port`（或 socks5） |
| **代理模式下的出站策略** | **显式关闭 ECH**；不使用 `--cf-hosts` 的 CF 候选 IP（改用代理解析）；走普通 TLS |
| 保留 `alias`（CNAME 真名）策略 | **保留**——它解决的是"按域名封锁"，不是"隐藏 SNI"，与代理无关 |
| 与平台侧语义一致性 | 与 `EchTransportPolicy.isProxyRoute()` 同口径，**三端不需要各自判定** |

**结论：D4-b 不需要"ECH + 代理"的 PoC**，但需要一次**语义确认**：网关在收到上游代理配置时，必须把自己切到"代理模式"（此前它是无状态的直连出站）。

## 六、顺带完成 · U8（DoH 是否被下掉 HTTPS 记录）

本项为只读查询，本机可做，已实测。

### 6.1 实测结果（AliDNS，2026-10-10）

**`cloudflare-ech.com`（type 65）——正常，含 ECH：**

```json
{"Status":0,"TC":false,"RD":true,"RA":true,"AD":false,"CD":false,
 "Question":{"name":"cloudflare-ech.com.","type":65},
 "Answer":[{"name":"cloudflare-ech.com.","TTL":190,"type":65,
   "data":"1 . alpn=\"h3,h2\" ipv4hint=\"104.18.10.118,104.18.11.118\"
           ech=\"AEX+DQBBfAAgACDS/HJeLkFCWgJwi/tLzjbiwNyTmO0HLFRZOOBxb+jZOwAEAAEAAQASY2xvdWRmbGFyZS1lY2guY29tAAA=\"
           ipv6hint=\"2606:4700::6812:a76,2606:4700::6812:b76\""}]}
```

**`hanime1.me`（type 65）——无 ECH，且 ipv4hint 不在 CF 段内：**

```json
{"Status":0,"TC":false,"RD":true,"RA":true,"AD":false,"CD":false,
 "Question":{"name":"hanime1.me.","type":65},
 "Answer":[{"name":"hanime1.me.","TTL":178,"type":65,
   "data":"1 . alpn=\"h2\" ipv4hint=\"69.162.134.178\""}]}
```

### 6.2 三条读数

**① 默认 DoH（AliDNS）没有下掉 `cloudflare-ech.com` 的 ECH 记录** → 网关当前的 ECH 获取路径可用，U8 的核心担忧（被 NXDOMAIN/丢弃）在本机网络下不成立。**但仍要注意 `AD:false`（无 DNSSEC 认证），响应可被篡改。**

**② `hanime1.me` 自己的记录没有 `ech=`，且 `ipv4hint=69.162.134.178` 不在任何 Cloudflare 段内。** 两种解释：

- **(a) 中国解析器对 hanime1.me 的答案被篡改或降级** —— 项目自身已记录同一现象：*"系统 DNS 对 `hanime1.me` / `www.hanime1.me` / `hanimeone.me` 全部返回**不可达**的假 IP（443 握手超时，`hanimeone.me` 甚至落到 Facebook 段）"*
- **(b) `hanime1.me` 是 CF **仅 DNS（灰云）**接入**，不在 CF 代理后 —— 那它本来就不该有 ECH

**③ ⚠️ 无论 (a) 还是 (b)，都推出一条硬结论：不能把"目标域自己的 HTTPS 记录"当作 ECH 配置来源。**

### 6.3 由此**撤回**我 v1 里 F1 的一条建议

v1 的 F1 写的是"**目标域自有 HTTPS 记录 + `cloudflare-ech.com` 实时记录双源**"。**这条撤回**——对受限域，目标域自己的记录恰是最不可信的那一份（要么被篡改，要么本就不发 ECH）。

**F1 的正确形态**：**用多个可信端点去查同一个不受审查的域（`cloudflare-ech.com`）**，而不是去查更多域。这也正是参考项目 `EchDoh` 的 `LIVE_SOURCE_HOST` 设计——它的"多源"是**多端点**（纯 IP DoH 池 + 配置的 DoH），不是多域名。

### 6.4 附带发现

| # | 发现 | 影响 |
|---|---|---|
| **F24** | CF 该记录 **TTL 只有 190s**，而网关 `echCacheTTL` 是**固定 1 小时、完全忽略 TTL** | 可能长时间使用已被轮换的配置。参考项目是按 TTL 取 clamp（`coerceIn`）而非固定值。**采纳：TTL 跟随 DNS，clamp 到 [10min, 1h]** |

### 已拍板（2026-10-10 更新）

**D2 = D2-c（全自动），clearance 前置检查做成可配置策略（默认开）。**

落地形态（详见 `任务分解-B0到B5.md` §2）：

```kotlin
enum class AutoMirrorGuard {
    RequireClearance,  // 默认：只在目标域已有 clearance 存档时自动切
    Always,            // 逃生舱：无条件自动切，接受可能弹一次验证窗
}
```

做成**可配置**而非写死：两种取舍都合理（严格=不打断 / 宽松=可达性优先），翻转只是一个枚举值。

**另发现一条必须处理的约束**：`SiteSwitcher.switchTo()` 会递增 `generation`，而 `App.kt:161` 的 `key(generation)`
**重建整棵 composition**（nav 栈上所有 VM 重置）。手动切换这是对的；**自动切换若复用它会把用户正在看的界面推倒重来**
⇒ 必须新增轻量变体 `autoSwitchTo()`（不递增 generation、不清 cookie、不动 CSRF 槽位）。
