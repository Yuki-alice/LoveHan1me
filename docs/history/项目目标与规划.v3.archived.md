# LoveHan1me 项目目标与规划 v3

> 制定日期：2026-09-10 ｜ 状态：**v3**
> v2 → v3 变更（**重大修订**）：
> 1. 主轴改为**两段式**：先 1:1 KMP 复刻 Han1meViewer，再做差异化重构
> 2. 推翻 v2 中「死因 = AI 代码堆砌」的判断（前提错误：代码系从 Mac 迁移，非未验证的 AI 堆砌）
> 3. 按用户实测修正废案教训：编译期架构门禁=形式主义、hot reload 对 agent 无用、云同步无后端未测试、**真正的死因是前端视觉层写死导致改动寸步难行**
> 4. 风险 R4 由「重蹈 AI 堆砌」改为「**重蹈视觉层改不动**」

---

## 0. 目标：两段式

### 阶段一 —— KMP 版 Han1meViewer（1:1 复刻）

> 先把 `Han1meViewer-main`（Android 原生，326 kt / 52,602 行）**完整、可用、三端一致**地复刻成 KMP + Compose Multiplatform。**不追求超越，只求功能对齐且能跑。**

- 出口标准：Android / Desktop / iOS 三端均可运行，功能与原 Android 版对齐，无 P0 崩溃。
- 此阶段**不做**视觉重构、**不做**差异化功能。

### 阶段二 —— 差异化重构

> 在能跑的复刻版之上，做**前端视觉设计重建**与**功能差异取舍**，目标：超越原网站体验，比肩成熟流媒体客户端。

- 出口标准：设计系统可整体换肤；播放体验、离线、弹幕等差异化能力落地。

### 2.5 废案教训（按用户实测修正）

| 项 | v2 判断（错） | 用户实测（对） |
|---|---|---|
| 编译期架构门禁 | 最高价值资产，animeko 都没有 | **屁用没有，该报错还是报错，严重影响开发效率** |
| Compose Hot Reload | 未评估 | **对 agent 编码没有任何用，严重影响开发效率** |
| 云同步 | 最高价值，可直接复用 | **没有后端，根本没测试过** |
| 前端视觉层 | 未识别 | **存在无法修复的问题，改动重构寸步难行** ← **真正的死因** |

**由此得出本项目第一原则**：

> **可改动性 > 完整性。** 废案不是功能不够，是**改不动**。任何阶段都要保证"想改就能改"。

### 2.6 可改动性纪律（针对真实死因）

1. **视觉层绝不写死**：颜色/字号/圆角/间距一律走设计 token，页面只消费 token。阶段二换肤时改 token 即可，不必动页面。—— 这是废案用整个项目换来的教训。
2. **不引入形式化约束**：编译期门禁、强制 verify 任务等"看起来规范"的东西，若不能真正拦住错误，就是纯成本。
3. **每个改动当场验证**：编译 + 运行 + 演示。
4. **git 已建立基线**（`f32e117`），任何重构前先确保可回退。
5. **大文件优先拆**：阶段二动视觉之前，先把 `VideoPlayerUi`(1761) / `VideoIntroductionScreen`(1515) / `Parser`(1194) 拆到可改的粒度。

## 3. 阶段二：差异化设计

### 3.1 关键判断：与 animeko **不同构**

animeko 护城河是「bangumi.tv 只是元数据站，它把『查条目 → 看视频』那段路自己做完」。但 **hanime1.me 本身就能播**。

- ❌ 照抄 animeko 的 BT 下载、多源选源、字幕组偏好 → **无用功**（直链站点）
- ✅ 差异化是「**播得比它好**」+「**加它结构上做不到的东西**」

### 3.2 差异化矩阵

**A 类 · 原网站结构性做不到（护城河）**

| 功能 | 依赖后端 |
|---|---|
| 离线下载 + 离线浏览（原站纯在线） | 否 |
| 播放器硬能力：手势族、快捷键、倍速记忆、画中画、后台播放、自动跳片头、Anime4K 超分 | 否 |
| 跨端续播（三端共享进度） | 是 |
| 广告拦截 | 否 |
| 本地智能（基于本地行为的规则推荐、去重、统计） | 否 |

**B 类 · 体验碾压**

| 功能 | 目标 |
|---|---|
| 秒开首帧 | 预连接 + 解析缓存 + 地址预解析，**< 1s** |
| 搜索 | 高级筛选、历史、即时搜索、本地索引 |
| 自愈能力 | Cloudflare / IP 封锁友好提示 + 恢复，**单源失败不拖垮全局** |

**C 类 · 从 animeko 抄的韧性设计**

- 选源**时间分段降级**：0–5s 精确 → 5–15s 放宽 → 15s 后模糊
- 播放错误**自动换源/降级**，截止时间压到 1 秒，保留黑名单
- 单源失败必须 emit 空结果，否则一个源炸了全局不发射

### 3.3 明确不做

- ❌ BT / P2P（直链站点）
- ❌ 真·个性化推荐（无数据规模）
- ❌ 社交 / 一起看
- ❌ 上架应用商店
- ❌ 云同步（D13）、编译期架构门禁（D11）、hot reload（D12）

## 4. 架构目标

1. **平台 API 只出现在 `:platform`**，由 convention plugin 自动注入 commonMain
2. **三端启动器薄如纸** —— 启动器里出现业务代码即分层失败
3. **Page + ViewModel 同进 commonMain**
4. **依赖方向单向**：`platform ← data ← domain ← feature-ui ← application ← 启动器`
5. （D11）以上靠规范与 review 保证，**不引入编译期 verify 任务**

**模块演进**（渐进，不一步拆 45 个）：

```
现状：:shared  :app  :desktopApp
  ↓ 阶段一后期
:platform  :network  :parser  :database  :shared-ui  :app-shared
  ↓ 阶段二
:source-api  :source-local  :source-remote
:player-api  :player  :danmaku-api  :danmaku-ui  :feature-*
```

## 5. 分期规划

### 阶段一：KMP 版 Han1meViewer（1:1 复刻）

| 阶段 | 周期 | 内容 | 出口标准 |
|---|---|---|---|
| **P-1 环境** | 1 天 | `local.properties` / JDK 21 / platform / Gradle 9.4.1 | `:desktopApp:run` 跑起来 |
| **P0 编译攻坚** | 1–2 周 | 三端全绿、消灭双轨依赖 | 三端均可编译运行 |
| **P1 功能对齐** | 3–4 周 | 补齐与原 Android 版的功能差：下载 KMP 化（iOS/Desktop）、`res`→`composeResources`、拆 `Parser`、合并 5 个 Room 库 | **功能与原版对齐，无 P0 崩溃** |

### 阶段二：差异化重构

| 阶段 | 周期 | 内容 | 出口标准 |
|---|---|---|---|
| **P2 设计系统先行** | 2–3 周 | 建立 token 层（颜色/字号/圆角/间距）+ 可替换主题，页面改为消费 token | **换肤只需改 token** |
| **P3 解析代理服务** | 3–4 周 | Ktor 服务端 + 客户端 A/B 切换 + 契约测试 | 站点改版无需发版 |
| **P4 播放体验** | 4–6 周 | 先拆 `VideoPlayerUi`(1761)，再上秒开/预加载/手势族/快捷键/自动跳片头/错误换源 | 首帧 < 1s |
| **P5 弹幕引擎** | 3–4 周 | 引擎 + 本地文件导入 + 外部源接口 | 可挂载 ≥ 1 个源 |
| **P6 视觉重建** | 3–4 周 | 在 token 层之上重建前端视觉 | 视觉超越原网站 |
| **P7 发布** | 2 周 | README、Release 流程、下载页 | 首个公开 Release |

**总跨度约 6–7 个月**（每周 20h+）。
