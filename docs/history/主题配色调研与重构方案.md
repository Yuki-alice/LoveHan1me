# 主题配色调研与重构方案

> 状态：**调研完成，待评审，尚未编码**
> 调研方式：读代码 + 用项目真实依赖（`com.github.Kyant0:m3color:2026.1`，`SPEC_2026`）实跑色算，取 4 个种子 × 8 种调色板 × 明暗 = 64 组样本量化
> 目标：回答「当前配色与官方 MD3 有什么区别」，并给出可执行的重构分期

---

## 0. 一句话结论

架构是对的（HCT 动态色 + 语义角色 + 48 角色全量映射），**坏在实现层的三个具体决定**：

1. **卡片底色选错了角色** —— 浅色模式下卡片与页底 **完全同色（对比度 1.000）**，深色模式下却是 1.494。明暗严重不对称。
2. **页面底色有两套值** —— 9 处直接写 `background`、其余走 `pageSurface = surfaceContainer`，同一概念两个颜色。
3. **iOS 是半个主题** —— 只覆盖 3 个角色，8 种调色板 / 3 档对比度在 iOS 上点了没反应。

这三条都不是"审美偏好"，是可以用色值证明的缺陷，修完视觉变化明确可验收。

## 2. 与官方 MD3 的差异（逐条，带实测数据）

### D1 ⚠️ 卡片底色 `surfaceBright`：浅色模式完全失效

`HanimeDefaults.Colors.card = colorScheme.surfaceBright`

实测（4 种子 × 8 调色板 = 32 组，页底取 `surface`）：

| 候选角色 | 浅色分离度 | 深色分离度 | 明暗不对称度 |
|---|---:|---:|---:|
| **`surfaceBright`（现状）** | **1.000** | 1.494 | **0.494** ← 最差 |
| `surfaceContainerLowest` | 1.050 | 1.065 | 0.015 |
| `surfaceContainerLow` | 1.049 | 1.061 | 0.012 |
| **`surfaceContainerHigh`（建议）** | **1.165** | **1.234** | **0.070** |
| `surfaceContainerHighest` | 1.229 | 1.387 | 0.158 |

**浅色模式下 `surfaceBright` 与 `surface` 100% 同色**（Pink: 都是 `#FFF8F7`）。也就是说在这 9 个页面里，卡片背景和页面背景是同一个像素值，卡片的存在感完全靠描边和阴影撑着。

深色模式反过来是 1.494，比浅色高太多 —— 同一个 token 在两种模式下表现天差地别。

> 官方语义：`surfaceBright` / `surfaceDim` 的定位是"比 surface 更亮/更暗的**分区**色"，容器层级由 `surfaceContainer*` 承担。用它做卡片填充是角色误用。

### D2 ⚠️ 页面底色两套值并存

- 9 处直接 `.background(MaterialTheme.colorScheme.background)`
- 其余走 `HanimeDefaults.Colors.pageSurface = surfaceContainer`

实测 **`background == surface` 在 64/64 样本中完全相等**（SPEC_2026 下 `background` 已是 `surface` 的别名）。而 `surfaceContainer` ≠ `surface`（Pink 浅色：`#FDE9EB` vs `#FFF8F7`，差 1.11）。

→ **同一个"页面底色"概念，项目里有两个不同值**。9 个页面用 A，其余用 B。

受影响的 9 处：`SearchScreen`(2)、`VideoShellContent`(2)、`SharedHomeScreen`、`VideoScreen`、`PreviewContent`、`AvatarCropScreen`、`SubscriptionContent`。

> 官方语义：`background` / `onBackground` 是 M2 遗留角色，M3 里页面底色归 `surface`。

### D3 ⚠️ `surfaceVariant` 当容器填充（14 处）+ 半透明叠加（4 处）

**角色冗余**：实测 `surfaceVariant == surfaceContainerHighest` 在 **36/64 样本中完全相等** —— 包括默认 `TonalSpot` 以及 `Neutral` / `Vibrant` / `Expressive` / `Rainbow`（明暗均相等）；`FruitSalad` / `Fidelity` / `Content` 略有色相差。

→ 在用户默认使用的调色板下，`surfaceVariant` 就是 `surfaceContainerHighest` 的另一个名字，是冗余角色。

**半透明叠加破坏层级**（4 处 `surfaceVariant.copy(alpha = 0.35/0.4/0.55/0.6)`）：

| alpha | 叠加后实际色 | 与页底分离度 | 本应达到 |
|---|---|---:|---:|
| 0.35 | `#FBEFEF` | **1.071** | 1.231 |
| 0.40 | `#FBEDEE` | 1.085 | 1.231 |
| 0.55 | `#F9E9EA` | 1.120 | 1.231 |
| 0.60 | `#F8E8E9` | 1.131 | 1.231 |

alpha=0.35 时**层级差被稀释掉 60%**。文字对比度反而从 4.94 升到 5.68（不影响可读性），所以这是**层级失效**，不是可读性问题 —— 正因如此才一直没被发现。

> 官方语义：alpha 叠加只用于 scrim 和 state layer，容器填充必须用不透明角色，否则配对的 `onXxx` 语义失效。

### D4 ⚠️ iOS 是"半个主题"

`fallbackColorScheme()` 只在 `lightColorScheme()` / `darkColorScheme()` 基础上覆盖 `primary` / `secondary` / `tertiary` 三个角色，其余 45 个角色保持 **M3 baseline 紫色板**。

后果：
- iOS 上是「**粉色 primary + 紫色容器**」的混血配色
- **8 种调色板选项在 iOS 上完全无效**（点了无变化）
- **3 档对比度在 iOS 上完全无效**
- `useDynamicColor` 开关在 iOS 上无效（`rememberSystemAccentColorOrNull()` 恒 null）

三端不一致，且设置项给了但没效果 —— 这是体验问题不只是视觉问题。

### D5 ⚠️ 预设色与落地色严重不符

用户在选择器里看到的色块是 `ThemeAccent.colors.first()`，但真正落到 `primary` 的是 HCT 展开结果：

| 预设 | 选择时看到 | 实际 primary | Tone 变化 | Chroma 变化 |
|---|---|---|---:|---:|
| Pink | `#F596AA` 亮粉 | `#8A4D5A` 暗酒红 | 72 → **40** | 41 → 32 |
| Green | `#8BC34A` 亮绿 | `#4E6633` 橄榄褐 | 73 → **40** | 60 → 32 |
| Yellow | `#FFF59D` 淡黄 | `#6C6625` 橄榄褐 | 96 → **42** | 35 → 32 |
| Blue | `#03A9F4` 亮蓝 | `#346384` 暗蓝 | 66 → **40** | 57 → 32 |

色相完全保持（偏差 0°），但 **Tone 一律被压到 40**、Chroma 压到 32 —— 这是 `TonalSpot` 的固有行为（primary 固定 T40/C36），**不是 bug**。

问题在于：用户以为在选"亮粉"，拿到的是"暗酒红"，且 UI 没有任何解释，也没有"落地效果预览"。

### D6 48 角色映射在 androidMain / desktopMain 重复

两个文件各写了一份 48 角色的 `ColorScheme(...)` 构造（约 90 行，逐字段一致）。改一个角色要改两处，且违反了项目自己定的约定：

> 「`jvmMain` 是 `androidMain` + `desktopMain` 的共同父源集，两端行为相同的 actual 放 `jvmMain`」

m3color 是纯 JVM 色算，不依赖 Android 框架 —— 整段可以下沉到 `jvmMain`，androidMain 只留系统取色 + 系统栏。

### D7 语义层太薄

`HanimeDefaults.Colors` 只有 3 个别名，且命名是**控件名语义**而非**层级语义**：

```kotlin
pageSurface    = surfaceContainer      // 层级语义 ✓
card           = surfaceBright         // 层级语义，但角色选错
homeVideoCard  = surfaceContainerLow   // ❌ 控件名语义，绑死在"首页视频卡"
```

`homeVideoCard` 这个名字会让任何复用它的地方语义错乱（搜索页复用时叫"首页卡片"）。

### D8 缺失项（非差异，是能力缺口）

- 无 AMOLED / 纯黑模式（深色下 `surface` 是 `#130C0E`，非纯黑）
- 无内容/封面取色做种子（参考项目 animeko 有 `MaterialThemeFromPaletteAndImage`）
- 无成功/警告语义色 —— 导致 `NetworkSettings` 直接写死 Material 200 红黄绿
- 无配色体检/预览页（改主题只能靠肉眼扫全 App）

## 3. 重构方案

### 3.1 目标（按优先级）

| # | 目标 | 可验收的判据 |
|---|---|---|
| G1 | **三端同色** | iOS 与 Android/桌面配色一致，8 调色板 + 3 对比度三端全生效 |
| G2 | **层级可辨** | 卡片/页底分离度 ≥ 1.15，且明暗不对称度 ≤ 0.10 |
| G3 | **语义收敛** | 业务组件不直接点 `colorScheme.*`，只点语义 token；硬编码色清零 |
| G4 | **所见即所得** | 预设色选择器显示的是落地后的 primary，不是种子色 |

### 3.2 分层设计

```
L0 色算层   m3color Hct + 8 Scheme        （不动）
L1 角色层   ColorScheme 48 角色            （不动，补齐 iOS）
L2 语义层   HanimeThemeColors  ← 本次重点建设
L3 组件层   feature/* 只准用 L2
```

**L2 语义 token 提案**（替换现有 `HanimeDefaults.Colors`，命名全部改层级语义）：

```kotlin
object HanimeThemeColors {
    // —— 表面层级 ——
    val pageBackground: Color        // → surface（统一，不再有第二套）
        @Composable get() = MaterialTheme.colorScheme.surface

    val cardSurface: Color           // → surfaceContainerHigh（见 §3.3 选型依据）
        @Composable get() = MaterialTheme.colorScheme.surfaceContainerHigh

    val cardSurfaceMuted: Color      // → surfaceContainerLow（次级容器/内嵌块）
        @Composable get() = MaterialTheme.colorScheme.surfaceContainerLow

    val groupSurface: Color          // → surfaceContainer（分组/列表区块）
        @Composable get() = MaterialTheme.colorScheme.surfaceContainer

    val raisedSurface: Color         // → surfaceContainerHighest（浮层内/dialog 内）
        @Composable get() = MaterialTheme.colorScheme.surfaceContainerHighest

    // —— 内容 ——
    val textHigh / textMedium / textLow   // onSurface / onSurfaceVariant / onSurfaceVariant@disabled
    val divider                          // outlineVariant
    val borderStrong                     // outline

    // —— 扩展语义（M3 无对应角色，需定义，见决策点 Q3）——
    val success / warning / danger        // 状态色
    val scrim                            // scrim
}
```

### 3.3 卡片角色选型依据（实测）

32 组样本（4 种子 × 8 调色板），分离度 = 与页底 `surface` 的对比度：

| 角色 | 浅色 | 深色 | 不对称度 | 结论 |
|---|---:|---:|---:|---|
| `surfaceBright` | 1.000 | 1.494 | 0.494 | ✗ 浅色失效 |
| `surfaceContainerLow` | 1.049 | 1.061 | 0.012 | △ 太弱（比 1.000 只强一点） |
| **`surfaceContainerHigh`** | **1.165** | **1.234** | **0.070** | ✓ **推荐** |
| `surfaceContainerHighest` | 1.229 | 1.387 | 0.158 | △ 偏重，且不对称 |

**推荐 `surfaceContainerHigh`**：分离度是 `surfaceContainerLow` 的 3 倍以上（可感知），明暗差仅 0.070（对称）。

配合 M3 官方做法再加一道 `outlineVariant` 描边（FilledCard → OutlinedCard 的层级表达），浅色下即使色差弱也能看清边界。

### 3.4 分期

#### P0 — 止血（视觉变化明确，风险低）

| 项 | 改动 | 影响面 |
|---|---|---|
| P0-1 | `card` : `surfaceBright` → `surfaceContainerHigh` | 1 行，全局卡片 |
| P0-2 | 9 处 `colorScheme.background` → `HanimeDefaults.Colors.pageBackground`（= `surface`） | 9 行 |
| P0-3 | `pageSurface` : `surfaceContainer` → `surface`（与 P0-2 统一成一套） | 1 行 |
| P0-4 | `homeVideoCard` 重命名 → `cardSurfaceMuted`（值保留 `surfaceContainerLow`） | 改名，值不变 |
| P0-5 | 4 处 `surfaceVariant.copy(alpha)` → 不透明 `cardSurfaceMuted` / `raisedSurface` | 4 处 |
| P0-6 | 14 处 `surfaceVariant` → `raisedSurface`（= `surfaceContainerHighest`） | 14 处，浅深均等价或更准 |

> P0 完成后：卡片在浅色下首次可见；页面底色统一；层级表达不再依赖 alpha。

#### P1 — 补 iOS（G1 达成）

| 项 | 方案 |
|---|---|
| P1-1 | 48 角色映射下沉 `jvmMain`（androidMain / desktopMain 各删 ~90 行） |
| P1-2 | **iOS 动态色**：三选一，见决策点 Q1 |
| P1-3 | 设置项按平台能力隐藏：`useDynamicColor` 在桌/iOS 隐藏或置灰 |

#### P2 — 语义层与体验（G3 / G4）

| 项 | 方案 |
|---|---|
| P2-1 | 建 `HanimeThemeColors`（§3.2），迁移所有 `colorScheme.*` 直点（约 28 个角色、百余处） |
| P2-2 | 预设色选择器改为显示**落地 primary**（`expressiveColorScheme(seed).primary`），种子色作副色块 |
| P2-3 | 硬编码色清零：`AppearancePickers` 预览底改用当前主题；`NetworkSettings` 三档改用扩展语义色 |
| P2-4 | 扩展语义色 `success` / `warning` / `danger` 定义（见 Q3） |

#### P3 — 可选增强

- AMOLED 纯黑模式（`surface` → `#000000`，`surfaceContainer*` 同比例压暗）
- 封面取色做种子
- 配色体检页（见 §4）

## 4. 验收手段：配色体检页

新增一个 debug/设置内的 `ThemeAuditScreen`，一次性把隐性错误变成显性：

1. **48 角色色卡**：明暗各一组，按角色分组平铺，附 hex
2. **配对对比度矩阵**：`onXxx` on `xxx` 全量算一遍，< 4.5 标红（WCAG AA 正文）
3. **层级阶梯可视化**：`surface` → `surfaceContainer*` 五档横向排列，肉眼可判是否等距
4. **真实组件预览**：首页卡片 / 设置行 / Dialog / 按钮在同一屏渲染，直接看层级是否可辨

> 这页不进正式导航，挂设置页底部（debug 入口）。改配色后只看这一屏就能判定，不用扫全 App。

## 5. 需要你拍板的决策点

### Q1. iOS 动态色怎么补？（P1-2）

| 方案 | 做法 | 代价 | 效果 |
|---|---|---|---|
| **A. 纯 Kotlin HCT** | 把 m3color 的色算逻辑移到 commonMain（找 KMP 版或手写） | 中：需验证 KMP 可用性 | 三端完全一致 ✓ |
| **B. 预生成色板** | 构建期跑 JVM 色算，为 4 种子 × 8 调色板 × 3 对比度 × 明暗 = 192 种组合生成常量表，塞进 commonMain | 小：一次性生成，运行时零成本 | 三端一致 ✓，但种子色固定（够用，因为目前只有 4 个预设） |
| **C. 维持现状** | iOS 继续回退 3 角色 | 零 | ✗ 三端不一致 |

> 我倾向 **B**：项目种子色只有 4 个预设（不像壁纸取色那样需要任意输入），192 种组合全量预生成完全可行，且不需要引入新的 KMP 依赖、不影响 iOS 包体和启动耗时。

### Q2. 卡片要不要加描边？

`surfaceContainerHigh` 的 1.165 分离度在浅色下仍是"微妙"级别（M3 本来就是这样）。是否给卡片统一加 `outlineVariant` 描边来明确边界？

- 加：层级清晰，但会改变现有视觉风格（更"硬"）
- 不加：保持 M3 原味，靠色差

### Q3. 成功/警告/危险色怎么定义？

M3 没有这三个角色，需要自己定。选项：

- **a.** 从当前 scheme 派生（如 `success` =  tertiary 色系绿调）—— 随主题变，但语义不稳（TonalSpot 下 tertiary 未必是绿）
- **b.** 固定 HCT 常量（如 success = `Hct.from(140, 40, 50)`）—— 语义稳定，但不随主题
- **c.** 沿用 Material 200 固定色（现状）—— 简单但与主题脱节

### Q4. 预设色要不要调整？

现在 4 个种子色展开后 Tone 全被压到 40，用户拿到的都是"暗色版"。是否：

- **a.** 换种子色，让展开后的 primary 更接近预期（需要重新选 4 个种子并实测）
- **b.** 保持种子，只在 UI 上显示落地色（P2-2）—— 用户看到什么就得到什么
- **c.** 增加默认调色板为 `Vibrant` / `Fidelity`（这两个的 primary 更接近种子色）

```
Rainbow     #9A4057   FruitSalad #7A4998  Fidelity #934658   Content    #934658
```

> `Fidelity` 与 `Content` 的 primary 相同（两者都保留源色），差异只在 secondary / tertiary。

### 6.3 对比度档位的作用（Pink / 浅色）

| contrast | primary | onPrimary | 配对对比度 |
|---:|---|---|---:|
| 0.0（默认） | `#8A4D5A` | `#FFF7F7` | 6.05 |
| 0.5 | `#68323F` | `#FFCDD5` | 7.06 |
| 1.0 | `#421320` | `#FFCED6` | 11.19 |

> 三档在浅色下差异明显（设置项有效），深色下 primary 不变、只变 onPrimary。
