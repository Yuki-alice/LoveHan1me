# 三项目前端（UI）设计对比与优化建议

> 对比对象：
> - **本项目** `E:\LoveHan1me`（KMP + Compose Multiplatform 1.12 / Material3 Expressive，后文称 **LH**）
> - **参考 A** `E:\hanime1\references\animeko-main\animeko-main`（KMP + CMP 1.11 / Material3，后文称 **AK**）
> - **参考 B** `E:\hanime1\references\Kazumi-main`（Flutter 3.47 / Material3，后文称 **KZ**）
>
> 方式：三路并行静态代码阅读，逐页对比布局骨架与组件设计，未运行任何应用。
> 日期：2026-09-14
> 与既有文档的关系：本文件只做**横向对比 + 增量建议**。项目自审结论见
> 《前端设计体系审计报告.md》，布局类结论见《跨平台响应式布局重设计方案.md》，
> animeko 的**架构**借鉴见《animeko架构分析与借鉴.md》——那份只讲架构，本篇只讲 UI 设计。

---

## 0. 结论摘要

一句话：**LH 的设计系统（颜色 / 形状 / 动效 / 响应式）在三者中是最"重"也最完整的，但输在两处——页面内容的"形态丰富度"和工程验证基建。**

- LH 强在**底层 token 与响应式判据**：8 套命名主题板、显式 shape scale、motionScheme 驱动、
  以及 **"内容区宽度 ≠ 窗口宽度"** 这条判据（AK / KZ 都没有显式处理）。
- LH 弱在**内容组织形态**：三个首页/发现页里只有 LH 是单列 `LazyColumn` 流，没有网格密度、
  没有轮播锚点、没有"继续观看"这类横向内容区。AK 和 KZ 都是「Sliver/Grid + 折叠头图 + 多内容带」的结构。
- LH 最刺眼的工程差距：**全仓 `@Preview` 数量 = 0**（AK 约 130+，且有统一 Preview 入口）。
  这直接影响"能不能快速看一眼改得对不对"，是本次建议里性价比最高的一条。

## 2. 设计系统层对比

### 2.1 颜色与主题

| | LH | AK | KZ |
|---|---|---|---|
| 生成方式 | 8 个命名主题板（樱/竹/苍/柚/夜/雾/墨/随）+ 118KB 预生成表（48 套，三端字节一致） | seed + materialkolor `dynamicColorScheme(TonalSpot)`，Android 12+ 优先系统动态取色 | `colorSchemeSeed = Colors.green` + `dynamic_color` 插件 |
| 动态取色 | 仅"随"主题槽，且仅 Android（desktop/iOS 返回 null） | Android 31+ 全局优先 | Android 12+ 与桌面 |
| AMOLED | 正交开关（`amoled()`） | `modifyColorSchemeForBlackBackground` | `oledDarkTheme()`，可与动态取色叠加 |
| 对比度档 | **有**（standard/medium/high，接入设置链） | 无 | 无 |
| 切换动画 | 无 | **有**，`animateColorScheme` 逐字段 `animateColorAsState` | 无（Flutter 默认） |

**判读**：LH 的 8 主题板 + 对比度档是**唯一独有的差异化资产**，AK/KZ 都没有。
缺的是 AK 的两个细节：

- **`LocalDarkOnSurface`**：AK 把"暗色下的 onSurface"在 Theme 里算好一次下发
  （`AppTheme.kt:73/93`），注释明说"列表项各自生成会重复计算"。LH 若有类似散点计算，同样该提上去。
- **主题切换动画**：8 个主题板来回切时若配色瞬时跳变，观感割裂，建议补 `animateColorScheme`。

### 2.2 字阶（Typography）

| | LH | AK | KZ |
|---|---|---|---|
| 定制 | `AppTypography`，3 处修正：**bodyMedium 行高 20→22sp、bodySmall 16→18sp（CJK）、emphasized 提到 SemiBold** | 不定制，仅平台字体族替换 | 自定义 MI Sans，可切系统字体 |
| 双重编码 | 有残留：`SettingItem.kt:129` `titleMedium.copy(fontSize = 18.sp)`、`VideoCardItem` 内联 10/11/12/14sp | 无 | 大量字面量但无"语义阶"概念 |
| Expressive emphasized | 全项目仅 **2 处** | 未用 | 不适用 |

**判读**：
- CJK 行高修正是 AK/KZ 都没做的正确判断，**守住**。
- **emphasized 字阶只用了 2 处 = Expressive 最大的排版资产被浪费**。这是"白拿的分"。
- 缺自定义中文字体（KZ 有 MI Sans）。中文界面在 Windows 上落到微软雅黑、Linux 落到文泉驿，
  观感差异大——这是三端一致性里最容易补的一块。

### 2.3 形状（Shape）

| | LH | AK | KZ |
|---|---|---|---|
| 体系 | 显式 `AppShapes` 8 档（4/8/12/16/20/28/32/48）+ `Corners.pill` | 用 M3 默认 | 散落常量：10 / 12 / 24 / 28，无体系 |
| 按压插值 | **有**，`InterpolatedCornerShape` 逐角插值 | 无 | 有，`split_list_row` 按下时圆角 4→24（250ms） |
| 异形 | 无 | 无 | **有**，`material_new_shapes` 的 `cookie4Sided` 裁切图标徽标 |

**判读**：LH 这块三者最强。可补的是 KZ 的方向——**MaterialShapes 异形裁切**（空态图标徽标、
头像、状态徽章用非矩形裁切），这是 MD3 Expressive 的视觉签名，LH 现在完全没用。

### 2.4 间距与响应式

| | LH | AK | KZ |
|---|---|---|---|
| 断点 | 单源 5 档 350/600/840/1200/1600 | WSC + 自研 `isWidthAtLeastExtraLarge`(1600) | 2 档 600/840 |
| **判据** | **区分窗口宽 vs 内容区宽**（`ProvideContentWidth`），解决常驻导航占宽导致列数超算 | 用 `BoxWithConstraints.maxWidth`（注释明写"因为会被嵌进 sheet"） | `LayoutBuilder` / `MediaQuery` |
| 语义间距 | `HanimeDefaults.Spacing`（2/4/8/12/16/24/32） | `paneHorizontalPadding` 16/24、`cardHorizontalPadding` 16/20 | `StyleString.cardSpace/safeSpace` |
| 宽屏限宽 | 表单 640 / 正文 720（`ContentColumn`） | **主内容统一 `widthIn(max = 1300.dp)` + 居中** | 设置 `maxWidth 1000` 居中 |
| 布局参数 | `PageMetrics`（页边距/分类矩阵/卡片最小宽/侧栏宽） | **`SubjectDetailsLayoutParams` data class + `calculate(width)`，4 档全表** | 散在 `LayoutBuilder` 里 |

**判读**：
- 「内容宽 vs 窗口宽」是 LH 独有且正确的判据，**守住**（AK 是靠"用 maxWidth 而非窗宽"间接达到同一目的）。
- 两个具体差距：
  1. **网格主内容没有限宽**：搜索页 `GridCells.Adaptive(minWidth)` 在 1600dp+ 屏上会一直加列，
     而 AK 统一压到 1300dp 居中。超宽屏观感差别很大。
  2. **详情侧栏是硬编码 360/320 dp**：AK 把整页布局参数抽成 `@Immutable data class` 的 4 档表
     （Compact / MediumNarrow / Medium / Expanded，含 sidebar 280/340、rail 372、各间距），
     页面只查表不写魔数。LH 的 `PageMetrics` 已有一半，建议把详情页那两个硬编码也收进去。

### 2.5 动效

| | LH | AK | KZ |
|---|---|---|---|
| 规范源 | `MaterialTheme.motionScheme`（fast 27 / default 10 / slow 3） | `AniMotionScheme`（`@Immutable` + `calculate(density)`）+ `EasingDurations` 六令牌 | `PageTransitionsTheme` 按平台分流 |
| 转场 | `sharedAxisX` 走 slow spatial + effects | `NavigationMotionScheme` + 预测式返回 `predictivePopTransitionSpec` | 平台化：移动 Cupertino / 桌面 FadeUpwards |
| 共享元素 | **`SharedTransitionLayout` 已引入但 `sharedElement` 调用 = 0** | 有 `SharedTransitionKeys` | **Hero 全局铺开**（封面统一 tag + `transitionOnUserGestures`） |
| 系统动画开关 | 未见尊重 | 未见 | **有**，`MediaQuery.disableAnimationsOf` |

**判读**：这是 LH 最"亏"的一块——**舞台搭好了，演员没上场**。
`SharedTransitionLayout` 在 `SharedTopNavigation.kt:151` 就位，却没有任何 `sharedElement` 调用，
而 KZ 的 Hero 是贯穿卡片→详情→收藏的主线动效。这是投入极小、观感提升极大的一条。

## 3. 页面级对比（核心部分）

### 3.1 首页 / 发现

```text
LH：Box + 自绘 HomeTopBar(搜索框·新番·头像)
    └─ LazyColumn（单列流）
        ├─ 分类矩阵 CategoryBlock（2×4 / 3×3 / 4×2 / 5×2，按内容宽切换）
        ├─ 视频卡片列表
        └─ pullToRefresh + PullRefreshOverlay

AK：Scaffold + AniTopAppBar（滚动行为分叉：矮屏 pinned / 正常 enterAlways）
    └─ LazyVerticalGrid（限宽 1300 居中）
        ├─ NavTitleHeader（区块标题 + 右侧动作，统一组件）
        ├─ TrendingSubjectsCarousel（M3 Carousel 轮播）
        ├─ 「继续观看」LazyRow 横滑
        └─ 推荐网格

KZ：CustomScrollView + SliverAppBar(pinned, stretch, 120)
    ├─ flexibleSpace 折叠标题插值（字号 lerp 28→20、字重 w700↔w500）
    ├─ SliverGrid 3 → 5(>600) → 6(>840) 列
    ├─ 滚动 -200px 触底自动分页
    └─ FAB 回顶
```

**差距**：
1. **LH 首页是单列流，另两个是网格**。宽屏下 LH 首页左右大片留白，而 AK/KZ 用空间换信息密度。
2. **缺"内容带"结构**：AK 有轮播 + 继续观看 + 推荐三段，KZ 有折叠头图 + 网格。
   LH 靠分类矩阵撑，但那本质是**导航**，不是**内容**。首页第一屏缺少视觉锚点。
3. **缺横向内容区**："继续观看 / 最近更新"这类 `LazyRow` 是视频类 App 的标配，LH 没有。

### 3.2 搜索 / 发现结果

```text
LH：LazyVerticalGrid(GridCells.Adaptive(minWidth))，padding 全 Spacing.medium
    → 点击进入全屏详情页
AK：AniListDetailPaneScaffold（列表 + 详情双栏，宽屏同屏）
    默认 GridCells.Adaptive(360.dp)，加载态用 Expressive LoadingIndicator
KZ：M3 SearchBar 页头（minHeight 64，elevation 0）
    ├─ 未搜索态：历史记录 + 「按条件查找」入口
    ├─ showAdaptiveBottomSheet(maxHeightFactor 0.9) 出筛选面板
    └─ extentAfter > 360 触发加载更多
```

**差距**：
1. **宽屏无 List-Detail 双栏**：LH 搜索结果点进去是全屏详情页，AK 是左列表右详情。
   840dp+ 场景下体验差距明显。LH 的详情页其实已有双栏能力（≥840），但搜索页没接。
2. **缺"未搜索态"**：KZ 在没输入时给历史记录 + 条件入口，LH（推测）是空态占位。
   这是低成本高感知的一条。
3. **响应式入口三套并存**（既有自审已记录）：`SearchGridColumnsConfig`（按窗宽定列）
   + `PageMetrics.videoCardMinWidthFor`（按内容宽定最小宽）+ `GridCells.Adaptive`，
   同一页面可能走不同逻辑。建议统一到"按内容宽 → 最小宽 → Adaptive"一条链。

### 3.3 视频详情

```text
LH：contentWidth ≥ 840dp → 主栏 + 侧栏（固定 360 / 320 dp）
    VideoIntroductionScreen.kt 1515 行（含评论 / 子评论）
AK：SubjectDetailsLayoutParams 四档全表
    Compact(<600) / MediumNarrow(600~1000, sidebar 280) / Medium(1000~1600, sidebar 340)
    / Expanded(≥1600, sidebar 340 + rail 372)
    ├─ 左栏封面 + 操作，中栏区块流，右栏 RailCard
    └─ TopAppBar 双层：透明常驻 → 滚出后显示带底色标题栏
KZ：NestedScrollView + SliverAppBar.medium(expandedHeight 308)
    ├─ flexibleSpace 毛玻璃背景（0.5 降采样 + sigma 15 模糊 + 底部 48px 羽化）
    ├─ TabBar × 5（概览 / 吐槽 / 角色 / 关联 / 制作人员）
    └─ FAB.extended「开始观看」→ adaptiveBottomSheet(0.88)
```

**差距**：
1. **头图没有沉浸感**：KZ 的 308dp 折叠毛玻璃头图是整页的视觉锤，LH 详情页是平铺信息流。
   这是三者中**视觉冲击力差距最大**的一处。
2. **布局参数硬编码**：LH 的 360/320 是散在代码里的 dp 值；AK 是四档表。
   LH 的 `PageMetrics` 已有基础，把详情页收进去即可。
3. **单文件 1515 行**：拆成「头部 / 信息 / 评论 / 推荐」四个子 composable，
   既减认知负担，也让 Preview 能单独渲染子块——**这条与 P0 的 Preview 基建是绑定的**。

### 3.4 播放页

```text
LH：VideoPlayerUi.kt 1896 行，全自绘叠层（scrim 渐变 + OverlayAlpha 18 档）
AK：AdaptivePlayerScreenScaffold 三模式
    COMPACT（竖排 16:9 + TabRow）/ HORIZONTAL（左播放器 + 右侧 380 栏）/ THEATER
    ★ 用 movableContentOf 跨布局复用同一播放器实例（不重建内核）
KZ：LayoutBuilder：maxWidth > maxHeight || fullscreen || isPip → 铺满 + 悬浮 sidePanel
    + 键盘快捷键 / 指针交互 / 滚轮缩放
```

**差距**：
1. **`movableContentOf` 直接可抄**：LH 若有横竖屏 / 分栏切换，播放内核重建会造成黑帧与进度丢失。
   AK 这一手是播放器场景的标准解。
2. 1896 行单文件同上，需拆。
3. KZ 的**桌面输入**（键盘快捷键 / 滚轮缩放 / 鼠标悬停显隐）在桌面端是刚需，
   LH 已有 `playerHitTarget` 命中区机制（项目记忆里有），但键盘层未见成体系。

### 3.5 设置页

```text
LH：内容宽 ≥ 900dp → 双栏（左 280 分类 + 右栏，右栏限宽 640/720）
AK：AniListDetailPaneScaffold + 页内再嵌一层 NavDisplay（处理二级栈）
KZ：>600 → 双栏（左 280）+ SettingsPaneScope InheritedWidget，子组件自动感知是否嵌入双栏
```

**判读**：这一项 **LH 不落后**。可抄 KZ 的 `SettingsPaneScope`——用 InheritedWidget
（Compose 里是 CompositionLocal）让设置项自动适配"独立页 / 嵌入右栏"两种形态，避免写两套。

### 3.6 收藏 / 我的

```text
LH：MineScreen —— HanimeScaffold + LazyColumn(spacedBy 8)，CheckInCard / AccountCard
AK：CollectionPage —— Scaffold + SecondaryScrollableTabRow + PullToRefreshBox + 网格
    （注释明写：因为有 TabRow，不能用 PinnedBehavior，改 exitUntilCollapsed）
KZ：CollectLibraryView —— LayoutBuilder：≥1000 且 textScale ≤1.5 → 左分类 + 右内容双栏
    横向大卡（80×120 封面 + 元信息，圆角 24）+ Ctrl/Cmd+F 聚焦搜索
```

**差距**：LH 的"我的"是**设置式列表**形态，AK/KZ 是**内容型收藏页**（Tab 分类 + 网格 + 大卡）。
若 LH 的收藏是内容主体（而非入口列表），宽屏下应走网格 + 分类双栏，而不是单列列表。

## 4. 组件层对比

| 维度 | LH | AK | KZ |
|---|---|---|---|
| 组织 | `ui/component/` 平铺 26 文件 + `appbar/` `content/` `lazy/` | `ui-foundation` 156 文件，分 `widgets/ animation/ layout/ interaction/ effects/ lists/` | `lib/bean/` 分 `card/ appbar/ settings/ widget/ dialog/` |
| 卡片 | `CardContainerSurface`（按压形变 + 触感）、`VideoCardItem`（16:9 / 3:4） | 少封装，多用 M3 Card + `AniThemeDefaults` 配色 | `BangumiCardV`（`AspectRatio 0.65` + Hero）、横向大卡 |
| 空/错/载 | `EmptyContent` / `ErrorContent` / `LoadingContent` + `PageContent` 三态 | 移植 Accompanist `Modifier.placeholder` + Expressive `LoadingIndicator` | **skeletonizer 骨架屏 + 最小 600ms 展示时长** |
| 设置行 | `SettingItem`（5 种：Switch/Navigation/Info/Slider/Choice） | 复用 M3 | `SettingsList` 族 + `SplitListRow` 按下圆角 4→24 |
| 隐患 | **`AnimatedLazy.kt` 重定义了 `LazyColumn`/`LazyRow`/`LazyVerticalGrid`**（同名遮蔽官方 API） | 无 | 无 |

**判读**：
- LH 组件数量够，但**目录是平铺的**，随规模增长会失控。建议按 AK 的 five-way 分法
  （widgets / layout / interaction / effects / animation）重组——这是纯移动文件，低风险。
- **`AnimatedLazy` 同名遮蔽官方 API 是明确的技术债**：新人 import 时 IDE 无法区分，
  且官方 API 演进时容易踩坑。建议改名为 `AnimatedLazyColumn` 这类不冲突的形式。
- **骨架屏**：LH 是转圈/文案提示，KZ 是 skeletonizer + 防闪最小时长。
  网格页用骨架屏比转圈体感好很多（避免布局跳动）。

## 5. LH 要守住的优势（别在优化中丢掉）

1. **内容区宽度判据**（`ProvideContentWidth`）——AK/KZ 都没有显式处理，是独有的正确判断。
2. **8 套命名主题板 + 预生成表**——三端字节级一致的确定性配色，AK/KZ 都没有这个资产。
3. **CJK 字阶行高修正**——只有 LH 为中文做了排版修正。
4. **`InterpolatedCornerShape` 按压逐角插值**——AK 没有，KZ 是 AnimatedContainer 近似。
5. **对比度档接进设置链**——AK/KZ 都没有的无障碍深度。
6. **播放器 `OverlayAlpha` 18 档 + `playerHitTarget` 命中区机制**——精细度高于两个参考项目。

## 6. 优化建议（按投入产出排序）

### P0 — 投入小、感知强

**① 补 Preview 基建（0 → 1，最高性价比）**
- 现状：全仓 `@Preview` = 0。改一个卡片要在真机/桌面跑起来才能看，迭代成本极高。
- 做法（照抄 AK `ui/foundation/PreviewFoundation.kt:54`）：建**单一入口**
  `ProvideCompositionLocalsForPreview(darkMode)`，一次性提供导航 / 图片 loader（假图）/

   LH 用 1.12.0-alpha03 已在同一量级，不必跟进 alpha 的每次变动。

5. **KZ 的散落常量风格**（24/28/16 字面量满天飞）——这是它的短板，不是优点。
6. **AGPL 许可**：animeko 是 AGPLv3。只读参考、不复制源码（既有文档已记）。
   建议也核一下 KZ 的许可（GPL-3.0 系）后再决定借鉴深度。
