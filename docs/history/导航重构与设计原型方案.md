## 1. 原型说明（画布内容）

### 1.1 手机 · 首页（Compact，393×1080 长图）
- 状态栏 62 → **顶栏 64** → 内容区 → 底部导航 80
- **顶栏三件套**（左右都是点击热区）：
  | 元素 | 形态 | 点击去向 |
  |---|---|---|
  | 搜索框 | 胶囊 40dp，`#F0E7EA` 底，放大镜 + 「搜索番剧、角色、声优」 | 搜索页 |

### 1.5 分类区块 · 响应式矩阵规格（图例）

**矩阵由「可用内容宽度」分档，不由窗口断点分档。** 常驻 Rail 会吃掉 80–220dp，用窗口宽度会在桌面端误判（840dp 窗口 + 220dp Rail 只剩 620dp，还按 Expanded 排 4 列就会挤）。阈值按**最小卡宽 170dp** 反推：

| 可用内容宽度 | 矩阵 | 卡片数 | 卡片宽 / 间距 |
|---|---|---|---|
| < 540 | 2 列 × 4 行 | 8 | ≈172 / 12 |
| 540–759 | 3 列 × 3 行 | 9 | ≈172–206 / 16 |
| 760–1049 | 4 列 × 2 行 | 8 | ≈180–210 / 16 |
| ≥ 1050 | 5 列 × 2 行 | 10 | ≈200–246 / 20 |

落到常见设备上：

| 场景 | 窗口（Rail） | 可用内容宽 | 命中 |
|---|---|---|---|
| 手机竖屏 | 393（底栏不占宽） | ≈361 | 2 × 4 |
| 竖屏平板 | 768（折叠 Rail 80） | ≈656 | 3 × 3 |
| 平板横屏 | 1024（折叠 Rail 80） | ≈912 | 4 × 2 |
| 笔电 1440 | 1440（展开 Rail 220） | ≈1188 | 5 × 2 |
| **桌面 1920×1080** | 1920（展开 Rail 220） | **≈1636** | **5 × 2 ✅ 会触发** |

两条补充规则（回应「5×2 是不是太苛刻」）：
- **1920×1080 确实会触发 5×2** —— 扣掉 220dp Rail 与 64dp 左右边距仍有 ~1636dp，远高于 1050 下限。5 列是这个宽度下**唯一合理**的排法：换成 4 列，卡片会被拉到 ~380dp 宽，封面高度随之膨胀，一屏放不下两行。
- **5×2 只出现在「纯内容页」**（首页、各类列表）。**双栏页（视频详情：内容 + 360dp 侧栏）4 列封顶**，不参与 5 列分档 —— 剩下 ~1340dp 走 4 列更舒服。
- 数据源固定 10 个卡片 → **超出「列×行」的部分收进「更多」**；不足则少显示，不补空位。

## 2. 为什么是「首页 / 发现 / 我的」这三个

内容消费类应用的信息架构本质上只有三种意图：

| 意图 | 用户心理 | 对应目的地 |
|---|---|---|
| **发现内容** | 「有什么好看的」 | 首页（推荐流、更新、榜单） |
| **主动检索** | 「我要找某一部」 | **发现**（搜索 + 浏览态） |
| **我的内容** | 「我看过 / 收藏的」 | 我的（收藏、历史、订阅、下载…） |

横向对照：YouTube 的 Home / Subscriptions / **Library**、Plex 的 Home / Search / **My Libraries**、Twitch 的 Following / Browse / **Library** —— 都是「发现 + 检索 + 我的」三段式。

**关键判断 A：为什么叫「发现」而不是「搜索」？**
这一栏承载的不只是搜索框，还有搜索历史、热门标签、分类/年份筛选、排行榜等内容浏览态。只叫「搜索」会把它窄化成一个工具入口；叫「发现」才配得上一个常驻一级位置。**功能实现仍是原来的搜索界面**（图标换指南针，语义从「一个输入框」升级为「一个探索空间」）。

**关键判断 B：为什么不加第 4 个 tab（订阅）？**
订阅的**消费行为**（看更新）已被首页的「关注更新」模块覆盖；**管理行为**（增删订阅）属于「我的内容」，放 L2 语义更正确。
**v4 已拍板：保持 L2。** 追加一条硬理由 —— **订阅的后端依赖用户登录态**，做成一级 tab 会出现「未登录点进去是空页」的死状态；留在「我的」入口里可以就地降级（未登录时该行标灰 + 提示登录）。
→ 这仍是**可逆决策**：若埋点显示订阅打开率 > 30%，从「我的」提升为 L1 的成本只有一个枚举值 + 底栏加一项。

**关键判断 C：设置为什么不是一级目的地？**
设置是「工具」不是「内容空间」，用户没有「去设置逛逛」的诉求。它应该出现在**两个可预期的地方**：Rail 底部（大屏常驻）+ **「我的」页顶栏齿轮**（小屏）。改造后它彻底退出一级导航。
**v4 补充**：设置是**独立全屏路由**，进去之后不显示 Rail（和视频详情同构），但内部做**响应式双栏**（左分类 280dp / 右内容限宽 840，见 §7.4）。

**关键判断 D：签到去哪了？**
签到是「每天点一次的动作」，不是常驻内容空间，不该占一级 tab。**v4 已定：落在「我的」页首卡**（登录卡之上）—— 它天然属于「我的」语义，也不打扰首页的浏览节奏。首页顶栏不再放签到。
（首卡是**常显**的，未登录时按钮降级为「登录后签到」并跳登录，不隐藏整卡；显隐由已有的 `enable_check_in_feature` 开关控制。）

## 5. 悬浮导航栏（设置项规格）

**命名**：`外观与布局 › 导航栏样式` → 标准贴底 / 悬浮胶囊
**默认**：标准贴底
**作用域**：**只影响 Compact 宽度下的底栏形态**；Medium+ 的 NavigationRail 不受影响

**形态参数**：3 个等距 pill 装在圆角胶囊容器内，距屏幕左右 16dp、距底部 16dp + 系统手势 inset；容器 `surfaceContainer` 底 + 中等 elevation。

**⚠️ 落地最容易漏的一点：内容遮挡补偿**
悬浮态不再占据布局高度，`Scaffold` 的 `innerPadding` 算不到它。必须把
`navBarHeight + 16.dp(底部间距)` 显式加进列表的 `contentPadding`，
否则**最后一条内容会被胶囊盖住**。反之，悬浮态下 `ProvideContentWidth` 不需要再扣水平空间。

## 6. `tabletMode` 的退场

**现状**：`tabletMode`（用户开关）`&& isLandscapeOrientation()` 共同门控视频页双栏。
**目标**：删除开关，改由 **可用内容宽度** 单点驱动。

| 判据 | 阈值 |
|---|---|
| 单栏 / 双栏分界 | 内容宽度 ≥ **840dp** |
| 侧栏宽度 | 固定 **360dp**；内容宽度 < 1000dp 时降到 **320dp** |

**为什么用「内容宽度」而不是「窗口宽度」**：常驻 Rail 会吃掉 80–220dp。1024dp 窗口减去 220dp 只剩 804dp，用窗口宽度判断会误判成「够宽」。直接用项目已有的 `rememberContentWidthDp`（`ui/adaptive/`）。

**迁移**：从 `UserPreferences` 移除 `tabletMode`，设置页删该项，不做值迁移（新布局在所有宽度下都不劣于旧布局），Release Notes 写一句说明。

## 7. 路由树重构

### 7.1 目标路由树

```
│  ├─ Tab.Home      : HomeRoute
│  │                   ├─ NewAnimeList                ← 顶栏「新番列表」入口
│  │                   └─ VideoDetail(videoId)        ← 全屏 push，覆盖导航
│  ├─ Tab.Discover  : SearchRoute                     ← 原搜索界面，改名「发现」
│  │                   ├─ SearchResult(query)
│  │                   └─ VideoDetail(videoId)
│  └─ Tab.Mine      : MineRoute
│                      ├─ MineSection(type)           L2：6 个走同一模板
│                      ├─ PlaylistDetail(id)
│                      ├─ SubscriptionDetail(id)

```

| 设置作为 9 个 tab 之一 | 普通全屏路由 | 从「我的」顶栏齿轮 / Rail 底部进 |

### 7.3 四个必须在改造时补上的边界

1. **视频详情页要脱离导航宿主**（新决策）。既然详情页不显示 Rail，它就不能是 `MainScaffold` 的子节点，而应是**独立的全屏路由**，从三个 tab 都能 push 进来。
2. **冷启动深链**：从分享链接直达 `VideoDetail(videoId)` 时返回栈为空，返回会直接退出应用。必须补「先塞 `MainTab.Home` 再 push 详情」。
3. **每个 tab 的滚动位置**：`TopLevelBackStack` 保栈不保滚动位置，`rememberLazyListState` 需要提升到 tab 作用域。
4. **播放器全屏**：详情页进 `Player` 时应隐藏详情页自己的顶栏，避免播放区被压缩。

### 7.4 设置页的双栏化（v4 新增）

**先给结论：设置页是「无 Rail」这件事零成本，双栏才是真正要做的活。**

`设置` 现在就已经是 `MainScaffold` 之外的独立全屏路由（`SettingsScaffold`，见 `app/navigation/settings/SettingsNavHost.kt`），**它本来就不显示 NavigationRail**。所以「和详情页一样」这半句不用改任何东西，只需要保证重构后**不要把它挂回 `MainScaffold`**。

双栏改造的关键发现：**左栏分类不需要新数据结构 —— `SettingsDestinationSpec` 枚举现成就是分类表。**

| 枚举值 | 左栏标签 | 右栏来源 |
|---|---|---|
| `VideoPlayback` | 视频播放 | 视频语言 / 默认画质 / 画中画 / 播放记录 / 进阶（Player、Mpv、HKeyframe 三个子页入口） |
| `NetworkDownload` | 网络与下载 | 域名选择、移动数据提醒、深度链接、下载设置 |
| `Appearance` | 外观 | 动态取色 + 色板、应用语言 |
| `InterfaceInteraction` | 界面与交互 | **导航栏样式**（§5）、首页分类布局、触感反馈、预测返回 |
| `DataPrivacy` | 数据与隐私 | 安全模式、伪装图标、备份/恢复、缓存、本地与在线数据 |
| `DeveloperOptions` | 开发者选项 | 更新卡片、DPI、触发崩溃 |
| `About` | 关于 | 版本、开发者、用户条款、GitHub、**开源许可**（并入，不单列） |

- `Home` 不单列 —— 它现在的角色是「把所有 section 堆在一页」，双栏形态下这个角色由「左栏 + 默认选中第一项」承担。
- 分类 + 内容的渲染骨架：
  - **Compact / Medium**：单栏，`LazyColumn` + 分区标题（现状形态，基本不动）
  - **Large / XL**（可用内容宽度 ≥ 900dp）：`Row { 分类栏(280dp, `#F6EDF1`) + 内容区(fill) }`；内容区**复用现有那个 `widthIn(max = HanimeDefaults.Widths.contentMax)`（=840dp）并居中**
- **顺带拆文件**：`HomeSettingsScreen.kt` 现在 741 行、把 7 个分类的 section 全塞在一起。双栏化正好是把它按上表拆成 7 个 `@Composable` 的时机——**这也是本次重构里收益最直接的一次重构**。
- 状态保留：左栏选中项是**分类**，右栏是分类内容，所以不存在「双栏各有一套返回栈」的问题；`SettingsScaffold` 的 `TopLevelBackStack<HanimeScreen>` 继续管右栏的子页钻取（如 `PlayerSettingsRoute`）。

**阈值**：左栏 280dp 是正文可读性的下限保护——它要求可用内容宽度 ≥ 900dp（280 + 620 的窄内容区）才切双栏；低于此走单栏。这与 §8 的 Expanded 断点（840dp）基本重合，实现时**以 `rememberContentWidthDp() >= 900` 为准**，不要用窗口宽度。

## 8. 断点 × 布局规格

| 断点 | 宽度 | 导航形态 | 并存栏数 | 分类矩阵（见 §1.5） | 边距 / 间距 |
|---|---|---|---|---|---|
| Compact | < 600 | NavigationBar（可切悬浮） | 1 | 2 × 4 | 16 / 12 |

| Expanded | 840–1199 | NavigationRail 折叠 80dp | 2 | 4 × 2 | 24 / 16 |
| Large | 1200–1599 | NavigationRail 展开 220dp | 2 | 5 × 2 | 32 / 20 |
| Extra-large | ≥ 1600 | NavigationRail 展开 220dp | 3 | 5 × 2 | 40 / 24 |

> 表里的「分类矩阵」只是该断点下的**典型值**。实现上矩阵**读可用内容宽度**取档（§1.5），不读窗口断点 —— 两者在「Rail 展开」的窗口里会差 220dp。

补充规则：

- 文本型页面（设置右栏、简介正文）**限宽 840dp 居中**，保证 40–60 字符/行
- 网格列数统一由 `ui/adaptive/` 按**内容宽度**推导，删掉 `HorizontalCardCountConfig` 那类可调列数
- `ui/adaptive/Breakpoints.kt` 需新增 `ExtraLarge(1600)` 一档；「可用内容宽度」复用已有的 `rememberContentWidthDp`

### ⚠️ 相对设计稿的一处**有意偏离**：签到卡的登录门控

设计稿 §1.2 / §11 决策 1 写的是「未登录时按钮降级为『登录后签到』并跳登录页」。
**这条没有照做**，理由：

那条推理的前提是**原站签到是服务端功能、前提是登录**。但本项目落地后的签到是完全
**本地**的 —— Room 本地库（`CheckInRecordEntity` / `CheckInDao`）+ `CheckInCalendarViewModel`，
记录存在设备上，与 `SettingsRepository.loginStateFlow` **没有任何耦合**。

若照设计稿加登录墙，等于给一个本来就免登录可用的本地功能凭空设卡：用户登录后也**不会**
多出任何能力（没有云端同步、没有积分）。

因此实现为：**未登录也照常可用**（`MineRouteScreen` 已加注释说明）。
若后续真的把签到接回服务端，再补回降级逻辑。

**设置项**：`外观与布局 › 导航栏样式`（标准贴底 / 悬浮胶囊，默认贴底）。
数据链路 `NavBarStyle` 枚举 → `AppSettings` → `DataStoreManager` → `SettingsRepository`
→ `HomeSettingsUiState` → 界面与交互分类里的 `SettingNavigationItem` + `ChoiceDialog`。
四条三语字符串：`nav_bar_style` / `_summary` / `_standard` / `_floating`。

**悬浮形态**：`MainScaffold` 的 Compact 分支新增一态。M3 Expressive **没有重做
NavigationBar**，所以是自研 composition（`Surface` 胶囊 + 3 个 pill，距左右 16dp、
距底 16dp + `navigationBarsPadding()`）。

**⚠️ 遮挡补偿的关键实现**：悬浮胶囊不占布局高度，`Scaffold.innerPadding` 算不到它。
解法是 **bottomBar 放一个等高的透明占位**（`FloatingNavBarReserve = 88.dp` + 手势 inset），
真正的胶囊用 `Box.align(BottomCenter)` 浮在上面。这样各列表页的 `contentPadding`
**一行都不用改** —— 否则要给十几个页面逐个加底部 padding，必漏。

**动效统一**：清掉 8 处硬编码 `tween`：
- 新增 `ui/theme/Motion.kt` 的 `contentFade()`，替换三处
  `fadeIn(tween(300)) togetherWith fadeOut(tween(200))`（首页 / 播放列表 / 订阅）；
- `VideoShellContent` 侧栏宽度 `tween(300)` → `defaultSpatialSpec()`；
- `PreviewContent` 的 320/260/220/170/420/190 → 按语义映射到
  `slow/default/fastSpatialSpec` + `default/fastEffectsSpec`。

两个实现坑（都编译期才暴露）：
1. **`transitionSpec` 的 lambda 不是 `@Composable`**，而 `MaterialTheme.motionScheme.*`
   是 —— 必须在外部先取好 spec 再引用（项目里 `SharedTopNavigation` 的
   `defaultTransition` 就是这么写的）。
2. **位移 spec 的类型参数是 `IntOffset` 不是 `Int`**（slide 动画的是偏移向量），
   fade 才是 `Float`。
