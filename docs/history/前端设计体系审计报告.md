## 二、做得好的部分（不是客套，是可以作为基线保留的）

### 2.1 M3 Expressive 是真的落地了，不是只 import 了名字

- `ui/theme/Theme.kt:54` 使用 `MaterialExpressiveTheme` 装配，而非 `MaterialTheme`。
- 全项目 **21 处** `MaterialTheme.motionScheme.*`，动效规格走 token 而不是裸 `tween`。
- `ui/theme/Shape.kt` 里的 `InterpolatedCornerShape` 是**标准且正确**的做法：`ButtonShapes.pressedShape`
  在动画中间态需要逐角插值（四个角半径分别按 progress 插值并对 `size.minDimension / 2` 做 clamp），
  很多人图省事直接 `if (pressed) pressed else normal`，按压会跳变。
- 组件层已采用 Expressive 组件族：`LoadingIndicator`(21 处)、`FAB menu`(9 处)、
  `FilledTonalButton`(16 处)、`WavyProgressIndicator`(2 处)、`IconButtonDefaults.shapes()`。

### 2.2 颜色治理很干净

非 theme 目录只有 **9 处**硬编码 `Color(0x…)`，且基本都是语义合理的：

```
ui/component/VideoCardItem.kt:183         Color(0x9F000000)          封面底部渐变遮罩
feature/settings/NetworkSettingsScreen.kt:463-465 / 514-516
                                          Color(0xFF4CAF50/FFC107/F44336)  网速分级
feature/settings/AppearancePickers.kt:367-368
                                          Color(0xFF1B1B1F/0xFFFFFBFF) 主题预览色块
```

`ui/theme/Defaults.kt:46-55` 把 M3 的 surface 色阶收敛成三个语义别名，
这是很正确的做法——调用方写 `HanimeDefaults.Colors.card` 而不是
`MaterialTheme.colorScheme.surfaceBright`：

```kotlin
object Colors {
    val pageSurface: Color  get() = MaterialTheme.colorScheme.surfaceContainer
    val card: Color         get() = MaterialTheme.colorScheme.surfaceBright
    val homeVideoCard: Color get() = MaterialTheme.colorScheme.surfaceContainerLow
}
```

### 2.3 响应式与交互细节有意识投入

- `ui/adaptive/Breakpoints.kt` 把此前三套各自为政的宽度魔数收敛成单源
  （`HorizontalCardCountConfig` 的 350/600/840、`SearchGridColumnsConfig` 的 600/**900**/1200、
  `App` 常驻抽屉判定的 840），并附带了收敛原因的注释。
- `ui/adaptive/WindowSize.kt` 区分了**整窗宽度**与**内容区可用宽度**：
  `ProvideContentWidth` 在导航宿主处测量真实内容区宽度并下发，避免常驻抽屉占掉的约 360dp 被算进去
  （注释里记录了这个 bug：840dp 窗口下内容区仅约 480dp，却按 840dp 算列数，卡片被压扁）。
  这是很多 Compose 项目会踩且不自知的坑。
- 交互手感：`rememberHapticFeedback`、`shapeByInteraction`、`animateContentSize`、
  抽屉头卡片按压 0.98 缩放（`app/main/MainDrawerContent.kt:84-87`）——这些是"手感"层面的投入。

## 三、需要修正的问题（按优先级）

### P0 —— 间距体系有两套，而且同名不同值 ✅ **已于 2026-09-12 收敛**

| 名字 | `ui/theme/Defaults.kt`（`HanimeDefaults.Spacing`） | `ui/theme/Dimens.kt`（顶层常量） |
|---|---|---|
| ExtraSmall | 2 | 2 |
| Small | 4 | 4 |
| Medium / Normal | **8** | **16**（`SpacingMedium`） |
| Large | **12** | **16**（`SpacingLarge`） |
| ExtraLarge | 16 | 24 |

两个问题：

1. **同名不同值**：`SpacingMedium` 在 A 里是 8、在 B 里是 16，差一倍。
   这类冲突不会编译报错，只会让"改一处全局生效"这个前提静默失效。
2. **`Dimens.kt` 里 `SpacingMedium == SpacingLarge == 16`**，等于有名字没档位。

建议：以 `HanimeDefaults.Spacing` 为唯一源，按 M3 的 8dp 基准补齐阶梯
（4 / 8 / 12 / 16 / 24 / 32），`Dimens.kt` 只保留 `VideoNormalCardMinWidth` 这类尺寸常量。

> **收敛记录（2026-09-12）**
>
> 实测冲突面比上面那张表描述的小得多：两套里真正被使用的是 `SpacingNormal`（32 处）
> 与 `SpacingLarge`（2 处），其余 4 个常量（`SpacingExtraSmall` / `SpacingSmall` /
> `SpacingMedium` / `SpacingExtraLarge`）**零引用**。所以「同名不同值」的静失效风险
> 当时尚未真正爆发——但它随时会因为有人第一次去用 `SpacingMedium` 而爆。
>
> 做法：
> 1. `HanimeDefaults.Spacing` 补齐 24 / 32 两档（`extraExtraLarge` / `huge`），
>    `itemHorizontal` / `itemVertical` 改为引用档位而非裸值；
> 2. `Dimens.kt` 删掉全部 6 个 `Spacing*` 常量，只留尺寸常量；
> 3. 34 处引用按**值一一对应**替换：`SpacingNormal`(8) → `Spacing.medium`(8)、
>    `SpacingLarge`(16) → `Spacing.extraLarge`(16) —— **视觉零变化**，
>    只换了名字与单一真源。
>
> 踩到一个批量改写的坑：正则替换会**连 import 行和 KDoc 一起改**，把
> `import lovehan1me.ui.theme.SpacingNormal` 变成非法的
> `import lovehan1me.ui.theme.HanimeDefaults.Spacing.medium`。批量脚本务必先删旧 import
> 再做标识符替换，或事后统一兜一遍 `^import .*HanimeDefaults\.` 这类畸形行。

### P0 —— 字阶等于没做 ✅ 第一步已完成（2026-09-12）

> **收敛记录（2026-09-12）**：新建 `ui/theme/Type.kt`，以 `Typography().copy(...)` 定义

> ① `bodyMedium` 行高 20→22sp、`bodySmall` 16→18sp —— CJK 行高修正（M3 基准按拉丁文排版设计，
> 中文同字号下信息密度更高，行高偏紧）；② `bodyMediumEmphasized` / `bodySmallEmphasized`

> ③ size 一律沿用 M3 基准不动。四目标编译通过 + 静态校验「待人工 0」。

> `VideoCardItem.kt` 内联 10/11/12/14sp）先不动——先在真机/桌面端确认这版 Typography 的观感，
> 再决定是收编进 token 还是保留特例。

- 使用分布全是默认阶梯：

```

typography.titleMedium  36      typography.labelMedium   17
typography.bodySmall    35      typography.headlineSmall  9
typography.labelSmall   24      typography.bodyLarge      9
```

这里用了 2 次。

  `ui/component/VideoCardItem.kt` 内联 10/11/12/14sp 与 `style = labelSmall` 混用。

### P1 —— 动效 token 只覆盖一半 ✅ 已完成（2026-09-12）

> **收敛记录（2026-09-12）**：
> ① **M2 时代的共享轴落地重写**：`Motion.kt` 的 `materialSharedAxisX`（`tween(300,
> FastOutSlowInEasing)` + 手写 `ProgressThreshold` 错峰）整体删除，替换为 motionScheme 驱动的
> `sharedAxisX` —— **位移走 slow spatial**（页面级转场位移最大，正是 slow 档的目标场景）、
> 淡入 default / 淡出 fast effects。连带删掉 `DefaultMotionDuration` 常量与错峰辅助扩展。
> 有意偏离：不再做淡入淡出错峰（原来先淡出 35% 再淡入），改为位移+淡化同时进行 ——
> 弹簧档位自己会收节奏，手工错峰会和物理打架。
> ② **调用点约束**：`transitionSpec {}` 与 entry metadata 的 lambda 都**不是 @Composable**，
> 转场规格必须先在 composable 体内算好再传（`pageForward` / `pageBackward` 两个 val）——
> 直接在新 lambda 里调 motionScheme 会编译不过。
> ③ **顶层 Tab 切换也接 slow**：`defaultTransition` 从 `defaultSpatialSpec` 提到 slow spatial，
> tab 切换同样是整屏换内容，此前完全没有呼吸感。
> ④ **清掉剩余硬编码 tween**：`AnimatedLazy` 列表项入场（100ms 透明度 / 180ms 缩放）→
> fast effects / fast spatial；`TagChipGroup` 箭头旋转与折叠高度（240ms）→ default spatial。
> **有意保留 1 处**：`VerticalScrollbar` 的 `fadeOutDurationMillis = 500` —— 它是「静止后
> 自动隐去」的提示性淡化，不是状态转场，用弹簧反而像抖动，已在代码注释里写明原因。
> ⑤ 结果：`motionScheme.*` 分布 fast 27 / default 10 / **slow 3**（此前 slow 仅 1 处），
> 硬编码 tween 调用仅剩上述 1 处有意保留。四目标编译 + 静态校验「待人工 0」。

- 21 处 `motionScheme.*` 的分布：`fastEffectsSpec` 12 / `fastSpatialSpec` 6 /
  `defaultEffectsSpec` 2 / `defaultSpatialSpec` 1。
  **几乎全是 fast 档，slow 档未使用**——页面级转场没有呼吸感，等于把弹簧物理降级回了 tween。
- 另有 **8 处硬编码 `tween(200/220/260/300/320/420)`** 直接绕过 token，
  其中 3 处 `tween(300)` 出现在 `feature/home/homepage/SharedHomeScreen.kt:186`
  的 `AnimatedContent`。
- `ui/theme/Motion.kt:21` 的 `DefaultMotionDuration = 300` 是硬编码常量，
  且 `materialSharedAxisX` 用的是 M2 时代的 `FastOutSlowInEasing`，
  与 Expressive 的弹簧物理不是同一种语言。
